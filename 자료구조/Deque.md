## 덱의 정의

**덱(Deque)은 양쪽 끝에서 데이터를 삽입하고 삭제할 수 있는 선형 자료구조이다.** 이름은 **Double-Ended Queue**의 줄임말이며, 일반적으로 ‘덱’이라고 읽는다.

일반적인 큐는 뒤에서 데이터를 넣고 앞에서 데이터를 꺼내지만, 덱은 앞과 뒤를 모두 입구와 출구로 사용할 수 있다.

```
             앞쪽(front)               뒤쪽(back)
삽입·삭제 가능  ↔  [ A ] [ B ] [ C ] [ D ]  ↔  삽입·삭제 가능
```

덱에서 중요한 것은 **데이터가 들어온 순서만으로 제거 위치가 정해지지 않는다는 점**이다. 프로그램이 앞쪽과 뒤쪽 중 어느 쪽에서 데이터를 꺼낼지 선택한다.

---

## 스택·큐와의 차이

스택, 큐, 덱은 모두 데이터를 순서대로 저장하지만, 삽입과 삭제를 허용하는 위치가 다르다.

|구분|삽입 위치|삭제 위치|동작 특성|
|---|---|---|---|
|스택(Stack)|한쪽 끝이다.|삽입하는 쪽과 같은 끝이다.|나중에 넣은 데이터를 먼저 꺼내는 LIFO 방식이다.|
|큐(Queue)|뒤쪽이다.|앞쪽이다.|먼저 넣은 데이터를 먼저 꺼내는 FIFO 방식이다.|
|덱(Deque)|앞쪽과 뒤쪽이다.|앞쪽과 뒤쪽이다.|사용하는 연산에 따라 스택이나 큐처럼 동작한다.|

예를 들어 덱의 뒤쪽에서만 삽입하고 삭제하면 스택처럼 동작한다.

```
뒤에 삽입: A → B → C
뒤에서 삭제: C → B → A
```

덱의 뒤쪽에서 삽입하고 앞쪽에서 삭제하면 큐처럼 동작한다.

```
뒤에 삽입: A → B → C
앞에서 삭제: A → B → C
```

따라서 **덱은 스택과 큐의 동작을 모두 표현할 수 있는 자료구조이다.**

## 덱의 기본 연산

덱의 핵심 연산은 앞뒤 삽입과 앞뒤 삭제의 네 가지이다. 실제 함수 이름은 프로그래밍 언어와 라이브러리에 따라 달라진다.

|연산|의미|
|---|---|
|`push_front(x)`|앞쪽에 데이터 `x`를 추가한다.|
|`push_back(x)`|뒤쪽에 데이터 `x`를 추가한다.|
|`pop_front()`|앞쪽 데이터를 제거하고 반환한다.|
|`pop_back()`|뒤쪽 데이터를 제거하고 반환한다.|
|`front()`|앞쪽 데이터를 제거하지 않고 조회한다.|
|`back()`|뒤쪽 데이터를 제거하지 않고 조회한다.|
|`is_empty()`|덱이 비어 있는지 확인한다.|
|`size()`|저장된 데이터의 개수를 반환한다.|

### 연산 과정 예시

처음에는 덱이 비어 있는 상태이다.

```
초기 상태          []
push_back(10)      [10]
push_back(20)      [10, 20]
push_front(5)      [5, 10, 20]
push_front(1)      [1, 5, 10, 20]
pop_back()        [1, 5, 10]       → 20 반환
pop_front()       [5, 10]          → 1 반환
```

이 상태에서 `front()`는 `5`를 반환하고, `back()`은 `10`을 반환한다. 조회 연산은 데이터를 제거하지 않으므로 덱의 내용은 그대로 유지된다.

---

## 덱은 어떻게 구현하는가

덱은 **어떤 연산을 제공하는지를 정의한 추상 자료형**이다. 반드시 하나의 정해진 내부 구조를 사용해야 하는 것은 아니다.

대표적으로 원형 배열과 이중 연결 리스트로 구현한다.

### 원형 배열을 이용한 구현

원형 배열은 배열의 마지막 위치 다음을 첫 번째 위치처럼 취급하는 구조이다.

일반 배열에서 앞에 데이터를 삽입하려면 기존 원소들을 한 칸씩 옮겨야 할 수 있다. 원형 배열은 원소를 이동하는 대신 **앞쪽 위치를 나타내는 인덱스를 변경**하여 이 문제를 해결한다.

다음은 용량이 6인 원형 배열의 예시이다.

```
물리적 배열 위치    0    1    2    3    4    5
저장된 데이터     [G]  [H]  [ ]  [D]  [E]  [F]
                                ↑
                              front

논리적인 데이터 순서: D → E → F → G → H
```

배열에서는 데이터가 두 구간으로 나뉘어 있지만, 덱에서는 하나의 연속된 순서로 해석한다. `F` 다음 원소는 배열의 처음으로 돌아가서 찾은 `G`이다.

배열의 용량을 `C`, 맨 앞 원소의 인덱스를 `head`라고 하면, 앞에서부터 `i`번째 원소의 실제 위치는 다음과 같다. 여기서 `i`는 0부터 시작한다.

```
실제 인덱스 = (head + i) % C
```

`%`는 나머지 연산이다. 이를 이용하면 인덱스가 배열의 끝을 넘어갈 때 처음으로 돌아가게 할 수 있다.

#### 앞쪽에 삽입하는 과정

배열에 빈 공간이 있다는 전제에서 다음과 같이 처리한다.

1. `head`를 한 칸 앞으로 이동한다.
2. 새로운 `head` 위치에 데이터를 저장한다.
3. 저장된 원소 수를 1 증가시킨다.

```
head = (head - 1 + C) % C
```

`C`를 더하는 것은 음수 인덱스를 피하기 위한 처리이다.

#### 뒤쪽에 삽입하는 과정

현재 원소 수를 `size`라고 하면, 새로운 데이터를 저장할 위치는 다음과 같다.

```
삽입 위치 = (head + size) % C
```

해당 위치에 데이터를 저장한 뒤 `size`를 1 증가시킨다. 기존 원소를 전부 옮길 필요가 없으므로 빈 공간이 있는 동안에는 양쪽 삽입을 일정한 시간에 처리할 수 있다.

#### 배열이 가득 찬 경우

고정 크기 배열이라면 추가 삽입을 거부하거나 별도의 정책에 따라 처리한다.

크기가 늘어나는 배열이라면 더 큰 배열을 만들고 기존 원소를 복사한다. 이때 한 번의 확장에는 원소 수에 비례하는 **O(n)** 시간이 걸린다.

하지만 용량을 일정 비율로 늘리는 방식으로 구현하면, 여러 번의 삽입에 걸친 비용을 나누어 계산했을 때 삽입 한 번의 비용은 **분할 상환 O(1)**이 된다.

### 이중 연결 리스트를 이용한 구현

이중 연결 리스트는 각 노드가 데이터와 함께 이전 노드, 다음 노드의 위치를 저장하는 구조이다.

```
front                                  back
  ↓                                      ↓
[A] ⇄ [B] ⇄ [C] ⇄ [D]
```

각 노드는 개념적으로 다음 정보를 가진다.

```
노드 = 이전 노드 참조 + 데이터 + 다음 노드 참조
```

덱이 맨 앞 노드와 맨 뒤 노드를 가리키는 참조를 유지하면, 양쪽 끝에서 일부 연결만 바꾸어 삽입과 삭제를 수행할 수 있다.

예를 들어 앞쪽에 새 노드 `X`를 삽입하는 과정은 다음과 같다.

```
삽입 전: front → [A] ⇄ [B] ⇄ [C]

삽입 후: front → [X] ⇄ [A] ⇄ [B] ⇄ [C]
```

전체 노드를 순회하지 않으므로 양쪽 끝의 삽입과 삭제는 **O(1)**이다. 다만 실제 실행 시간에는 노드의 메모리 할당과 해제 비용도 영향을 준다.

각 노드가 연결 정보를 추가로 저장하므로 메모리 사용량이 늘어나며, 노드들이 메모리에 흩어져 있어 배열보다 캐시 활용에 불리할 수 있다.

---

## 시간 복잡도

덱의 성능은 내부 구현에 따라 달라진다. 다음 표는 대표적인 구현을 기준으로 한 것이다.

|연산|원형 배열 기반 덱|이중 연결 리스트 기반 덱|
|---|---|---|
|앞뒤 원소 조회|O(1)이다.|O(1)이다.|
|앞뒤 삽입|빈 공간이 있으면 O(1)이다.|O(1)이다.|
|앞뒤 삭제|O(1)이다.|O(1)이다.|
|인덱스로 원소 접근|O(1)이다.|O(n)이다.|
|값으로 원소 검색|O(n)이다.|O(n)이다.|
|중간 위치 삽입·삭제|원소 이동 때문에 일반적으로 O(n)이다.|위치 탐색까지 포함하면 O(n)이다.|

배열 기반 덱의 크기 확장이 발생하는 삽입은 O(n)이지만, 일반적인 기하급수적 확장 정책에서는 삽입 비용이 분할 상환 O(1)이다.

이중 연결 리스트에서는 **대상 노드를 이미 알고 있다면** 연결 변경 자체는 O(1)이다. 하지만 원하는 노드를 찾기 위해 순회해야 한다면 전체 연산은 O(n)이 된다.

또한 모든 덱이 인덱스 접근을 지원하는 것은 아니다. 덱이라는 이름만으로 임의 위치 접근 성능까지 판단해서는 안 된다.

## 분할 상환 O(1)의 의미

**분할 상환 O(1)은 모든 개별 연산이 항상 같은 시간에 끝난다는 뜻이 아니다.** 비용이 큰 연산이 가끔 발생하더라도, 연속된 여러 연산의 총비용을 기준으로 보면 연산당 비용이 상수 수준이라는 뜻이다.

예를 들어 배열 용량이 다음처럼 두 배씩 늘어난다고 가정한다.

```
용량: 4 → 8 → 16 → 32 → 64
```

확장 시 복사하는 원소 수는 다음과 같이 누적된다.

```
4 + 8 + 16 + 32 + …
```

이 누적 복사량은 전체 삽입 수에 비례하는 수준이다. 따라서 n번의 삽입에 드는 총비용이 O(n)이고, 삽입 한 번당 분할 상환 비용은 O(1)이다.

이 방식은 평균적인 처리량에는 효율적이지만, 개별 연산의 지연 시간을 엄격하게 제한해야 하는 상황에서는 확장 비용을 따로 고려해야 한다.

## 덱의 주요 활용 사례

### 스택과 큐의 동작 구현

덱의 한쪽 끝만 사용하면 스택으로 활용할 수 있다. 한쪽 끝에 넣고 반대쪽 끝에서 꺼내면 큐로 활용할 수 있다.

```
스택 방식: push_back + pop_back
큐 방식:   push_back + pop_front
```

한 자료구조로 두 동작을 모두 표현할 수 있지만, 실제 코드에서는 목적에 맞는 연산을 일관되게 사용해야 흐름을 이해하기 쉽다.

### 너비 우선 탐색(BFS)

BFS는 먼저 발견한 정점을 먼저 처리해야 하므로 FIFO 큐를 사용한다.

덱에서는 뒤쪽에 다음 탐색 대상을 추가하고, 앞쪽에서 처리할 대상을 꺼내는 방식으로 구현한다.

```
1. 시작 정점을 뒤쪽에 넣는다.
2. 앞쪽 정점을 꺼내 처리한다.
3. 아직 방문하지 않은 인접 정점을 뒤쪽에 넣는다.
4. 덱이 빌 때까지 반복한다.
```

원형 배열이나 연결 리스트로 구현한 덱은 앞쪽 삭제 때 나머지 원소 전체를 이동할 필요가 없어 이 작업에 적합하다.

### 슬라이딩 윈도 최댓값·최솟값

슬라이딩 윈도는 일정 길이의 구간을 한 칸씩 이동시키며 계산하는 방식이다.

다음 배열에서 길이가 3인 각 구간의 최댓값을 구한다고 가정한다.

```
배열: [1, 3, -1, -3, 5, 3, 6, 7]

[ 1,  3, -1] → 3
[ 3, -1, -3] → 3
[-1, -3,  5] → 5
[-3,  5,  3] → 5
[ 5,  3,  6] → 6
[ 3,  6,  7] → 7
```

매 구간을 처음부터 확인하면 배열 길이가 n이고 구간 길이가 k일 때 O(nk) 시간이 걸린다.

덱에 **최댓값이 될 가능성이 있는 원소의 인덱스만 유지**하면 전체를 O(n)에 처리할 수 있다. 이때 덱 내부의 값이 일정한 순서를 유지하도록 관리하는 방식을 **단조 덱(Monotonic Deque)**이라고 한다.

최댓값을 구하는 단조 덱은 다음처럼 동작한다.

1. 현재 구간을 벗어난 인덱스를 앞쪽에서 제거한다.
2. 새 값보다 작거나 같은 값을 가리키는 인덱스를 뒤쪽에서 제거한다.
3. 새 값의 인덱스를 뒤쪽에 추가한다.
4. 덱의 맨 앞 인덱스가 가리키는 값을 현재 구간의 최댓값으로 사용한다.

새 값보다 작고 더 일찍 들어온 원소는 이후 구간에서도 새 값보다 먼저 구간을 벗어나므로 최댓값 후보로 남길 필요가 없다.

각 인덱스는 한 번 들어가고 최대 한 번 제거되므로, 반복문 안에서 여러 원소를 제거하더라도 전체 시간 복잡도는 O(n)이다.

### 양 끝 비교

문자열의 앞뒤 문자가 같은지 반복해서 확인하는 회문 검사에도 덱을 사용할 수 있다.

```
r a c e c a r
↑           ↑
앞과 뒤를 꺼내 비교한다.
```

양 끝의 문자가 같으면 다음 쌍을 비교하고, 다르면 회문이 아니라고 판단한다.

다만 문자열을 인덱스로 직접 접근할 수 있다면 두 개의 인덱스를 사용하는 방식도 가능하다. 덱은 양 끝에서 꺼내는 동작을 자료구조로 표현하는 선택지이다.

## 덱의 변형

덱의 삽입 또는 삭제 위치를 제한한 형태도 있다.

| 종류                               | 허용되는 동작                            |
| -------------------------------- | ---------------------------------- |
| 입력 제한 덱(Input-Restricted Deque)  | 삽입은 한쪽 끝에서만 가능하고, 삭제는 양쪽 끝에서 가능하다. |
| 출력 제한 덱(Output-Restricted Deque) | 삽입은 양쪽 끝에서 가능하고, 삭제는 한쪽 끝에서만 가능하다. |

이러한 변형은 덱의 유연성을 일부 제한하여 특정 처리 규칙을 표현한 것이다.

## 구현과 사용 시 주의할 점

### 빈 덱에서의 삭제와 조회

원소가 없는 상태에서 데이터를 꺼내려고 하면 언더플로가 발생한다.

구현에 따라 예외를 발생시키거나, 실패 여부 또는 특별한 값을 반환한다. 따라서 빈 덱에서의 동작을 확인하고 처리해야 한다.

### 용량 제한과 데이터 유실 정책

용량이 제한된 덱이 가득 찼을 때의 동작은 구현마다 다르다.

추가 삽입을 거부할 수도 있고, 반대쪽의 오래된 원소를 자동으로 버릴 수도 있다. 최근 기록처럼 일부 데이터만 유지하는 용도에서는 자동 제거가 유용하지만, 모든 데이터를 보존해야 하는 용도에서는 적합하지 않을 수 있다.

### 원형 배열의 빈 상태와 가득 찬 상태 구분

원형 배열에서 앞뒤 인덱스만 사용하면, 두 인덱스가 같은 상황이 빈 상태인지 가득 찬 상태인지 모호해질 수 있다.

이를 해결하는 대표적인 방법은 원소 수를 별도로 저장하거나, 배열의 한 칸을 항상 비워 두는 것이다. 두 방법은 사용할 수 있는 용량과 상태 판정 방식이 다르므로 구현 규칙을 일관되게 유지해야 한다.

### 중간 접근과 검색 성능

**덱의 핵심 장점은 양쪽 끝에서의 삽입과 삭제이다.**

중간 원소를 자주 삽입하거나 특정 값을 반복해서 검색하는 작업까지 자동으로 빨라지는 것은 아니다. 중간 접근이 많다면 배열 계열 자료구조를, 값 검색이 중심이라면 해시 테이블이나 검색 트리 등을 검토해야 한다.

## 덱이 적합한 상황

덱을 선택할 때는 **양쪽 끝에서 데이터를 넣거나 꺼낼 필요가 있는지**를 먼저 살펴보면 된다.

- 앞쪽과 뒤쪽에서 모두 삽입·삭제해야 한다면 덱이 적합하다.
- FIFO 처리가 필요하고 앞쪽 삭제를 효율적으로 수행해야 한다면 덱을 큐로 활용할 수 있다.
- 슬라이딩 윈도에서 불필요한 후보를 양쪽 끝에서 제거해야 한다면 단조 덱이 유용하다.
- 인덱스를 통한 임의 접근이 많다면 해당 덱의 내부 구현과 접근 복잡도를 확인해야 한다.
- 모든 개별 연산의 지연 시간을 제한해야 한다면 배열 확장이나 메모리 할당 비용까지 고려해야 한다.
