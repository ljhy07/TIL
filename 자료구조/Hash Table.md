# 해시 테이블이란 무엇인가

**해시 테이블(Hash Table)은 키를 이용해 값을 빠르게 저장하고 조회하는 자료구조이다.** 키를 해시 함수로 변환해 데이터가 저장될 위치를 결정하는 것이 핵심 원리이다.

예를 들어 학생의 학번으로 이름을 조회하는 상황을 생각할 수 있다.

|키(Key)|값(Value)|
|---|---|
|`20260001`|김민수|
|`20260002`|이서연|
|`20260003`|박지훈|

여기서 학번은 데이터를 구분하는 **키**이고, 학생 이름은 키에 연결된 **값**이다.

배열이나 연결 리스트에서 학번을 하나씩 비교하면 조회에 최대 O(n)의 시간이 필요하다. 해시 테이블은 키로 저장 위치를 계산하므로, 적절한 조건에서 **조회·삽입·삭제를 평균 O(1)에 수행한다.**

---

## 해시 테이블의 기본 구조

해시 테이블을 이해하려면 키, 해시 함수, 버킷이라는 세 가지 요소를 알아야 한다.

### 키와 값

키는 데이터를 찾는 기준이고, 값은 실제로 저장하려는 데이터이다.

```
키: "apple"
값: 1500
```

이 데이터는 `"apple"`이라는 키에 `1500`이라는 값이 연결되어 있다는 의미이다.

일반적인 맵 형태의 해시 테이블에서는 같은 키를 여러 개의 독립적인 항목으로 저장하지 않는다. 이미 존재하는 키에 새 값을 넣으면 기존 값을 갱신하는 방식으로 동작한다.

```
저장: "apple" → 1500
갱신: "apple" → 1800

최종 상태: "apple" → 1800
```

반면 서로 다른 키가 같은 값을 가지는 것은 가능하다.

```
"apple"  → 1500
"banana" → 1500
```

### 해시 함수

**해시 함수(Hash Function)는 키를 정수 형태의 해시값으로 변환하는 함수이다.**

```
키 → 해시 함수 → 해시값
```

실제 저장 위치를 구하려면 해시값을 내부 배열의 범위에 맞게 변환해야 한다.

```
키 → 해시값 → 배열 인덱스
```

이를 개념적으로 표현하면 다음과 같다.

```
hash_value = hash(key)
index = hash_value % capacity
```

`capacity`는 내부 배열의 크기이고, `%`는 나머지 연산이다. 실제 구현에서는 나머지 연산 대신 비트 연산 등을 사용하기도 한다.

예를 들어 배열의 크기가 10이고 해시값이 42라면 저장 위치는 다음과 같다.

```
42 % 10 = 2
```

따라서 인덱스 2를 기준으로 데이터를 저장하거나 찾는다.

### 버킷과 슬롯

**버킷(Bucket)은 데이터가 배치되는 저장 구역이다.** 슬롯(Slot)은 내부 배열의 한 칸을 가리킬 때 자주 사용하는 용어이다.

구현 방식에 따라 한 버킷에 여러 항목을 연결하기도 하고, 한 슬롯에 한 항목을 저장한 뒤 충돌이 발생하면 다른 슬롯을 탐색하기도 한다.

따라서 해시 테이블을 단순히 “배열의 한 칸에 데이터 하나를 저장하는 구조”로만 이해하면 충돌 처리 과정을 놓치게 된다.

---

## 데이터를 저장하고 찾는 과정

내부 배열의 크기가 8이고, 설명을 위해 정수 키의 저장 위치를 다음과 같이 계산한다고 가정한다.

```
index = key % 8
```

실제 해시 테이블에서는 더 복잡한 해시 함수를 사용하지만, 이 예시는 기본 동작을 이해하기 위한 것이다.

### 삽입 과정

키 `10`, 값 `"사과"`를 저장하면 다음과 같이 동작한다.

1. 키 `10`의 저장 위치를 계산한다.
2. `10 % 8 = 2`이므로 인덱스 2를 확인한다.
3. 해당 위치가 비어 있으면 키와 값을 저장한다.

```
인덱스    저장된 데이터
0         비어 있음
1         비어 있음
2         (10, "사과")
3         비어 있음
4         비어 있음
5         비어 있음
6         비어 있음
7         비어 있음
```

일반적으로 값뿐 아니라 키도 함께 저장한다. 같은 위치로 계산되는 서로 다른 키를 구분해야 하기 때문이다.

### 조회 과정

키 `10`으로 값을 조회하면 다음과 같이 동작한다.

1. 삽입할 때와 같은 방식으로 저장 위치를 계산한다.
2. 인덱스 2에 저장된 항목을 확인한다.
3. 저장된 키가 `10`과 같은지 비교한다.
4. 키가 일치하면 값 `"사과"`를 반환한다.

핵심은 **앞에서부터 전체 데이터를 훑는 대신, 키로 계산한 위치에서 탐색을 시작한다는 점**이다.

---

## 충돌이 발생하는 이유

**충돌(Collision)은 서로 다른 키가 같은 저장 위치에 대응하는 현상이다.**

앞의 예시에서 키 `10`과 키 `18`은 같은 인덱스로 계산된다.

```
10 % 8 = 2
18 % 8 = 2
```

두 키가 다르더라도 같은 위치를 사용하려 하므로 충돌이 발생한다.

해시값 자체가 같은 경우에도 충돌이 발생할 수 있고, 해시값은 다르지만 배열 인덱스로 변환하는 과정에서 같은 위치가 될 수도 있다.

해시 테이블의 저장 공간은 제한되어 있고 가능한 키의 종류는 매우 많으므로, 일반적으로 충돌 가능성을 완전히 제거할 수는 없다.

따라서 좋은 해시 테이블은 다음 두 가지를 함께 고려한다.

- 해시 함수를 통해 데이터가 여러 위치에 고르게 분산되도록 한다.
- 충돌이 발생해도 데이터를 올바르고 효율적으로 처리하도록 한다.

대표적인 충돌 처리 방식은 **체이닝**과 **개방 주소법**이다.

---

## 충돌 처리 방식 ① 체이닝

**체이닝(Separate Chaining)은 같은 버킷에 대응하는 항목들을 별도의 자료구조로 연결하는 방식이다.**

연결 리스트를 사용하는 경우를 예로 들면 다음과 같다.

```
인덱스    버킷
0         비어 있음
1         비어 있음
2         (10, "사과") → (18, "바나나") → (26, "포도")
3         비어 있음
...
```

키 `10`, `18`, `26`이 모두 인덱스 2로 계산되므로 같은 버킷 안에 연결한다.

### 조회 방식

키 `18`을 조회할 때는 다음과 같이 동작한다.

1. 해시 계산으로 인덱스 2를 찾는다.
2. 해당 버킷의 항목들을 차례로 확인한다.
3. 키 `10`은 일치하지 않으므로 다음 항목으로 이동한다.
4. 키 `18`을 찾으면 값 `"바나나"`를 반환한다.

즉, **버킷을 찾는 과정은 빠르지만, 버킷 내부에서는 추가 탐색이 필요하다.**

### 장점과 단점

- 충돌한 항목을 버킷 내부에 추가하면 되므로 구조를 이해하고 구현하기 비교적 쉽다.
- 연결 리스트 방식에서는 삭제할 항목을 찾은 뒤 연결을 수정해 제거할 수 있다.
- 연결 노드와 포인터 등을 저장하기 위한 추가 메모리가 필요하다.
- 특정 버킷에 데이터가 몰리면 버킷 내부 탐색 시간이 길어진다.
- 연결 리스트의 노드가 메모리 곳곳에 흩어지면 캐시 효율이 떨어질 수 있다.

모든 데이터가 하나의 연결 리스트에 몰리면 조회 시간이 O(n)까지 증가한다. 일부 구현은 충돌이 많은 버킷을 균형 트리로 바꾸어 이 문제를 완화한다.

---

## 충돌 처리 방식 ② 개방 주소법

**개방 주소법(Open Addressing)은 충돌이 발생하면 정해진 규칙에 따라 다른 슬롯을 탐색하여 저장하는 방식이다.**

체이닝처럼 외부 연결 구조를 두는 대신, 항목들을 내부 배열의 슬롯에 배치한다.

### 선형 탐사

**선형 탐사(Linear Probing)는 충돌 위치에서 일정한 간격으로 다음 슬롯을 확인하는 방식이다.**

간격이 1인 경우의 탐색 순서는 다음과 같다.

```
원래 위치 → 다음 위치 → 그다음 위치 → ...
```

키 `10`, `18`, `26`의 최초 위치가 모두 인덱스 2라면 다음과 같이 저장할 수 있다.

```
인덱스    저장된 데이터
0         비어 있음
1         비어 있음
2         (10, "사과")
3         (18, "바나나")
4         (26, "포도")
5         비어 있음
6         비어 있음
7         비어 있음
```

배열의 끝에 도달하면 처음으로 돌아가 탐색한다.

조회할 때도 삽입할 때와 같은 순서를 따라간다. 키 `26`을 찾는다면 인덱스 2, 3, 4를 순서대로 확인한다.

선형 탐사는 인접한 메모리에 접근하므로 캐시 효율이 좋을 수 있다. 다만 데이터가 연속으로 뭉치는 **군집화(Clustering)**가 발생하면 탐색 길이가 늘어난다.

### 제곱 탐사

**제곱 탐사(Quadratic Probing)는 탐사 횟수의 제곱 등을 이용해 이동 위치를 정하는 방식이다.**

대표적인 형태는 다음과 같다.

```
h, h + 1², h + 2², h + 3², ...
```

각 위치는 배열 크기에 맞게 변환한다.

선형 탐사의 연속적인 군집화를 줄일 수 있지만, 배열 크기와 탐사 규칙을 적절하게 선택해야 한다. 설계에 따라 빈 슬롯이 있어도 탐색이 그 위치에 도달하지 못할 수 있기 때문이다.

### 이중 해싱

**이중 해싱(Double Hashing)은 두 번째 해시 함수로 탐사 간격을 결정하는 방식이다.**

```
index(i) = (h1(key) + i × h2(key)) % capacity
```

첫 번째 함수는 시작 위치를 정하고, 두 번째 함수는 이동 간격을 정한다.

키마다 탐사 간격을 다르게 만들 수 있지만, 간격이 0이 되지 않고 필요한 슬롯들을 탐색할 수 있도록 설계해야 한다.

### 삭제 시 주의점

개방 주소법에서는 삭제한 슬롯을 단순히 “처음부터 비어 있던 슬롯”으로 처리하면 조회가 잘못될 수 있다.

앞의 예시에서 키 `18`을 삭제했다고 가정한다.

```
2: (10, "사과")
3: 비어 있음
4: (26, "포도")
```

키 `26`을 조회할 때 인덱스 3이 비어 있다는 이유로 탐색을 끝내면, 인덱스 4에 있는 데이터를 놓치게 된다.

이를 해결하는 대표적인 방법은 **삭제 표시인 툼스톤(Tombstone)**을 남기는 것이다.

```
2: (10, "사과")
3: 삭제 표시
4: (26, "포도")
```

조회는 삭제 표시를 만나도 계속 진행한다. 삽입 과정에서는 정해진 규칙에 따라 삭제 표시가 있는 슬롯을 재사용할 수 있다.

다른 방식으로는 삭제 후 일부 항목을 재배치하여 탐색 경로를 유지하기도 한다.

## 적재율과 리사이징

### 적재율의 의미

**적재율(Load Factor)은 저장된 항목 수를 내부 배열 크기로 나눈 값이다.**

```
적재율 α = 항목 수 n / 배열 크기 m
```

배열 크기가 10이고 항목이 7개라면 적재율은 0.7이다.

```
α = 7 / 10 = 0.7
```

적재율이 높아지면 일반적으로 충돌이나 추가 탐색이 증가한다.

다만 체이닝과 개방 주소법에서 적재율의 의미에는 차이가 있다.

- 체이닝에서는 한 버킷에 여러 항목을 연결할 수 있으므로 적재율이 1보다 클 수 있다.
- 한 슬롯에 한 항목을 저장하는 일반적인 개방 주소법에서는 항목 수가 슬롯 수를 초과할 수 없으며, 공간이 거의 차면 탐색 성능이 크게 저하된다.

개방 주소법에서는 삭제 표시가 많이 쌓이는 것도 성능에 영향을 준다. 실제 항목 수가 적더라도 탐색 중 지나가야 하는 슬롯이 많아질 수 있기 때문이다.

### 리사이징의 동작

**리사이징(Resizing)은 성능을 유지하기 위해 내부 배열의 크기를 변경하는 작업이다.**

배열을 확장할 때는 일반적으로 다음 과정을 수행한다.

1. 더 큰 배열을 생성한다.
2. 기존 항목의 새 저장 위치를 계산한다.
3. 항목들을 새 배열에 다시 배치한다.
4. 기존 배열을 새 배열로 교체한다.

배열 크기가 달라지면 저장 위치도 달라질 수 있다.

```
배열 크기가 8일 때:  10 % 8  = 2
배열 크기가 16일 때: 10 % 16 = 10
```

따라서 기존 항목을 같은 인덱스에 그대로 복사하는 것만으로는 충분하지 않다.

이처럼 해시 규칙에 맞게 항목을 다시 배치하는 작업을 흔히 **리해싱(Rehashing)**이라고 한다. 구현에 따라 저장해 둔 해시값을 재사용할 수 있으므로, 반드시 모든 키의 해시 함수를 처음부터 다시 실행한다는 뜻은 아니다.

## 시간 복잡도를 정확하게 이해하는 방법

일반적인 해시 테이블의 시간 복잡도는 다음과 같다.

|연산|평균적인 경우|일반적인 최악의 경우|
|---|---|---|
|조회|O(1)|O(n)|
|삽입|O(1)|O(n)|
|삭제|O(1)|O(n)|

이 표를 이해하려면 세 가지 조건을 함께 알아야 한다.

### 평균 O(1)에는 조건이 있다

해시값이 충분히 고르게 분포하고 적재율이 적절하게 유지되어야 한다.

체이닝에서 버킷 내부를 선형 탐색한다면, 일반적인 해시 분포 가정 아래 평균 탐색 비용은 O(1 + α)로 설명할 수 있다. 적재율 α를 일정한 범위로 유지하면 평균 O(1)이 된다.

반대로 많은 키가 같은 위치에 몰리면 조회·삽입·삭제에 O(n)이 필요할 수 있다.

### 리사이징이 발생하는 삽입은 비싸다

리사이징이 발생한 한 번의 삽입은 기존 항목을 옮겨야 하므로 보통 O(n)의 비용이 든다.

다만 배열 크기를 일정한 배수로 늘리는 등 적절한 확장 정책을 사용하면, 여러 번의 삽입에 걸쳐 이 비용을 나누어 볼 수 있다. 이를 **분할 상환 분석(Amortized Analysis)**이라고 한다.

해시 분포도 양호하다는 조건에서 삽입은 **평균적으로 분할 상환 O(1)**이라고 설명한다.

여기서 평균적인 해시 분포와 여러 연산에 걸친 비용 분산은 서로 다른 개념이다.

### 키의 해시 계산 비용도 존재한다

O(1)이라는 설명에서는 보통 해시 계산과 키 비교 비용을 상수로 취급한다.

하지만 길이가 L인 문자열의 해시를 처음 계산하려면 일반적으로 O(L)의 시간이 필요하다. 문자열 비교에도 길이에 따른 비용이 발생할 수 있다.

따라서 **문자열이 아무리 길어져도 전체 조회 비용이 항상 일정하다는 뜻은 아니다.**

## 좋은 해시 함수와 올바른 키의 조건

### 같은 키는 같은 해시값을 가져야 한다

키의 동등성 비교에서 두 키가 같다면, 두 키의 해시값도 같아야 한다.

```
a == b이면 hash(a) == hash(b)이어야 한다.
```

반대 방향은 성립하지 않는다.

```
hash(a) == hash(b)이더라도 a와 b는 다를 수 있다.
```

이 때문에 해시 테이블은 해시값이나 인덱스만 확인하지 않고 **실제 키가 같은지도 비교한다.**

### 해시값이 고르게 분산되어야 한다

특정 위치에 키가 집중되면 충돌이 많아진다. 좋은 해시 함수는 예상되는 키들을 저장 공간 전체에 고르게 분산시키도록 설계한다.

해시 함수 자체의 계산 비용도 지나치게 크지 않아야 한다. 저장 위치를 빨리 찾기 위해 사용하는 함수가 너무 느리면 전체 성능이 나빠지기 때문이다.

### 저장 중에는 키의 기준이 안정적이어야 한다

키를 저장한 뒤 해시 계산이나 동등성 비교에 사용되는 내용을 바꾸면, 데이터가 저장된 위치와 조회 시 계산한 위치가 달라질 수 있다.

예를 들어 객체의 `name`을 기준으로 해시를 계산하는데 저장 후 `name`을 변경하면, 테이블 안에 항목이 있어도 조회에 실패할 수 있다.

따라서 키의 해시와 동등성에 영향을 주는 상태는 테이블에 저장된 동안 유지되어야 한다. 불변 객체가 키로 자주 사용되는 이유이다.

## 해시 테이블을 사용하는 대표적인 상황

### 빈도 계산

단어를 키로, 등장 횟수를 값으로 저장할 수 있다.

```
입력: apple, banana, apple, grape, banana, apple

결과:
apple  → 3
banana → 2
grape  → 1
```

각 단어가 나올 때마다 해당 키의 값을 증가시키는 방식이다.

### 중복 확인

이미 등장한 데이터를 해시 집합에 저장해 중복 여부를 빠르게 확인할 수 있다.

```
입력: 3, 5, 3, 8, 5
서로 다른 원소: 3, 5, 8
```

해시 집합(Hash Set)은 키의 존재 여부를 관리하는 구조이다. 해시 맵(Hash Map)은 키와 값의 연결을 관리하는 구조이다.

### 캐시와 메모이제이션

계산에 사용한 입력을 키로, 계산 결과를 값으로 저장할 수 있다.

```
입력 A → 계산 결과 A
입력 B → 계산 결과 B
```

같은 입력이 다시 들어오면 저장된 결과를 조회하여 계산을 생략한다.

해시 테이블은 빠른 조회를 담당하며, 캐시의 만료나 용량 제한, 삭제 순서 등은 별도의 정책으로 관리한다.

### 객체와 데이터의 식별

사용자 ID로 사용자 정보를 찾거나, 상품 코드로 상품 정보를 찾는 상황에도 활용할 수 있다.

```
사용자 ID → 사용자 정보
상품 코드 → 상품 정보
파일 경로 → 파일 메타데이터
```

공통점은 **명확한 키로 특정 데이터 하나를 빠르게 찾는 작업**이라는 점이다.

## 자주 하는 오해

- **해시 테이블이 항상 O(1)이라는 설명은 부정확하다.** 평균적인 성능이며, 충돌·적재율·리사이징·키 처리 비용의 영향을 받는다.
- **해시값이 같다고 같은 키인 것은 아니다.** 충돌할 수 있으므로 실제 키를 비교해야 한다.
- **충돌이 발생했다고 데이터가 사라지는 것은 아니다.** 정상적인 구현은 충돌 처리 규칙에 따라 여러 항목을 구분한다.
- **해시 테이블은 암호화 기능이 아니다.** 저장 위치를 계산하는 해시와 암호학적 해시는 요구하는 성질과 목적이 다르다.
- **데이터가 적을 때도 언제나 가장 빠른 것은 아니다.** 해시 계산과 메모리 사용 등의 부가 비용 때문에 작은 배열의 단순 탐색이 더 빠를 수도 있다.

해시 테이블의 동작을 연결하면 **키로 위치를 계산하고, 충돌을 해결하며, 적재율을 관리해 빠른 접근을 유지하는 구조**이다. 평균 O(1)이라는 성능은 이 세 가지가 함께 제대로 동작할 때 얻어지는 결과이다.
