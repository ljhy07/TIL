# Java 메모리 구조

Java 메모리 구조를 이해하려면 **메서드 실행에 필요한 데이터, 객체 자체, 클래스 정보가 각각 어디에서 관리되는지**를 구분해야 한다.

아래에서는 JVM 명세의 공통 개념을 먼저 설명하고, 실제 구현은 널리 사용하는 **HotSpot JVM**을 기준으로 설명한다. JVM 명세는 논리적인 영역과 동작을 정의하며, 구체적인 메모리 배치와 최적화 방식은 구현체에 맡긴다. 

## 전체 구조

JVM의 실행 중 메모리 영역은 크게 **스레드마다 사용하는 영역**과 **스레드들이 공유하는 영역**으로 나뉜다.

|구분|영역|역할|
|---|---|---|
|스레드별 영역|JVM 스택|메서드 호출에 필요한 프레임을 관리한다.|
|스레드별 영역|PC 레지스터|현재 실행 중인 JVM 명령어의 위치를 나타낸다.|
|스레드별 영역|네이티브 메서드 스택|네이티브 코드 실행을 지원한다.|
|공유 영역|힙|객체와 배열을 관리한다.|
|공유 영역|메서드 영역|클래스 구조, 메서드 코드, 런타임 상수 풀 등을 관리한다.|

런타임 상수 풀은 별도의 독립된 최상위 영역이라기보다 **메서드 영역에 속하는 클래스별 자료 구조**다.

HotSpot 프로세스의 실제 메모리 사용량에는 이 밖에도 다음 영역이 포함된다.

```
Java 프로세스
├─ Java 힙
│  └─ 객체, 배열
├─ 클래스 메타데이터
│  └─ Metaspace, Compressed Class Space
├─ 스레드 실행용 메모리
│  └─ 플랫폼 스레드의 스택 등
├─ Code Cache
│  └─ JIT가 생성한 기계어 코드 등
└─ 기타 네이티브 메모리
   └─ Direct Buffer, GC 자료 구조, 네이티브 라이브러리 등
```

따라서 **Java 프로세스가 사용하는 전체 메모리와 Java 힙의 크기는 서로 다르다**. HotSpot은 이러한 내부 메모리 사용을 Native Memory Tracking으로 구분해 제공한다.

## JVM 스택과 메서드 호출

### 스택에는 메서드별 실행 상태가 쌓인다

메서드가 호출되면 해당 호출을 위한 **스택 프레임**이 만들어진다. 프레임에는 매개변수, 지역 변수, 계산에 필요한 공간, 호출 복귀를 위한 정보 등이 들어간다.

다음 호출 관계를 예로 든다.

```
public static void main(String[] args) {
    first();
}

static void first() {
    second();
}

static void second() {
    int value = 10;
}
```

`second()`를 실행하는 동안의 논리적인 호출 스택은 다음과 같다.

```
스택의 위쪽
┌──────────────────┐
│ second() 프레임  │ ← 현재 실행 중이다.
├──────────────────┤
│ first() 프레임   │
├──────────────────┤
│ main() 프레임    │
└──────────────────┘
스택의 아래쪽
```

`second()`가 끝나면 해당 프레임이 제거되고 `first()`의 실행이 이어진다. 메서드 호출은 이처럼 **나중에 들어간 호출이 먼저 끝나는 LIFO 방식**으로 처리된다.

### 프레임 내부에는 지역 변수와 피연산자 스택이 있다

지역 변수 배열에는 매개변수와 지역 변수의 값이 들어간다. 인스턴스 메서드에서는 `this` 참조도 포함된다.

피연산자 스택은 계산 중인 값을 임시로 다룬다. 다음 코드는 개념적으로 `a`와 `b`를 피연산자 스택에 올리고, 더한 결과를 `result`에 저장하는 방식으로 처리된다.

```
int result = a + b;
```

**메서드 호출들을 관리하는 JVM 스택과 프레임 안에서 계산하는 피연산자 스택은 서로 다른 개념이다**. JIT로 최적화된 실제 실행에서는 이 계산이 CPU 레지스터 등을 사용하도록 바뀔 수 있다.

## 힙과 객체 참조

### 객체와 객체를 가리키는 변수는 구분해야 한다

다음 코드를 예로 든다.

```
class User {
    int age;
}

static void example() {
    int count = 3;

    User user = new User();
    user.age = 20;
}
```

일반적인 실행 모델에서는 다음처럼 이해한다.

```
example()의 프레임              힙
┌──────────────────┐           ┌──────────────────┐
│ count = 3        │           │ User 객체        │
│ user = 참조값 ───┼──────────→│ age = 20         │
└──────────────────┘           └──────────────────┘
```

`user` 변수에 들어가는 값은 객체 자체가 아니라 **객체를 가리키는 참조값**이다.

반면 `age`는 `User` 객체의 인스턴스 필드이므로 객체의 일부로 관리된다. 따라서 기본형인 `int`라고 해서 항상 스택에 저장되는 것은 아니다.

### 변수의 저장 위치는 선언된 위치에 따라 달라진다

|코드 형태|일반적인 저장 관계|
|---|---|
|메서드 내부의 `int count`|지역 변수로서 해당 호출의 프레임에서 관리된다.|
|메서드 내부의 `User user`|참조값이 해당 호출의 프레임에서 관리된다.|
|객체의 `int age`|기본형 값이 힙 객체의 일부로 관리된다.|
|객체의 `User friend`|참조값이 힙 객체의 필드로 관리된다.|
|`new int[100]`|배열 자체와 기본형 원소들이 힙에서 관리된다.|

핵심은 **기본형과 참조형이라는 구분은 저장하는 값의 종류를 결정하고, 지역 변수와 필드라는 구분은 그 값이 소속되는 위치를 결정한다**는 점이다.

참조형 배열의 원소에는 객체 자체가 아닌 참조값이 들어간다. 예를 들어 `new User[100]`은 참조를 담을 배열 하나를 만들며, `User` 객체 100개를 자동으로 만들지는 않는다.

### 객체를 복사하지 않고 참조를 복사할 수 있다

```
User a = new User();
User b = a;

b.age = 30;

System.out.println(a.age); // 30
```

`b = a`는 객체 복사가 아니라 참조값 복사다. 따라서 `a`와 `b`는 동일한 객체를 가리킨다.

이 관계는 다음처럼 표현한다.

```
a ──┐
    ├──→ User 객체 { age = 30 }
b ──┘
```

## 메서드 영역과 Metaspace

### 메서드 영역은 JVM 명세의 논리적 개념이다

메서드 영역은 클래스별 구조와 메서드 코드 등을 관리하는 공유 영역이다. 이름에 메서드가 들어가지만 클래스 정보 전반을 포함한다.

### Metaspace는 HotSpot의 클래스 메타데이터 저장 방식이다

HotSpot은 JDK 8부터 과거의 **PermGen**을 제거하고, 클래스 메타데이터를 **Metaspace라는 네이티브 메모리 영역**에 저장한다.

여기에는 클래스의 필드와 메서드에 대한 구조 정보 등이 포함된다. 클래스가 언로드되면 관련 메타데이터도 회수될 수 있다.

|용어|의미|
|---|---|
|메서드 영역|JVM 명세가 정의한 논리적 영역이다.|
|Metaspace|HotSpot이 클래스 메타데이터를 관리하는 구현상의 영역이다.|
|PermGen|과거 HotSpot이 사용하던 영역이며 JDK 8부터 제거됐다.|

따라서 “메서드 영역이 곧 Metaspace다”라는 표현은 입문용으로는 편리하지만, 명세와 구현의 차이를 정확히 드러내지는 못한다.

Metaspace는 `-Xmx`로 제한하는 Java 힙에 포함되지 않는다. 별도로 상한을 설정하려면 `-XX:MaxMetaspaceSize`를 사용한다.

### `static` 필드의 값과 클래스 메타데이터도 구분해야 한다

```
class Cache {
    static int count = 10;
    static User current = new User();
}
```

HotSpot에서는 정적 필드의 실제 저장 공간이 **힙에 있는 해당 클래스의 `java.lang.Class` 객체에 포함된다**.

위 코드의 `count` 값과 `current` 참조값은 그 공간에서 관리되며, `current`가 가리키는 `User` 객체도 힙에 존재한다. 클래스 구조를 설명하는 메타데이터는 Metaspace에서 관리된다.

즉, **`static`이라는 이유로 필드 값이나 참조 대상 객체가 모두 Metaspace에 저장되는 것은 아니다**. 

## 런타임 상수 풀과 문자열 풀

### 런타임 상수 풀은 클래스별 참조 정보를 관리한다

`.class` 파일에는 상수 풀이 있으며, JVM은 이를 바탕으로 클래스별 런타임 상수 풀을 구성한다.

이 풀은 숫자 상수뿐 아니라 클래스, 필드, 메서드에 대한 **심볼 참조**도 다룬다. 심볼 참조는 이름과 타입 정보로 대상을 표현하며, JVM은 이를 해석해 실제 실행에 필요한 대상을 연결한다.

따라서 런타임 상수 풀은 단순한 “상수값 보관함”보다 **클래스의 실행에 필요한 참조 정보표**에 가깝다.

### 문자열 풀은 동일한 문자열을 공유하는 데 사용한다

```
String a = "java";
String b = "java";
String c = new String("java");

System.out.println(a == b);      // true
System.out.println(a == c);      // false
System.out.println(a.equals(c)); // true
```

문자열 리터럴인 `a`와 `b`는 동일한 intern된 `String` 객체를 참조한다. `c`는 별도로 생성한 `String` 객체를 참조한다.

- `==`는 두 참조가 동일한 객체를 가리키는지 비교한다.
- `equals()`는 문자열 내용을 비교한다.
- `intern()`은 같은 내용을 대표하는 풀의 문자열 참조를 반환한다.

```
String d = c.intern();

System.out.println(a == d); // true
```

**문자열 풀과 클래스별 런타임 상수 풀은 서로 다른 개념이다**. 런타임 상수 풀의 문자열 상수는 intern된 `String` 객체를 참조할 수 있으며, 그 `String` 객체 자체는 힙 객체다.

## PC 레지스터와 네이티브 메서드 스택

**PC 레지스터**는 스레드별로 현재 실행 중인 JVM 명령어의 위치를 나타낸다. 네이티브 메서드를 실행하는 동안에는 JVM 명세상 그 값이 정의되지 않는다.

**네이티브 메서드 스택**은 C·C++ 등으로 작성된 네이티브 코드의 실행을 지원한다. 물리적으로 Java 호출용 스택과 네이티브 호출용 스택을 어떻게 배치하는지는 JVM 구현에 따라 달라진다.

## GC와 객체의 생명주기

### 메서드가 끝나는 시점과 객체가 사라지는 시점은 다르다

```
static User createUser() {
    User user = new User();
    return user;
}

static void example() {
    User saved = createUser();
    System.out.println(saved.age);
}
```

`createUser()`가 반환하면 해당 호출의 프레임은 제거된다. 하지만 반환된 객체는 `saved`를 통해 계속 사용하므로 살아 있다.

**지역 변수의 수명과 그 변수가 참조한 객체의 수명은 일치하지 않는다**.

### GC는 도달 가능성을 기준으로 회수 대상을 찾는다

GC의 핵심 기준은 **실행 중인 프로그램이 앞으로 해당 객체에 접근할 수 있는지**다.

이를 분석할 때 출발점이 되는 참조들을 보통 **GC Roots**라고 부른다. 실행 중인 스레드의 참조, 살아 있는 클래스의 정적 필드를 통한 참조, JNI 참조 등이 관련된다.

```
살아 있는 참조 → A → B → C
```

이 경우 `A`뿐 아니라 연결된 `B`, `C`도 도달 가능하다.

```
User a = new User();
User b = a;

a = null;
```

위 코드에서는 `b`가 여전히 객체를 가리킨다. 따라서 `a = null`만으로 객체가 회수되지는 않는다.

또한 어떤 객체가 회수 대상이 되더라도 **실제로 언제 회수될지는 보장되지 않는다**.

### GC가 있어도 메모리 누수가 발생한다

프로그램이 더 이상 필요로 하지 않는 객체를 계속 참조하면 GC는 그 객체를 회수할 수 없다.

대표적인 사례는 다음과 같다.

- 크기 제한 없이 커지는 캐시가 객체를 계속 보관한다.
- 정적 컬렉션에서 사용이 끝난 데이터를 제거하지 않는다.
- 장시간 살아 있는 스레드의 `ThreadLocal`에 불필요한 값을 남긴다.
- 리스너나 콜백 등록을 해제하지 않아 객체가 유지된다.

Java의 메모리 누수는 흔히 **불필요한 객체가 도달 가능한 상태로 남는 문제**다.

## 힙의 세대 구조와 GC 방식

### Young와 Old는 객체의 생존 특성을 활용한다

많은 GC는 대부분의 객체가 짧게 살아 있다는 특성을 활용해 힙을 세대로 관리한다.

|구분|역할|
|---|---|
|Young Generation|새로 생성된 객체와 비교적 짧게 살아 있는 객체를 관리한다.|
|Old Generation|여러 번의 수집을 거치며 오래 살아남은 객체를 관리한다.|

대표적인 흐름은 다음과 같다.

```
객체 생성 → Eden
             ↓ 수집 후 생존
          Survivor
             ↓ 생존 기간과 수집 정책
          Old Generation
```

다만 모든 객체가 이 경로를 반드시 거치는 것은 아니다. 큰 객체나 수집기의 정책에 따라 다른 경로를 사용할 수 있다.

### G1은 힙을 Region으로 나눈다

G1은 힙을 여러 **Region**으로 나누고, 각 Region을 Eden, Survivor, Old 등의 역할로 사용한다.

따라서 Young와 Old가 반드시 하나씩의 연속된 메모리 구간으로 존재하는 것은 아니다. G1의 매우 큰 객체는 **Humongous 객체**로 취급하며 Old에 직접 할당할 수 있다.

G1의 Mixed GC는 Young 영역과 선택된 Old Region을 함께 수집한다. 이를 Full GC와 같은 의미로 이해해서는 안 된다.

## JIT, Code Cache와 할당 최적화

### 자주 실행하는 코드는 기계어로 컴파일한다

HotSpot의 JIT 컴파일러는 자주 실행되는 코드를 기계어로 컴파일해 실행 성능을 높인다. 이 기계어 코드는 **Code Cache**에서 관리한다.

따라서 다음을 구분해야 한다.

- 클래스의 바이트코드와 메서드 정보는 클래스 관련 자료 구조에서 관리한다.
- JIT가 생성한 기계어 코드는 Code Cache에서 관리한다.

### 소스 코드의 `new`가 항상 실제 객체 할당으로 이어지지는 않는다

```
static int calculate() {
    User user = new User();
    user.age = 10;
    return user.age + 1;
}
```

JIT는 객체가 외부로 전달되지 않는지 등을 **Escape Analysis**로 분석한다. 조건이 맞으면 객체를 실제로 만들지 않고 필요한 필드 값만 계산하는 **Scalar Replacement**를 적용할 수 있다.

그러므로 소스 코드에 `new`가 있다고 해서 실행 중 항상 별도의 힙 객체가 생성된다고 단정할 수는 없다. 이러한 최적화는 코드와 실행 상황에 따라 달라진다.

참조값의 크기도 고정된 원시 주소 크기와 항상 같지는 않다. HotSpot은 설정에 따라 **Compressed Oops**를 사용해 객체 참조를 압축할 수 있다.

## 네이티브 메모리와 Direct Buffer

다음 코드는 직접 버퍼를 생성한다.

```
ByteBuffer buffer =
    ByteBuffer.allocateDirect(1024 * 1024);
```

직접 버퍼는 네이티브 I/O가 버퍼의 내용을 직접 다루도록 설계된다. HotSpot에서 그 데이터 저장 공간은 일반 Java 힙 밖의 네이티브 메모리를 사용하며, 버퍼를 표현하는 Java 객체는 힙에 존재한다.

따라서 객체 수가 적어 보여도 직접 버퍼의 데이터가 크면 프로세스 메모리 사용량이 커질 수 있다.

Java 프로세스의 메모리를 계획할 때는 다음 관계를 고려해야 한다.

```
프로세스 메모리 사용량
≈ Java 힙
+ 클래스 메타데이터
+ 플랫폼 스레드 스택
+ Code Cache
+ 직접 버퍼
+ JVM 및 네이티브 라이브러리의 기타 메모리
```

이 식은 용량 계획을 위한 개념적인 합산이다. 운영체제가 표시하는 RSS, 예약된 가상 주소 공간, JVM이 실제 사용하는 메모리는 측정 기준이 서로 다르다.

특히 **`-Xmx`는 Java 힙의 최대 크기이며 프로세스 전체 메모리 상한이 아니다**.

## 가상 스레드에서 달라지는 스택 저장 방식

플랫폼 스레드는 일반적으로 운영체제 스레드와 연결되며 네이티브 스택 메모리를 사용한다.

반면 HotSpot의 가상 스레드는 스택을 **Java 힙의 Stack Chunk 객체**로 저장한다. 이 스택은 필요에 따라 확장되고, GC의 관리 대상이 된다.

따라서 다음 두 설명은 구분해야 한다.

- 각 스레드는 논리적으로 자신만의 호출 스택을 가진다.
- 그 호출 스택이 물리적으로 어디에 저장되는지는 구현과 스레드 종류에 따라 달라진다.

가상 스레드도 메모리를 사용하므로, 대량으로 생성한 가상 스레드의 실행 상태와 `ThreadLocal` 데이터는 힙 사용량에 영향을 준다.

## 메모리 오류와 설정 옵션

### 오류 메시지로 문제가 발생한 영역을 구분한다

|오류|주요 의미|
|---|---|
|`StackOverflowError`|호출 깊이가 허용된 스택 용량을 초과한다.|
|`OutOfMemoryError: Java heap space`|Java 힙에서 필요한 할당 공간을 확보하지 못한다.|
|`OutOfMemoryError: Metaspace`|클래스 메타데이터 공간을 확보하지 못한다.|
|`OutOfMemoryError: Compressed class space`|압축 클래스 포인터용 클래스 공간이 부족하다.|
|`OutOfMemoryError: Direct buffer memory`|직접 버퍼 할당에 필요한 공간이나 한도를 확보하지 못한다.|
|`OutOfMemoryError: unable to create native thread`|메모리나 운영체제 제한 등으로 네이티브 스레드를 생성하지 못한다.|

`OutOfMemoryError`가 발생했다고 해서 항상 메모리 누수인 것은 아니다. 설정한 한도가 작거나, 동시에 처리하는 작업이 많거나, 필요한 데이터 자체가 클 수도 있다.

### 주요 옵션은 서로 다른 영역을 제어한다

|옵션|의미|
|---|---|
|`-Xms`|Java 힙의 초기·최소 크기를 설정한다.|
|`-Xmx`|Java 힙의 최대 크기를 설정한다.|
|`-Xss`|플랫폼 스레드의 스택 크기를 설정한다.|
|`-XX:MaxMetaspaceSize`|클래스 메타데이터 메모리의 상한을 설정한다.|
|`-XX:ReservedCodeCacheSize`|Code Cache의 최대 크기를 설정한다.|
|`-XX:MaxDirectMemorySize`|NIO 직접 버퍼에 사용할 메모리 한도를 설정한다.|

`-Xss`는 가상 스레드마다 고정된 크기의 네이티브 스택을 예약한다는 의미로 적용되지 않는다. 옵션의 정확한 적용 방식은 사용 중인 JDK와 JVM을 기준으로 확인해야 한다.

### 힙 문제와 네이티브 메모리 문제는 다른 자료로 분석한다

**힙 덤프**는 어떤 객체가 메모리를 차지하고, 어떤 참조 때문에 살아 있는지 분석하는 데 사용한다.

**GC 로그**는 객체 생성량, 수집 빈도, 수집 후 남는 힙 사용량, 정지 시간을 분석하는 데 사용한다.

**Native Memory Tracking**은 HotSpot 내부의 스레드, 클래스, 코드 등 네이티브 메모리 범주를 확인하는 데 사용한다. NMT가 모든 외부 네이티브 라이브러리의 할당을 추적하는 것은 아니므로 운영체제의 메모리 측정과 함께 해석해야 한다.

## 메모리 구조와 Java Memory Model의 차이

힙과 스택은 **데이터를 어디에 저장하고 어떻게 관리하는지**에 관한 개념이다.

반면 **Java Memory Model, JMM**은 여러 스레드 사이에서 읽기와 쓰기가 어떤 순서로 관찰되는지 정의한다. `volatile`, `synchronized`, happens-before 관계 등이 여기에 속한다.

힙을 공유한다는 사실만으로 한 스레드의 변경이 다른 스레드에 올바르게 전달된다고 보장할 수는 없다. 공유 객체를 안전하게 사용하려면 가시성, 실행 순서, 원자성을 함께 고려해야 한다.

또한 JMM의 설명에 등장하는 메인 메모리와 작업 메모리를 각각 힙과 JVM 스택에 그대로 대응시키는 것은 부정확하다. **메모리 저장 구조와 스레드 간 관찰 규칙은 서로 다른 관점이다**.
