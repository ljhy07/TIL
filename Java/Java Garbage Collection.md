# Java Garbage Collection

**Java의 Garbage Collection, 이하 GC는 더 이상 사용할 수 없는 객체가 차지한 메모리를 JVM이 자동으로 회수하는 기능이다.**

GC를 이해하려면 다음 세 가지를 구분해야 한다.

- **회수 대상 판단**은 어떤 객체를 더 이상 사용할 수 없는지 결정하는 과정이다.
- **메모리 회수 방식**은 해당 객체의 공간을 어떻게 다시 사용할 수 있게 만드는지 결정하는 과정이다.
- **GC 수집기**는 이러한 과정을 어떤 알고리즘과 실행 방식으로 구현하는지 결정한다.

이 설명은 주로 OpenJDK와 Oracle JDK에서 사용하는 **HotSpot JVM**을 기준으로 한다. GC의 구체적인 동작과 옵션은 JVM 구현체, JDK 버전, 선택한 수집기에 따라 달라진다.

---

## GC가 필요한 이유

프로그램은 실행하면서 계속 객체를 생성한다.

```
public String createMessage(String name) {
    StringBuilder builder = new StringBuilder();
    builder.append("Hello, ");
    builder.append(name);
    return builder.toString();
}
```

이 코드에서 `builder`가 가리키는 `StringBuilder` 객체는 메시지를 만드는 동안 필요하다. 반환한 문자열과 달리, 이 `StringBuilder` 객체는 메서드 실행 이후 다른 곳에서 참조하지 않으면 더 이상 사용할 필요가 없다.

이러한 객체를 계속 메모리에 남겨 두면 새로운 객체를 생성할 공간이 부족해진다. GC는 회수 가능한 객체의 메모리를 다시 사용할 수 있게 만든다.

Java 개발자는 일반적으로 객체마다 메모리 해제 코드를 작성하지 않는다. 그러나 **GC가 있다는 사실이 메모리 사용량이나 객체의 수명을 신경 쓰지 않아도 된다는 뜻은 아니다.**

GC도 CPU와 메모리를 사용하며, 일부 작업은 애플리케이션 실행을 일시적으로 멈추게 한다.

## GC와 JVM 메모리 구조

### 힙과 스택의 차이

GC를 이해할 때 가장 먼저 구분해야 하는 영역은 **힙과 스택**이다.

|영역|주요 내용|GC와의 관계|
|---|---|---|
|힙, Heap|객체와 배열을 저장하는 영역이다.|객체 메모리 회수의 중심 대상이다.|
|JVM 스택, JVM Stack|스레드마다 메서드 호출에 필요한 프레임을 관리한다.|메서드 반환에 따른 프레임 제거는 일반적인 힙 GC와 별개이다.|
|메타스페이스, Metaspace|HotSpot에서 클래스 메타데이터를 저장하는 네이티브 메모리 영역이다.|클래스 언로딩과 관련하여 메모리를 회수할 수 있다.|
|코드 캐시, Code Cache|JIT 컴파일한 기계어 코드 등을 저장한다.|일반 객체를 수집하는 힙 GC와 관리 방식이 다르다.|
|기타 네이티브 메모리|스레드 스택, 직접 버퍼의 데이터, JVM 내부 구조 등에 사용한다.|힙 GC만으로 전체 사용량을 설명할 수 없다.|

예를 들어 다음 코드에서 `user`는 객체를 가리키는 참조 변수이며, `new User()`로 생성한 객체 자체와 구분된다.

```
User user = new User();
```

개념적으로 메서드의 지역 참조는 스택 프레임에서 관리하고, 객체는 힙에서 관리한다고 이해할 수 있다. 다만 실제 실행에서는 JIT 최적화에 의해 값이 레지스터에 놓이거나 객체 할당 자체가 제거될 수도 있다.

JVM 명세는 객체 저장을 위한 힙과 자동 메모리 관리를 정의하지만, 특정 GC 알고리즘을 의무화하지는 않는다. 

### 힙 크기와 프로세스 메모리의 차이

다음 옵션은 최대 Java 힙 크기를 지정한다.

```
java -Xmx2g -jar app.jar
```

**`-Xmx2g`는 Java 프로세스 전체의 메모리 사용량을 2GB로 제한한다는 뜻이 아니다.**

프로세스는 힙 이외에도 메타스페이스, 스레드 스택, 코드 캐시, 직접 버퍼 등에서 메모리를 사용한다. 따라서 컨테이너 메모리 제한을 설정할 때는 힙 바깥에서 사용하는 메모리도 고려해야 한다.

## GC가 회수할 객체를 판단하는 기준

### 핵심은 도달 가능성이다

Java GC의 핵심 기준은 **도달 가능성, Reachability**이다.

어떤 객체가 아직 사용할 수 있는 객체나 실행 상태에서 참조 경로를 따라 도달 가능한 상태라면 살아 있는 객체로 취급한다. 반대로 이러한 경로가 사라지면 회수 가능한 상태가 된다.

이 탐색의 출발점을 **GC Roots**라고 한다.

대표적인 출발점에는 다음과 같은 참조가 포함된다.

- 실행 중인 스레드의 스택 프레임과 레지스터에서 유지하는 살아 있는 참조가 포함된다.
- 살아 있는 클래스와 클래스 로더를 통해 유지되는 정적 필드의 참조가 포함된다.
- JNI에서 유지하는 전역 참조 등이 포함된다.
- JVM 내부에서 객체를 유지하기 위해 사용하는 참조가 포함된다.

다음 구조에서는 `A`, `B`, `C`가 모두 도달 가능한 상태이다.

```
GC Roots → A → B → C
```

`A`에서 `B`로 향하는 참조가 사라지고 다른 경로도 없다면, `B`와 `C`는 회수 가능한 상태가 된다.

```
GC Roots → A

           B → C
```

**개발자가 업무적으로 더 이상 필요하지 않다고 생각하는 객체라도, 참조 경로가 남아 있으면 GC는 회수하지 못한다.**

### `null`을 대입해도 즉시 회수되지는 않는다

```
User first = new User();
User second = first;

first = null;
```

`first`에 `null`을 대입해도 `second`가 객체를 계속 참조하므로 해당 객체는 회수 대상이 아니다.

```
second = null;
```

다른 참조가 없다는 전제에서, 이제 해당 객체는 회수 가능한 상태가 된다. 그러나 **회수 가능한 시점과 실제로 회수하는 시점은 다르다.**

또한 지역 변수가 소스 코드의 범위 안에 있다는 이유만으로 객체가 반드시 살아 있는 것은 아니다. JVM 최적화는 이후 실행에서 객체를 더 이상 사용하지 않는다는 사실을 이용할 수 있다.

### 순환 참조도 회수할 수 있다

```
class Node {
    Node next;
}

Node a = new Node();
Node b = new Node();

a.next = b;
b.next = a;

a = null;
b = null;
```

두 객체는 서로를 참조하지만, 외부에서 두 객체에 도달할 수 있는 경로는 사라진 상태이다.

```
GC Roots       A ↔ B
```

Java의 일반적인 추적 기반 GC는 GC Roots에서의 도달 가능성을 확인하므로, 이러한 순환 참조도 회수할 수 있다.

**객체끼리 서로 참조한다는 사실만으로 메모리 누수가 발생하지는 않는다.**

## 메모리를 회수하는 기본 알고리즘

실제 GC 수집기는 여러 기법을 조합하지만, 기본적으로 다음 방식을 이해하면 동작을 파악하기 쉽다.

### Mark-Sweep

Mark-Sweep은 살아 있는 객체를 표시한 뒤, 표시하지 않은 객체의 공간을 회수하는 방식이다.

1. GC Roots에서 출발하여 도달 가능한 객체를 표시한다.
2. 표시하지 않은 객체의 공간을 회수한다.

```
회수 전: [살아 있음][쓰레기][살아 있음][쓰레기]
회수 후: [살아 있음][빈 공간][살아 있음][빈 공간]
```

살아 있는 객체를 이동하지 않는 구현에서는 객체 이동 비용을 줄일 수 있다. 그러나 빈 공간이 여러 위치에 흩어지는 **메모리 단편화**가 발생할 수 있다.

전체 빈 공간은 충분하더라도, 큰 객체를 배치할 연속 공간이 부족해질 수 있다.

### Mark-Compact

Mark-Compact는 살아 있는 객체를 표시한 뒤, 객체를 이동하여 빈 공간을 모으는 방식이다.

```
정리 전: [A][빈 공간][B][빈 공간][C]
정리 후: [A][B][C][      빈 공간      ]
```

단편화를 줄일 수 있지만, 객체 이동과 참조 수정에 비용이 발생한다.

### Copying 또는 Evacuation

Copying은 살아 있는 객체를 다른 공간으로 복사한 뒤, 기존 공간을 통째로 재사용하는 방식이다. 수집기 문서에서는 이러한 객체 이동을 **Evacuation**이라고 부르기도 한다.

```
기존 공간: [A][쓰레기][B][쓰레기]
복사 공간: [A][B]
```

살아남는 객체가 적을 때 효율적이며, 복사 결과로 빈 공간도 정리된다. 다만 복사할 목적지 공간이 필요하다.

세대별 GC에서 짧게 살아 있는 객체를 처리할 때 자주 활용하는 방식이다.

## 세대별 GC와 객체의 생애주기

### 대부분의 객체는 짧게 살아남는다

세대별 GC는 다음과 같은 경험적 관찰을 활용한다.

> 대부분의 객체는 생성된 후 짧은 시간 안에 더 이상 필요하지 않게 된다.

요청 처리 중에 생성하는 임시 컬렉션, 문자열 조립 객체, 중간 계산 결과 등이 대표적인 예이다.

이러한 특성을 **약한 세대 가설, Weak Generational Hypothesis**이라고 한다.

매번 전체 힙을 탐색하는 대신, 새 객체가 많은 영역을 자주 수집하면 작업량을 줄일 수 있다.

### Young Generation과 Old Generation

세대별 GC는 객체를 주로 다음과 같이 구분한다.

|세대|역할|
|---|---|
|Young Generation|새로 생성한 객체와 비교적 어린 객체를 관리한다.|
|Old Generation|여러 차례 수집 과정에서 살아남은 객체 등을 관리한다.|

전통적인 Serial·Parallel 계열의 Young 영역은 다음 구조로 설명할 수 있다.

```
Heap
├── Young Generation
│   ├── Eden
│   ├── Survivor 0
│   └── Survivor 1
└── Old Generation
```

일반적인 객체 이동 과정은 다음과 같다.

1. 새 객체 대부분을 Eden에 할당한다.
2. Young GC에서 살아남은 객체를 Survivor 또는 Old로 이동한다.
3. Survivor에 남은 객체는 이후 수집에서 다른 Survivor 공간으로 이동하면서 나이를 증가시킨다.
4. 나이가 충분하거나 공간 조건에 해당하면 Old로 승격한다.

이때 승격을 **Promotion**이라고 한다.

객체의 나이는 보통 생성 후 경과한 초 단위 시간이 아니라 **GC 과정에서 살아남은 횟수**와 관련된 값이다.

다만 모든 수집기가 물리적으로 고정된 Eden·Survivor 두 공간을 사용하는 것은 아니다. G1은 리전으로 이러한 역할을 구현하며, ZGC의 내부 구조도 전통적인 Survivor 모델과 다르다.

### Old 객체가 Young 객체를 참조하는 경우

다음 상황을 생각할 수 있다.

```
Old의 캐시 객체 → Young의 새 데이터 객체
```

Young 영역만 조사하고 Old에서 들어오는 참조를 무시하면, 아직 필요한 데이터 객체를 잘못 회수할 수 있다.

이를 방지하기 위해 세대별 수집기는 **카드 테이블, Card Table**이나 **Remembered Set** 등의 구조로 영역 간 참조 정보를 관리한다.

이 정보를 유지하면 Young GC 때마다 Old 전체를 탐색하는 작업을 줄일 수 있다.

### Minor GC, Major GC, Full GC

이 용어들은 다음과 같이 이해할 수 있다.

- **Minor GC 또는 Young GC**는 일반적으로 Young 세대를 중심으로 수행하는 수집을 의미한다.
- **Major GC**는 Old 세대 수집을 가리키는 경우가 있지만, 자료나 도구마다 의미가 달라질 수 있다.
- **Full GC**는 일반적으로 힙 전체를 대상으로 하는 수집을 의미한다.

**Major GC와 Full GC를 항상 같은 의미로 사용하면 안 된다.**

특히 G1의 **Mixed GC는 Young 리전과 일부 Old 리전을 함께 수집하는 작업이며, Full GC와 다르다.**

## Stop-The-World와 병렬·동시 실행

### Stop-The-World

**Stop-The-World, STW는 GC 등의 JVM 작업을 위해 애플리케이션 스레드의 실행을 일시적으로 멈추는 상태이다.**

GC는 객체의 참조 관계를 정확하게 확인하고, 필요한 경우 객체 이동과 참조 수정을 수행해야 한다. 일부 단계에서는 애플리케이션을 잠시 멈추는 방식으로 일관성을 확보한다.

예를 들어 HTTP 요청을 처리하던 도중 STW가 발생하면 해당 요청의 처리도 지연될 수 있다.

다만 관측한 응답 지연이 모두 GC 때문인 것은 아니다. 스레드 경합, CPU 부족, I/O 지연, 다른 종류의 JVM safepoint도 함께 확인해야 한다.

### Parallel과 Concurrent의 차이

|구분|의미|
|---|---|
|병렬, Parallel|여러 GC 스레드가 GC 작업을 나누어 수행한다.|
|동시, Concurrent|GC 작업과 애플리케이션 실행이 같은 시간대에 진행된다.|

두 개념은 서로 독립적이다.

Parallel GC는 여러 GC 스레드를 사용하지만 주요 수집 작업 중에는 애플리케이션을 멈춘다. G1과 ZGC는 여러 스레드를 활용하면서 일부 또는 대부분의 작업을 애플리케이션과 동시에 수행한다.

**동시 실행 수집기라고 해서 STW가 완전히 사라지는 것은 아니다.** G1은 동시 마킹을 수행하지만 일반적인 객체 대피 작업은 STW에서 수행한다.

### Barrier

애플리케이션이 실행되는 동안 GC도 동작하면, 객체의 참조 관계가 계속 바뀔 수 있다.

JVM은 이를 추적하기 위해 참조 읽기나 쓰기 주변에 **Barrier**라는 추가 처리를 삽입할 수 있다.

- **Write Barrier**는 참조 쓰기와 관련된 정보를 기록하거나 처리한다.
- **Load Barrier**는 참조 읽기 과정에서 필요한 GC 처리를 수행한다.

예를 들어 Old 객체에 Young 객체의 참조를 저장하면, Write Barrier를 통해 변경한 메모리 영역을 기록할 수 있다.

Barrier는 GC의 정확성과 짧은 중단 시간에 도움이 되지만, 애플리케이션 실행에도 일정한 비용을 추가한다. 구체적인 Barrier의 역할과 구현은 수집기마다 다르다.

## 주요 GC 수집기의 특징

### 전체 비교

|수집기|주요 특징|검토할 만한 상황|
|---|---|---|
|Serial GC|하나의 GC 스레드로 수집한다.|작은 힙과 적은 CPU 자원을 사용하는 환경에서 검토한다.|
|Parallel GC|여러 GC 스레드로 처리량을 높이는 데 집중한다.|중단 시간보다 전체 작업량이 중요한 배치 작업 등에서 검토한다.|
|G1 GC|리전 단위 수집으로 처리량과 중단 시간의 균형을 추구한다.|일반적인 서버 애플리케이션의 출발점으로 검토한다.|
|ZGC|비용이 큰 작업 대부분을 동시에 수행하여 짧은 중단 시간을 추구한다.|응답 지연에 민감한 서비스에서 검토한다.|
|Shenandoah GC|객체 이동 등을 동시에 수행하여 짧은 중단 시간을 추구한다.|해당 수집기를 지원하는 JDK 배포판에서 검토한다.|

어떤 수집기가 가장 적합한지는 힙 크기만으로 결정할 수 없다. 살아 있는 데이터의 크기, 객체 생성 속도, CPU 자원, 응답 시간 목표가 함께 영향을 준다.

HotSpot은 대부분의 일반적인 환경에서 G1을 기본 선택하지만, 일부 환경에서는 다른 수집기를 선택할 수 있다. 실제 실행 환경의 설정을 확인해야 한다.

### G1 GC

G1은 힙을 동일한 크기의 **리전, Region**으로 나누어 관리한다.

```
[Eden] [Old ] [Free] [Survivor]
[Old ] [Eden] [Old ] [Free    ]
[Free] [Old ] [Eden] [Old     ]
```

각 리전이 Eden, Survivor, Old 등의 역할을 맡는다.

G1은 살아 있는 객체의 양과 예상 수집 비용 등을 고려하여 회수 효율이 높은 Old 리전을 선택한다. 선택한 리전의 살아 있는 객체를 다른 리전으로 이동시키고 기존 공간을 재사용한다.

대표적인 흐름은 다음과 같다.

1. Young GC를 수행하면서 일부 객체를 Old로 승격한다.
2. 필요 시 동시 마킹을 시작하여 Old 객체의 생존 정보를 구한다.
3. Remark·Cleanup 등의 단계를 거쳐 수집할 Old 리전을 결정한다.
4. Mixed GC에서 Young 리전과 일부 Old 리전을 함께 수집한다.

공간 확보가 따라가지 못하는 등의 상황에서는 Full GC가 발생할 수 있다.

다음 옵션은 G1이 추구할 중단 시간 목표를 지정한다.

```
-XX:MaxGCPauseMillis=200
```

**이 옵션은 모든 GC 중단이 반드시 200ms 이하라는 보장이 아니다.** G1은 실시간 실행을 보장하는 수집기가 아니며, 과거 실행 정보를 활용하여 목표에 맞게 작업량을 조정한다.

### ZGC

ZGC는 **매우 짧은 GC 중단 시간**을 주요 목표로 설계한 수집기이다.

비용이 큰 작업 대부분을 애플리케이션과 동시에 수행하며, 힙 크기가 커져도 중단 시간이 크게 증가하지 않도록 설계한다.

다만 짧은 GC 중단 시간이 모든 요청의 응답 시간을 보장하지는 않는다. 동시 수집에 사용할 CPU와 여유 힙이 부족하면 성능이 떨어지거나 할당 대기가 발생할 수 있다.

ZGC의 세대별 모드는 버전에 따라 다음과 같이 달라졌다.

|JDK 버전|변화|
|---|---|
|JDK 21|Generational ZGC를 선택할 수 있게 되었다.|
|JDK 23|ZGC를 선택하면 세대별 모드가 기본으로 적용되었다.|
|JDK 24 이후|비세대별 ZGC 모드가 제거되었다.|

따라서 JDK 21에서 세대별 ZGC를 선택하는 예시는 다음과 같다.

```
java -XX:+UseZGC -XX:+ZGenerational -jar app.jar
```

JDK 24 이후에는 다음과 같이 ZGC를 선택하면 된다.

```
java -XX:+UseZGC -jar app.jar
```

서로 다른 JDK 버전의 옵션을 그대로 복사해서 사용하면 안 된다.

### Shenandoah GC

Shenandoah도 짧은 중단 시간을 목표로 하며, 객체 이동을 포함한 상당한 작업을 애플리케이션과 동시에 수행한다.

사용 가능 여부는 JDK 배포판과 빌드에 따라 확인해야 한다.

JDK 25에서는 Generational Shenandoah가 실험 기능에서 정식 기능으로 전환되었다. 다만 **정식 기능으로 전환되었다는 사실과 기본 모드로 선택된다는 사실은 다르다.** JDK 25에서 세대별 모드를 선택하려면 해당 모드를 명시해야 한다.

## 참조 종류와 외부 자원 정리

### Strong·Soft·Weak·Phantom Reference

Java는 일반 참조 외에도 GC와 특별하게 상호작용하는 참조를 제공한다.

|참조 종류|특징|
|---|---|
|Strong Reference|일반적인 객체 참조이며, 강하게 도달 가능한 객체는 회수하지 않는다.|
|Soft Reference|메모리 수요에 따라 참조를 제거할 수 있으며, 유지 기간을 보장하지 않는다.|
|Weak Reference|객체가 약하게만 도달 가능한 상태가 되면 GC가 해당 약한 참조를 제거한다.|
|Phantom Reference|객체의 생애주기와 연결된 후처리 등에 활용하며, `get()`으로 객체를 얻을 수 없다.|

예를 들어 다음과 같이 약한 참조를 생성할 수 있다.

```
WeakReference<User> reference =
        new WeakReference<>(new User());

User user = reference.get();

if (user != null) {
    user.process();
}
```

`get()`의 결과는 이미 `null`일 수 있으므로 반환값을 확인해야 한다. 반환한 객체를 일반 지역 변수에 보관하여 사용하는 동안에는 그 참조가 강한 참조로 작용한다.

또한 `SoftReference`를 사용한다고 예측 가능한 캐시가 자동으로 만들어지지는 않는다. 캐시의 용량이나 만료 정책이 중요하면 이를 명시적으로 관리해야 한다.

### 파일과 소켓은 명시적으로 닫아야 한다

GC는 객체의 메모리를 관리하지만, 파일·소켓·데이터베이스 연결을 원하는 시점에 닫아 주는 기능은 아니다.

외부 자원은 `try-with-resources` 등으로 명시적으로 정리해야 한다.

```
try (InputStream input = Files.newInputStream(path)) {
    byte[] content = input.readAllBytes();
    process(content);
}
```

이 구조는 정상 종료와 예외 발생 시 자원의 `close()`를 호출하도록 한다.

`finalize()`에 자원 정리를 의존하면 안 된다. 실행 시점을 보장할 수 없으며, finalization은 제거 예정으로 폐기된 기능이다. `Cleaner` 역시 결정적인 시점의 자원 해제를 대체하는 수단으로 생각하면 안 된다.

## GC 성능을 평가하는 핵심 지표

### 중단 시간

각 STW가 얼마나 오래 지속되는지 확인한다.

평균만 확인하면 드물게 발생하는 긴 중단을 놓칠 수 있으므로, 상위 백분위와 최댓값을 함께 확인해야 한다.

서비스 관점에서는 GC 중단 시간과 요청 응답 시간의 p95·p99를 같은 시간축에서 비교하는 것이 유용하다.

### 처리량과 GC 비용

같은 CPU와 메모리 조건에서 초당 요청 수나 작업 완료 시간을 확인한다.

STW 시간 비율만 계산하면 다음과 같은 단순 지표를 얻을 수 있다.

```
관측 시간: 10초
총 STW 시간: 0.2초
STW에 멈추지 않은 시간 비율: 98%
```

다만 이 값만으로 애플리케이션 처리량을 판단할 수 없다. 동시 GC는 애플리케이션을 멈추지 않는 동안에도 CPU와 메모리 대역폭을 사용하기 때문이다.

### 할당률과 승격률

**할당률, Allocation Rate**은 단위 시간당 생성하는 객체의 메모리 양이다.

**승격률, Promotion Rate**은 Young에서 Old로 이동하는 객체의 메모리 양이다.

할당률이 높으면 GC가 자주 발생할 수 있다. 승격률이 높으면 Old 영역을 확보해야 하는 부담도 커질 수 있다.

### 살아 있는 데이터의 크기

**Live Set**은 수집 이후에도 유지해야 하는 살아 있는 데이터의 크기이다.

동일한 4GB 힙이라도 살아 있는 객체가 500MB인 경우와 3.5GB인 경우의 GC 부담은 크게 다를 수 있다.

GC는 살아 있는 객체를 회수할 수 없으므로, 애플리케이션이 유지하는 데이터 자체가 너무 크다면 수집기 변경만으로 해결하기 어렵다.

또한 GC 비용은 쓰레기 양뿐 아니라 살아 있는 객체의 양, 참조 관계, 객체 이동량 등에 영향을 받는다.

## GC 로그를 확인하는 방법

### GC 로그 활성화

JDK 9 이후 HotSpot에서는 통합 로깅을 사용할 수 있다.

```
java \
  -Xms1g \
  -Xmx2g \
  '-Xlog:gc*,safepoint:file=gc.log:time,uptime,level,tags:filecount=5,filesize=20M' \
  -jar app.jar
```

각 설정의 의미는 다음과 같다.

- `-Xms1g`는 초기·최소 힙 크기를 1GB로 설정한다.
- `-Xmx2g`는 최대 힙 크기를 2GB로 설정한다.
- `gc*`는 GC 관련 태그 조합의 로그를 기록한다.
- `safepoint`는 safepoint 관련 로그를 기록한다.
- `filecount`와 `filesize`는 로그 파일 회전을 설정한다.

위 힙 크기는 문법을 설명하기 위한 예시이며, 실제 값은 애플리케이션 측정 결과에 따라 정해야 한다.

### 로그 한 줄 해석

다음은 설명을 위해 단순화한 G1 로그 예시이다.

```
[12.345s][info][gc] GC(42) Pause Young (Normal) (G1 Evacuation Pause) 1024M->256M(2048M) 18.500ms
```

|항목|의미|
|---|---|
|`12.345s`|JVM 시작 후 약 12.345초 시점이다.|
|`GC(42)`|해당 GC 이벤트의 식별자이다.|
|`Pause Young`|Young 수집에 해당하는 중단 이벤트이다.|
|`G1 Evacuation Pause`|G1의 객체 대피 작업과 관련된 중단이다.|
|`1024M->256M`|기록된 힙 사용량이 수집 전 1024MB에서 수집 후 256MB로 감소했다는 의미이다.|
|`(2048M)`|해당 시점에 기록된 힙 용량이며, 항상 `-Xmx` 값과 같지는 않다.|
|`18.500ms`|해당 GC 중단에 약 18.5ms가 걸렸다는 의미이다.|

한 번의 로그보다 시간에 따른 빈도, 중단 시간, 회수 후 사용량의 변화를 확인해야 한다. 로그의 세부 형식은 JDK 버전과 수집기에 따라 달라질 수 있다.

### 진단 도구 활용

실행 중인 프로세스에는 다음과 같은 명령을 사용할 수 있다.

```
jcmd <PID> VM.flags
jcmd <PID> GC.heap_info
jcmd <PID> JFR.start name=gc-analysis settings=profile duration=60s filename=gc-analysis.jfr
```

첫 번째 명령은 JVM 옵션을 확인하고, 두 번째 명령은 힙 정보를 확인한다. 세 번째 명령은 60초 동안 Java Flight Recorder 데이터를 수집한다.

힙 덤프는 다음과 같이 생성할 수 있다.

```
jcmd <PID> GC.heap_dump heap.hprof
```

힙 덤프 생성은 큰 힙에서 상당한 중단과 디스크 사용을 유발할 수 있다. 또한 기본 동작에서는 Full GC를 요청하므로 운영 환경에서 실행할 때는 이러한 영향을 고려해야 한다.

## GC가 있어도 메모리 누수가 발생하는 이유

### 불필요한 객체의 참조가 남아 있기 때문이다

Java에서 흔한 메모리 누수는 **더 이상 필요하지 않은 객체를 애플리케이션이 계속 참조하는 상황**이다.

```
class RequestHistory {
    private static final List<byte[]> HISTORY = new ArrayList<>();

    static void record() {
        HISTORY.add(new byte[1024 * 1024]);
    }
}
```

이 코드에서는 `record()`를 호출할 때마다 1MB 배열을 목록에 추가한다.

목록이 계속 도달 가능한 상태이고 요소를 제거하지 않으면, 배열도 계속 살아 있게 된다. GC 입장에서는 정상적으로 참조하는 데이터이므로 회수할 수 없다.

대표적인 원인은 다음과 같다.

- 크기 제한이나 만료 정책이 없는 캐시에서 참조를 계속 유지한다.
- 정적 컬렉션에 데이터를 추가한 뒤 제거하지 않는다.
- 이벤트 리스너나 콜백 등록을 해제하지 않는다.
- 장수하는 스레드의 `ThreadLocal` 값을 적절하게 정리하지 않는다.
- 처리 속도보다 입력 속도가 빨라 큐가 계속 증가한다.
- 클래스 로더와 관련 객체의 참조가 남아 메타데이터 회수를 방해한다.

### 누수 의심 패턴

정상적인 힙 사용량은 객체 할당에 따라 증가했다가 GC 후 감소하는 패턴을 보일 수 있다.

```
정상 가능성: 증가 → 감소 → 증가 → 감소
누수 의심:   GC 후 300MB → 500MB → 800MB → 1.2GB
```

안정적인 부하에서 충분한 수집 이후에도 살아 있는 데이터가 지속적으로 증가한다면 누수를 의심할 수 있다.

다만 데이터 증가, 캐시 준비 과정, 요청 적체도 비슷한 모습을 만들 수 있으므로, 사용량 증가만으로 누수를 확정할 수는 없다.

힙 덤프를 분석할 때는 객체 수뿐 아니라 다음 항목을 확인해야 한다.

- **Retained Size**를 통해 특정 객체가 유지하는 전체 객체 집합의 크기를 확인한다.
- **Dominator Tree**를 통해 많은 메모리를 붙잡고 있는 객체를 확인한다.
- **Path to GC Roots**를 통해 해당 객체를 살아 있게 만드는 참조 경로를 확인한다.

### OutOfMemoryError가 곧 누수를 의미하지는 않는다

`OutOfMemoryError`는 누수 외에도 정상적인 데이터에 비해 힙이 작거나, 지나치게 큰 할당을 시도하거나, 힙 바깥의 메모리가 부족할 때 발생할 수 있다.

`Java heap space`와 `Metaspace` 등의 상세 메시지를 구분하여 조사해야 한다.
