## 하네스란

AI 모델과 하네스를 이해할 때는 **작업자와 작업 환경**에 비유하면 쉽다.

- **AI 모델:** 상황을 이해하고 다음 행동을 판단하는 작업자
- **도구:** 파일 편집기, 검색, 터미널처럼 작업에 사용하는 장비
- **하네스:** 작업 지시, 장비 연결, 권한, 기록, 검증 절차를 관리하는 체계

예를 들어 모델이 “이 파일을 수정해야겠다”고 판단하더라도, 실제 파일이 바뀌려면 외부 프로그램이 그 요청을 받아 실행해야 한다. 실행 결과를 다시 모델에 전달해야 다음 판단도 이어진다.

**이처럼 모델의 판단과 실제 환경의 변화를 연결하는 부분이 하네스의 핵심이다.**

다만 하네스의 범위를 완전히 동일하게 정의하는 것은 아니다. 좁게는 모델 호출과 도구 실행을 관리하는 프로그램을, 넓게는 작업 규칙·문서·검증 체계까지 포함한 환경을 뜻한다. OpenAI의 하네스 엔지니어링 사례도 에이전트가 일할 수 있는 환경과 피드백 구조의 설계를 강조한다.

---

## 왜 모델만으로는 부족할까

“로그인 기능을 만들어 줘”라는 요청을 생각해 본다.

모델은 로그인 코드를 생성할 수 있습니다. 하지만 실제 개발에는 다음 작업이 필요한다.

1. 기존 프로젝트 구조를 확인한다.
2. 현재 인증 방식과 요구사항을 파악한다.
3. 적절한 파일을 수정한다.
4. 서버와 테스트를 실행한다.
5. 오류가 발생하면 원인을 찾아 수정한다.
6. 실제로 로그인이 되는지 확인한다.
7. 완료한 내용과 남은 문제를 기록한다.

이 과정에는 **추론 능력뿐 아니라 실행 환경, 상태 관리, 피드백**이 필요한다.

특히 작업이 길어지면 앞서 한 일을 놓치거나, 일부 기능만 구현하고 완료했다고 판단할 수 있다. Anthropic은 장시간 작업 실험에서 이런 문제를 관찰했고, 기능 목록·진행 기록·작은 단위의 구현·실제 동작 검증을 결합해 개선했다.

## 하네스 구성

구현마다 다르지만, 주요 역할은 다음과 같다.

|구성 요소|하는 일|예시|
|---|---|---|
|**실행 루프**|모델의 판단과 도구 실행을 반복 연결|수정 → 테스트 → 오류 확인 → 재수정|
|**컨텍스트 관리**|현재 판단에 필요한 정보를 제공|관련 코드, 사용자 요구사항, 이전 작업 요약|
|**도구 연결**|모델의 요청을 실제 작업으로 실행|파일 읽기, 명령 실행, 브라우저 조작|
|**상태 저장**|중단 후에도 작업을 이어갈 수 있게 기록|완료 항목, 미해결 문제, 체크포인트|
|**권한 제어**|허용된 범위 안에서 작업하도록 제한|수정 가능한 폴더, 네트워크 접근 범위|
|**검증과 피드백**|결과가 요구사항을 만족하는지 확인|테스트 결과, 화면 확인, 평가 기준|
|**종료·복구 관리**|무한 반복을 막고 실패에 대응|시간 제한, 재시도 횟수, 사용자에게 인계|
|**실행 기록**|문제의 원인과 비용을 추적|호출 내역, 오류 로그, 토큰 사용량|

여기서 중요한 차이가 있다.

**“이렇게 행동하라”는 지시와 “이렇게만 행동할 수 있다”는 제한은 다르다.**

예를 들어 “허용된 폴더만 수정하라”는 프롬프트는 행동 지침이다. 운영체제나 샌드박스에서 다른 폴더의 쓰기를 막는 것은 실제 접근 제한이다. 하네스는 이런 지침과 기술적 제어를 함께 구성할 수 있다.

## 동작

기본 흐름은 다음과 같다.

```
사용자 요청
    ↓
하네스가 지침·작업 상태·사용 가능한 도구를 준비
    ↓
모델이 다음 행동을 판단
    ↓
하네스가 도구 요청을 검사하고 실행
    ↓
실행 결과와 갱신된 상태를 모델에 전달
    ↓
모델이 결과를 보고 다음 행동을 판단
    ↓
완료 조건을 충족하거나 중단 조건에 도달할 때까지 반복
```

예를 들어 다음과 같은 대화가 시스템 내부에서 이어지는 셈이다.

> 모델: “인증 코드를 읽어야겠다.”  
> 하네스: 파일 읽기 도구를 실행하고 내용을 전달한다.  
> 모델: “여기가 문제다. 이 부분을 수정하겠다.”  
> 하네스: 수정 요청을 실행하고 결과를 전달한다.  
> 모델: “테스트로 확인해야겠다.”  
> 하네스: 테스트를 실행하고 실패 로그를 전달한다.  
> 모델: “이 오류를 반영해 다시 수정하겠다.”

**모델은 다음 행동을 제안하고, 하네스는 그 행동이 실행되고 결과가 돌아오는 절차를 관리한다.** 일부 단계는 모델 판단 대신 정해진 코드나 규칙으로 처리할 수도 있다.

## 프롬프트·에이전트·프레임워크

서로 연결된 개념이지만 초점이 다르다.

|개념|중심 역할|이해하기 쉬운 표현|
|---|---|---|
|**모델**|입력을 해석하고 응답·행동을 생성|판단하는 두뇌|
|**프롬프트**|목표, 조건, 행동 방식을 전달|작업 지시서|
|**도구**|외부 환경에 접근하거나 행동을 실행|작업 장비|
|**하네스**|모델·도구·상태·제어를 연결|작업을 굴리는 실행 체계|
|**에이전트**|목표를 향해 행동하는 전체 시스템|실행 가능한 작업자|
|**프레임워크·SDK**|이런 시스템을 만들 때 쓰는 재사용 코드|개발용 부품과 기반|

**프롬프트와 하네스의 차이**

프롬프트에 “수정 후 테스트하라”고 쓸 수 있다. 하네스는 테스트 도구를 제공하고, 실행 결과를 전달하며, 필요하다면 테스트 통과 여부를 완료 조건으로 검사한다.

**프레임워크와 하네스의 차이**

프레임워크는 하네스를 만드는 데 사용할 수 있다. 어떤 프레임워크는 기본 하네스까지 제공한다. 따라서 두 용어가 가리키는 기능이 겹치기도 하지만, 프레임워크는 **개발 기반**, 하네스는 **실제로 작업을 운영하는 구조**에 초점이 있다.

## 하네스 엔지니어링이 하는 일

**하네스 엔지니어링은 에이전트의 성공률을 높이기 위해 실행 환경과 피드백 구조를 설계하고 개선하는 작업이다.**

예를 들어 에이전트가 반복해서 실패한다면 원인을 구분한다.

|반복되는 문제|하네스에서 검토할 부분|
|---|---|
|관련 파일을 찾지 못한다|검색 도구, 프로젝트 구조 안내|
|이전 결정을 잊는다|상태 저장, 컨텍스트 전달 방식|
|오류를 계속 반복한다|오류 메시지 품질, 재시도·중단 규칙|
|기능을 덜 만들고 종료한다|요구사항 목록, 완료 조건|
|테스트는 통과하지만 사용이 어렵다|실제 사용자 흐름 검증, 평가 기준|
|시간과 비용이 과도하다|불필요한 호출, 중복 작업, 실행 예산|

이때 모델의 능력 부족과 환경의 문제를 구분하는 것이 중요한다. 올바른 정보가 전달되지 않았다면 컨텍스트 구성을 개선하고, 도구가 불안정하다면 도구부터 고쳐야 한다.

OpenAI의 사례도 사람이 목표를 명확히 하고, 에이전트가 이해할 수 있는 환경과 검증 가능한 규칙을 만드는 역할을 강조한다.

## 좋은 하네스는 복잡한 하네스인가

**필요한 기능을 갖추되, 각 기능이 실제로 도움이 되는지 확인하는 것이 중요한다.**

작업이 단순하면 모델 호출과 몇 가지 도구만으로 충분할 수 있다. 긴 개발 작업에서는 상태 저장과 검증 루프가 중요해지고, 작업 범위가 넓어지면 역할을 나눈 에이전트가 도움이 될 수 있다.

하지만 에이전트를 추가하면 호출 비용, 대기 시간, 정보 전달 부담도 늘어난다. 평가 에이전트를 따로 두어도 그 평가가 자동으로 정확해지는 것은 아니다.

Anthropic의 후속 실험에서는 계획·생성·평가 역할을 분리해 결과를 개선했지만, 비용과 실행 시간도 늘었다. 또한 모델이 발전하면 기존에 필요했던 보완 장치를 줄일 수 있다고 설명한다.

따라서 하네스를 평가할 때는 다음을 함께 본다.

- **성공률:** 요구사항을 충족한 작업의 비율
- **결과 품질:** 정확성, 사용성, 유지보수성
- **시간과 비용:** 완료까지 걸린 시간과 사용 자원
- **복구 능력:** 오류나 중단 이후 이어갈 수 있는 정도
- **개입 부담:** 사람이 수정하거나 도와야 하는 빈도

## 자주 생기는 오해

**“하네스를 개선하면 모델이 다시 학습되는가?”**

일반적으로 모델의 가중치는 바뀌지 않는다. 모델에 주는 정보와 도구, 실행 절차, 피드백이 달라진다. 같은 모델도 환경에 따라 작업 성과가 달라질 수 있다.

**“하네스가 있으면 환각이나 실수가 없어지는가?”**

없어지지는 않는다. 외부 자료 조회와 검증을 통해 오류를 발견하고 줄이는 구조를 만들 수 있다. 검증 자체가 잘못되면 오류가 통과할 수도 있다.

**“하네스에는 반드시 여러 에이전트가 필요한가?”**

필수는 아니다. 하나의 모델을 도구와 연결해 반복 실행하는 구조도 하네스이다.

**“테스트 하네스와 같은 말인가?”**

공통적으로 **대상을 실행하고 제어하며 결과를 확인하는 주변 체계**라는 의미가 있다. 테스트 하네스는 테스트 실행과 평가에, 에이전트 하네스는 목표 수행을 위한 모델·도구·상태 관리에 초점을 둔다.
