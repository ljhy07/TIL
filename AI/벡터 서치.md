## 핵심 원리

다음 문서가 저장되어 있다고 가정하면

```
문서 A: 결제 후 7일 이내에 상품을 환불할 수 있습니다.
문서 B: 비밀번호는 계정 설정에서 변경할 수 있습니다.
문서 C: 배송 현황은 주문 내역에서 확인할 수 있습니다.
```

사용자가 다음과 같이 검색한다.

```
구매한 물건을 취소하고 돈을 돌려받고 싶어요.
```

키워드 검색에서는 질의에 `환불`이라는 단어가 없기 때문에 문서 A를 놓칠 수 있다. 벡터 서치는 질의와 문서를 임베딩한 뒤 의미적 거리를 비교한다.

```
질의 벡터 ↔ 문서 A 벡터: 가까움
질의 벡터 ↔ 문서 B 벡터: 멂
질의 벡터 ↔ 문서 C 벡터: 다소 멂
```

따라서 문서 A를 가장 관련성 높은 결과로 반환한다.

핵심 흐름은 다음과 같다.

```
문서 → 임베딩 모델 → 문서 벡터 → 벡터 저장소

질의 → 같은 임베딩 모델 → 질의 벡터
                              ↓
                    가까운 문서 벡터 검색
```

---

## 일반 검색과 다른 점

### 키워드 검색

키워드 검색은 주로 단어나 문자열의 일치를 이용한다.

```
질의: 자동차 수리
문서: 자동차를 수리하는 방법
```

정확한 단어, 희귀한 고유명사, 상품 코드, 오류 코드 검색에 강한다.

```
ERR_CONNECTION_RESET
AB-19374
김민수
```

하지만 표현이 달라지면 결과를 놓칠 수 있다.

```
질의: 자동차 수리
문서: 차량 정비 방법
```

### 벡터 검색

벡터 검색은 표현이 달라도 의미가 비슷하면 찾을 수 있다.

```
자동차 수리 ≈ 차량 정비
환불하고 싶다 ≈ 구매를 취소하고 돈을 돌려받고 싶다
```

반면 정확한 문자열 구분에는 약할 수 있다.

```
제품 코드 A-100
제품 코드 A-101
```

두 문자열은 의미와 구조가 비슷해 벡터도 가까울 가능성이 있지만, 사용자가 원하는 것은 정확한 코드 일치일 수 있다.

실무에서는 보통 두 방식을 결합한 **하이브리드 검색**을 사용한다.

---

## 벡터 서치의 전체 구조

벡터 검색 시스템은 크게 색인 단계와 검색 단계로 나뉜다.

### 색인 단계

```
원본 데이터 수집
    ↓
정제 및 전처리
    ↓
문서 분할(chunking)
    ↓
임베딩 생성
    ↓
벡터 + 원문 + 메타데이터 저장
    ↓
벡터 인덱스 구축
```

### 검색 단계

```
사용자 질의
    ↓
질의 전처리
    ↓
질의 임베딩 생성
    ↓
메타데이터 필터링
    ↓
유사 벡터 검색
    ↓
후보 결과 재순위화
    ↓
최종 결과 반환
```

RAG 시스템에서는 마지막에 검색된 문서를 언어 모델에 전달한다.

```
검색 결과 + 사용자 질문
           ↓
         LLM
           ↓
근거를 이용한 답변 생성
```

## 벡터에서 저장하는 것

벡터 데이터베이스에는 일반적으로 벡터만 저장하지 않는다. 원문과 메타데이터를 함께 저장한다.

```
{
  "id": "policy-103",
  "vector": [0.12, -0.45, 0.81],
  "text": "상품은 결제 후 7일 이내에 환불할 수 있다.",
  "metadata": {
    "category": "refund",
    "language": "ko",
    "department": "customer-support",
    "updated_at": "2026-07-01"
  }
}
```

각 필드의 역할은 다음과 같다.

- `id`: 항목을 구별하는 식별자
- `vector`: 유사도 검색에 사용하는 임베딩
- `text`: 검색 결과로 반환할 원문
- `metadata`: 날짜, 조직, 권한, 언어 등 필터 조건

벡터는 “무엇이 비슷한지” 판단하고, 메타데이터는 “검색 대상에 포함해도 되는지” 결정한다.

## 유사도 계산 방법

벡터 검색에서는 두 벡터 사이의 유사도 또는 거리를 계산한다.

### 코사인 유사도

가장 흔히 사용되는 방식이다.

\[ \text{cosine}(A,B) = \frac{A \cdot B}{\|A\|\|B\|} \]

벡터의 크기보다 **방향이 얼마나 비슷한지** 측정한다.

```
같은 방향   → 유사도가 높음
다른 방향   → 유사도가 낮음
반대 방향   → 음수 가능
```

텍스트 임베딩에서는 문장의 길이나 벡터 크기보다 의미적 방향을 비교하려는 경우가 많아 코사인 유사도가 널리 사용된다.

### 내적

\[ A \cdot B = \sum_i A_iB_i \]

두 벡터가 정규화되어 있다면 코사인 유사도와 같은 순위를 만들 수 있다.

```
||A|| = 1, ||B|| = 1
→ A · B = cosine(A, B)
```

일부 모델은 내적 검색을 전제로 학습된다.

### 유클리드 거리

\[ d(A,B)=\sqrt{\sum_i(A_i-B_i)^2} \]

공간상 실제 거리를 계산하다. 값이 작을수록 가깝다.

중요한 점은 **임베딩 모델이 권장하는 거리 함수를 사용해야 한다**는 것이다. 모델은 코사인 유사도에 맞게 학습됐는데 검색 시스템은 다른 방식을 사용하면 성능이 떨어질 수 있다.

## KNN과 ANN

벡터 검색에서 사용되는 두 가지 중요한 개념이다.

### 정확한 KNN

KNN은 K-Nearest Neighbors, 즉 가장 가까운 K개 항목을 찾는 방법이다.

문서 벡터가 100개라면 질의 벡터를 모든 문서와 비교해도 큰 문제가 없다.

```
질의 벡터
  ├─ 문서 1과 비교
  ├─ 문서 2와 비교
  ├─ 문서 3과 비교
  └─ ...
```

문서가 \(N\)개이고 벡터 차원이 \(D\)라면, 단순 검색 비용은 대략 다음과 같다.

\[ O(ND) \]

벡터가 수백만 개라면 매번 전부 비교하는 것은 느리고 비싼다.

### 근사 ANN

ANN은 Approximate Nearest Neighbor, 즉 근사 최근접 이웃 검색이다.

모든 벡터를 확인하지 않고, 가까울 가능성이 높은 영역만 탐색한다.

```
정확한 검색:
전체 1,000만 개 비교

근사 검색:
후보 영역 일부만 탐색
```

정답을 아주 조금 놓칠 수 있는 대신 속도를 크게 높인다. 대규모 서비스에서는 대부분 ANN을 사용한다.

ANN의 핵심 트레이드오프는 다음과 같다.

```
검색 범위를 넓힘
→ 정확도 상승
→ 지연 시간과 비용 상승

검색 범위를 줄임
→ 속도 상승
→ 정답을 놓칠 가능성 상승
```

## 대표적인 벡터 인덱스

### Flat 또는 Brute-force

모든 벡터를 직접 비교한다.

장점:
- 가장 정확함
- 구조가 단순함
- 작은 데이터셋에 적합함

단점:
- 데이터가 커질수록 느려짐
- 계산량이 선형적으로 증가함

평가용 정답 기준을 만들거나 데이터가 적을 때 유용한다.

---

### HNSW

HNSW는 Hierarchical Navigable Small World의 약자이다. 벡터들을 그래프 형태로 연결한다.

```
상위 계층: 드문드문 연결된 고속 이동 경로
하위 계층: 촘촘하게 연결된 세부 탐색 경로
```

검색할 때 상위 계층에서 목표 영역으로 빠르게 이동한 뒤, 하위 계층에서 가까운 벡터를 자세히 탐색한다.

장점:
- 검색 속도와 재현율이 좋음
- 실시간 검색에 적합함
- 다양한 데이터 분포에서 안정적인 편

단점:
- 메모리 사용량이 큼
- 인덱스 생성 비용이 있음
- 대량 삽입·삭제 운영이 복잡할 수 있음

주요 설정 개념은 다음과 같다.

- `M`: 노드당 연결 수
- `efConstruction`: 인덱스를 만들 때 탐색하는 후보 수
- `efSearch`: 검색할 때 탐색하는 후보 수

대체로 값을 키우면 품질과 비용이 함께 증가한다.

---

### IVF

IVF는 Inverted File Index의 약자이다. 벡터 공간을 여러 군집으로 나눈다.

```
전체 벡터
  ├─ 군집 1
  ├─ 군집 2
  ├─ 군집 3
  └─ ...
```

검색 시 질의와 가까운 군집 몇 개만 조사한다.

장점:
- 대규모 데이터셋에 적합함
- 검색량을 직접 조정하기 쉬움
- 압축 기법과 함께 사용하기 좋음

단점:
- 군집 학습이 필요함
- 군집 경계에 있는 정답을 놓칠 수 있음
- 데이터 분포가 바뀌면 재학습이 필요할 수 있음

대표 설정은 다음과 같다.

- `nlist`: 전체 군집 개수
- `nprobe`: 검색할 군집 개수

`nprobe`가 커질수록 정확도는 높아지지만 느려진다.

---

### PQ

PQ는 Product Quantization의 약자입니다. 고차원 벡터를 작은 코드로 압축한다.

```
원본 벡터: 수백~수천 개 실수
압축 벡터: 짧은 정수 코드
```

장점:
- 메모리 사용량 감소
- 매우 큰 데이터셋에 유리
- 디스크 및 네트워크 비용 절감

단점:
- 압축 과정에서 정보 손실
- 검색 정확도가 낮아질 수 있음

대규모 환경에서는 `IVF + PQ`처럼 조합해서 사용하기도 한다.

## 문서 분할이 중요한 이유

긴 문서를 통째로 하나의 벡터로 만들면 여러 주제가 섞인다.

예를 들어 사내 규정 문서에 다음 내용이 모두 들어 있다고 해본다.

```
1장: 휴가 정책
2장: 비용 처리
3장: 보안 규정
4장: 퇴직 절차
```

문서 전체를 하나의 벡터로 만들면 `휴가`, `비용`, `보안`, `퇴직` 정보가 평균적으로 섞인다. 특정 질문과의 유사도가 충분히 높지 않을 수 있다.

그래서 문서를 작은 청크로 나눈다.

```
문서
  ├─ 청크 1: 연차 신청 방법
  ├─ 청크 2: 병가 규정
  ├─ 청크 3: 출장비 정산
  └─ 청크 4: 계정 보안
```

### 너무 작은 청크

```
"7일 이내 가능합니다."
```

검색되더라도 무엇이 7일 이내 가능한지 알기 어렵다.

### 너무 큰 청크

환불, 배송, 교환 규정이 한꺼번에 들어가 의미가 희석된다.

### 일반적인 전략

- 제목과 본문을 함께 저장
- 문단 또는 의미 단위로 분할
- 청크 사이에 일정한 중복 구간 사용
- 표나 코드 블록의 구조를 가능하면 보존
- 상위 문서 ID를 메타데이터로 유지

고정된 글자 수보다 **의미적으로 완결된 단위**가 더 중요하다.

## 메타데이터 필터링

벡터가 의미상 가깝더라도 반환하면 안 되는 문서가 있을 수 있다.

예를 들어 사용자에게 자신의 부서 문서만 보여줘야 한다면:

```
department = "finance"
AND access_level <= 사용자 권한
AND language = "ko"
```

그 조건을 만족하는 문서 안에서만 벡터 검색해야 한다.

특히 권한 제어는 검색 이후가 아니라 검색 과정에서 적용하는 것이 안전하다.

```
좋지 않은 방식:
전체 문서 검색 → 상위 결과 반환 직전에 권한 검사

권장 방식:
권한 필터 적용 → 허용된 문서에서 검색
```

벡터 데이터베이스마다 필터를 처리하는 방식이 다르다.

- 사전 필터링: 조건에 맞는 데이터만 대상으로 ANN 검색
- 사후 필터링: ANN 결과를 가져온 뒤 조건에 맞지 않는 항목 제거
- 통합 필터링: 인덱스 탐색 중 조건을 함께 적용

사후 필터링만 사용하면 원하는 결과 개수를 채우지 못할 수 있다.

## 하이브리드 검색

하이브리드 검색은 벡터 검색과 키워드 검색을 결합한다.

```
질의
 ├─ 벡터 검색 → 의미적으로 비슷한 결과
 └─ 키워드 검색 → 단어가 정확히 일치하는 결과
                    ↓
                결과 결합
```

예를 들어 다음 질의를 생각해 본다.

```
ERR-4312 결제 실패 해결 방법
```

- `결제 실패 해결 방법`은 의미 검색이 잘 처리하다.
- `ERR-4312`는 정확한 키워드 검색이 더 잘 처리한다.

결과를 합치는 방법에는 여러 가지가 있다.

### 가중 점수 결합

\[ score = \alpha \times vectorScore + (1-\alpha) \times keywordScore \]

하지만 두 검색 점수의 분포가 다르므로 정규화가 필요하다.

### 순위 기반 결합

각 검색 결과의 실제 점수 대신 순위를 사용다. 대표적으로 RRF(Reciprocal Rank Fusion)가 있다.

\[ RRF(d)=\sum_r \frac{1}{k+\text{rank}_r(d)} \]

서로 다른 검색 엔진의 점수 범위를 직접 맞추지 않아도 된다는 장점이 있다.

---

## 재순위화

벡터 검색은 빠르지만 미묘한 사실 관계를 완벽하게 구별하지 못할 수 있다.

```
A: 무료 취소는 출발 24시간 전까지 가능합니다.
B: 무료 취소는 출발 24시간 전부터 불가능합니다.
```

두 문장은 거의 같은 단어를 사용하므로 임베딩이 가깝게 나올 수 있다. 이때 reranker가 질문과 문서를 함께 자세히 읽고 순위를 다시 계산한다.

```
1단계: ANN 검색으로 후보 50개 추출
2단계: reranker가 50개를 정밀 비교
3단계: 상위 5개 반환
```

검색과 재순위 모델의 차이는 다음과 같다.

- 임베딩 검색: 질의와 문서를 따로 벡터화하므로 빠름
- 교차 인코더 reranker: 질의와 문서를 함께 읽으므로 정확하지만 느림

그래서 넓은 후보 검색에는 임베딩을, 소수 후보의 정밀 순위 결정에는 reranker를 사용한다.

## 벡터 점수의 올바른 해석

벡터 유사도는 확률이 아니다.

```
코사인 유사도 0.82
≠ 82% 확률로 정답
```

또한 점수 기준은 다음에 따라 달라진다.

- 임베딩 모델
- 언어
- 문서 길이
- 데이터 분야
- 질의 유형
- 벡터 정규화 여부

따라서 `0.8 이상이면 관련 문서` 같은 전역 규칙을 무조건 적용해서는 안 된다. 실제 질문과 정답 문서로 검증해 임계값을 정해야 한다.

필요하다면 절대 점수뿐 아니라 다음도 함께 본다.

```
1위 점수
1위와 2위의 점수 차이
상위 결과들의 점수 분포
키워드 검색 점수
reranker 점수
```

관련 문서가 없을 때는 억지로 결과를 반환하지 않도록 **검색 거절 기준**도 필요한다.

## 벡터 검색 품질 평가

검색 결과가 그럴듯해 보이는지만 확인하면 부족한다. 실제 질문과 정답 문서로 평가 세트를 만들어야 한다.

### Recall@K

정답 문서가 상위 K개 결과 안에 들어왔는지 측정한다.

```
정답 문서가 Top 5 안에 있음 → 성공
```

RAG에서는 정답 문서가 생성 모델에 전달되기만 하면 활용할 가능성이 있으므로 Recall@K가 특히 중요하다.

### Precision@K

상위 K개 중 실제 관련 문서가 얼마나 많은지 측정하다.

\[ Precision@K = \frac{\text{상위 K개 중 관련 문서 수}}{K} \]

### MRR

첫 번째 정답 문서가 얼마나 높은 순위에 나오는지 측정한다.

```
1위에 정답 → 1
2위에 정답 → 1/2
5위에 정답 → 1/5
```

### nDCG

관련성이 여러 단계일 때 순위 품질을 평가한다.

```
매우 관련 있음
부분적으로 관련 있음
관련 없음
```

### 시스템 지표

품질뿐 아니라 운영 성능도 측정해야 한다.

- 평균 검색 시간
- p95·p99 지연 시간
- 임베딩 생성 비용
- 인덱스 메모리 사용량
- 인덱스 갱신 시간
- 초당 처리량
- 검색 실패율

## 데이터 업데이트와 삭제

운영 환경에서는 문서가 계속 변경된다.

```
새 문서 추가
기존 문서 수정
문서 삭제
권한 변경
임베딩 모델 교체
```

문서를 수정했다면 관련 청크의 임베딩도 다시 계산해야 한다.

삭제할 때는 세 부분을 함께 처리해야 한다.

- 원본 문서
- 청크
- 벡터 인덱스 항목

권한이 제거된 문서가 오래된 인덱스에 남아 검색되는 문제는 심각한 정보 노출로 이어질 수 있다.

임베딩 모델을 교체하면 보통 전체 문서를 새 모델로 다시 임베딩한다. 서로 다른 모델의 벡터는 같은 공간에서 직접 비교할 수 없기 때문이다.

안전한 교체 방법은 보통 다음과 같다.

```
기존 인덱스 유지
    ↓
새 모델로 새 인덱스 구축
    ↓
오프라인 품질 평가
    ↓
일부 트래픽으로 시험
    ↓
검색 인덱스 전환
    ↓
기존 인덱스 제거
```

## 자주 발생하는 실패 사례

### 모든 문서를 하나의 거대한 청크로 저장

세부 정보가 희석되어 정확한 단락을 찾기 어렵다.

### 청크가 지나치게 작음

검색은 되지만 답변에 필요한 문맥이 없다.

### 질문과 문서를 서로 다른 모델로 임베딩

두 벡터를 비교할 수 없는 공간에 배치하게 된다.

### 코드와 고유명사까지 의미 검색에만 의존

오류 코드, 계약 번호, 제품 SKU는 키워드 검색과 결합해야 한다.

### `Top K`를 무조건 크게 설정

관련 없는 문서까지 LLM에 전달되어 답변 품질과 비용이 악화될 수 있다.

### 검색 점수를 확률로 해석

유사도 점수만 보고 정답 여부를 단정하면 안 된다.

### 검색 이후에만 권한 검사

후보 처리나 로그 단계에서 민감한 문서가 노출될 수 있습니다. 권한을 검색 조건에 포함해야 한다.

### 평가 없이 모델이나 청크 크기 선택

몇 개의 데모 질문이 잘된다는 이유만으로 전체 품질을 판단하면 실제 트래픽에서 문제가 발생한다.

## 설계 기준

1. 무엇을 검색할 것인지 정의한다.
2. 실제 사용자 질문과 정답 문서로 평가 세트를 만든다.
3. 문서를 의미 단위로 분할한다.
4. 도메인과 언어에 적합한 임베딩 모델을 선택한다.
5. 키워드 검색이 필요한 필드를 구분한다.
6. 접근 권한과 메타데이터 필터를 설계한다.
7. 작은 규모에서는 정확 검색으로 기준 성능을 측정한다.
8. 데이터가 커지면 HNSW나 IVF 같은 ANN 인덱스를 적용한다.
9. 후보 검색 뒤에 reranker를 추가한다.
10. Recall@K, 지연 시간, 비용을 함께 최적화한다.
