## 소프트웨어 아키텍처란?

**소프트웨어 아키텍처는 시스템을 어떤 구성 요소로 나누고, 각 요소가 어떤 책임을 맡으며, 서로 어떻게 협력할지 정하는 큰 구조와 핵심 설계 결정이다.**

웹 서비스와 애플리케이션을 만드는 **소프트웨어·시스템 아키텍처**를 기준으로 설명한다.

쇼핑몰을 예로 들면 다음과 같은 질문이 아키텍처에 해당한다.

- 상품, 주문, 결제 기능을 하나의 애플리케이션에 넣을까, 별도 서비스로 나눌까?
- 주문 정보와 결제 정보는 어디에 저장할까?
- 결제 서비스가 응답하지 않으면 주문을 어떻게 처리할까?
- 사용자가 늘어나면 어느 부분을 확장할까?
- 누가 어떤 데이터에 접근할 수 있게 할까?

즉, 아키텍처는 **기능을 구현하는 방법뿐 아니라, 시스템을 변경하고 운영하는 방법까지 결정하는 설계**이다.

---

## 아키텍처가 필요한 이유

작은 프로그램은 한 파일에 모든 기능을 작성해도 동작할 수 있다. 하지만 기능과 사용자가 늘어나면 구조가 없는 시스템은 관리하기 어려워진다.

예를 들어 주문 처리 코드 안에 가격 계산, 데이터베이스 저장, 결제 요청, 이메일 발송이 모두 섞여 있다고 가정해 본다.

이 구조에서는 할인 정책 하나를 바꾸는 작업이 결제나 주문 저장에 영향을 줄 수 있다. 이메일 발송이 실패했다는 이유로 주문 자체가 실패할 수도 있다.

아키텍처는 이런 문제를 줄이기 위해 다음을 정한다.

|설계 대상|핵심 질문|
|---|---|
|책임 분리|어떤 구성 요소가 어떤 일을 담당하는가?|
|의존 관계|어떤 구성 요소가 다른 구성 요소를 알아야 하는가?|
|데이터 관리|데이터의 주인은 누구이며, 어디에서 변경하는가?|
|통신 방식|직접 호출할 것인가, 메시지를 전달할 것인가?|
|장애 처리|일부 기능이 실패하면 나머지는 어떻게 동작하는가?|
|배포와 확장|어떤 단위로 배포하고 자원을 늘리는가?|

좋은 아키텍처의 목적은 구조를 복잡하게 만드는 것이 아니다. **필요한 기능을 안정적으로 제공하면서, 변경에 드는 비용과 위험을 줄이는 것**이다.

## 아키텍처는 여러 관점으로 봐야 한다

아키텍처를 서버와 데이터베이스가 연결된 그림 하나로 이해하면 중요한 부분을 놓치기 쉽다. 같은 시스템도 관점에 따라 다른 구조를 가진다.

### 논리 구조: 기능과 책임

시스템을 업무 단위나 역할 단위로 나누는 관점이다.

쇼핑몰이라면 다음과 같이 나눌 수 있다.

- **회원:** 가입, 로그인, 사용자 정보 관리
- **상품:** 상품 정보, 가격, 판매 상태 관리
- **주문:** 주문 생성, 상태 변경, 취소
- **결제:** 결제 승인, 결제 취소, 환불
- **배송:** 배송 요청, 운송장, 배송 상태 관리

여기서 중요한 것은 이름보다 **책임의 경계**이다. 예를 들어 결제 모듈이 주문 테이블을 직접 수정하기 시작하면, 주문 상태를 누가 책임지는지 불분명해진다.

### 코드 구조: 구현 정리

폴더, 패키지, 모듈과 이들 사이의 의존 관계를 다룬다.

```
application/
├── members/
├── products/
├── orders/
├── payments/
└── shipping/
```

이런 폴더 구조는 출발점일 뿐이다. 폴더를 나누었더라도 모든 모듈이 서로의 내부 구현을 직접 사용한다면 경계가 제대로 지켜지는 것은 아니다.

**코드 구조의 핵심은 파일 위치보다, 무엇을 공개하고 무엇을 내부에 숨기는가에 있다.**

### 실행 구조: 실제 요청 처리

실행 중에 구성 요소들이 협력하는 방식이다.

```
사용자 → API 서버 → 주문 처리 → 결제 시스템 → 주문 결과 반환
```

여기서는 호출 순서, 응답 시간, 동시 처리, 타임아웃, 재시도 등을 살펴본다.

### 배포 구조: 실행

애플리케이션과 데이터베이스를 어떤 환경에 배치하는지 다룬다.

```
인터넷
  ↓
로드 밸런서
  ├── 애플리케이션 서버 A
  └── 애플리케이션 서버 B
              ↓
          데이터베이스
```

논리적으로 여러 모듈로 나뉘어 있어도 배포는 하나의 애플리케이션으로 할 수 있다. 반대로 하나의 기능을 여러 서버에서 실행할 수도 있다.

**모듈을 나누는 것과 서버를 나누는 것은 서로 다른 결정이다.**

## 웹 서비스 아키텍처의 주요 구성 요소

일반적인 웹 서비스에는 다음과 같은 구성 요소가 등장한다. 모든 서비스가 처음부터 전부 갖출 필요는 없다.

### 클라이언트

사용자가 직접 사용하는 웹 브라우저나 모바일 앱이다.

주요 책임은 화면 표시, 사용자 입력, 서버 요청, 결과 안내이다.

클라이언트에서도 입력을 검사하지만, 중요한 검증은 서버가 다시 수행해야 한다. 예를 들어 결제 금액을 클라이언트가 전달했다고 해서 서버가 그대로 신뢰해서는 안 된다.

### API 서버

클라이언트의 요청을 받아 업무 처리를 수행하는 진입점이다.

주로 다음을 담당한다.

- 사용자 인증과 접근 권한 확인
- 요청 데이터 검증
- 업무 로직 실행
- 데이터 조회와 저장
- 외부 시스템 호출
- 처리 결과 반환

작은 서비스에서는 하나의 API 서버 애플리케이션이 대부분의 기능을 담당해도 충분하다.

### 데이터베이스

주문, 회원, 결제 기록처럼 지속적으로 보존해야 하는 데이터를 저장한다.

설계할 때는 저장 형식뿐 아니라 다음을 함께 고려한다.

- 어떤 데이터가 서로 일관성을 유지해야 하는가?
- 어떤 작업을 하나의 트랜잭션으로 처리해야 하는가?
- 조회와 수정이 동시에 발생하면 어떻게 처리하는가?
- 백업을 실제로 복원할 수 있는가?

특히 **트랜잭션 경계**는 중요하다. 주문 생성과 재고 차감이 반드시 함께 성공해야 한다면, 이를 보장할 수 있는 구조가 필요하다.

### 캐시

반복해서 조회하는 데이터를 빠르게 제공하기 위한 저장소이다.

상품 정보처럼 자주 읽는 데이터를 캐시에 두면 데이터베이스 부하와 응답 시간을 줄일 수 있다. 대신 원본 데이터가 바뀌었을 때 캐시를 언제 갱신하거나 삭제할지 정해야 한다.

따라서 캐시는 성능 문제를 해결하는 동시에 **데이터가 잠시 오래된 상태일 수 있다는 문제**를 추가한다.

### 메시지 큐와 작업 처리기

즉시 완료할 필요가 없는 작업을 나중에 처리하도록 전달한다.

```
주문 완료 → 메시지 큐 → 작업 처리기 → 이메일 발송
```

사용자가 주문 결과를 받기 위해 이메일 발송까지 기다릴 필요가 없게 만드는 방식이다.

다만 메시지는 중복 전달되거나 처리가 지연될 수 있다. 같은 작업이 여러 번 실행되어도 문제가 없도록 설계하고, 실패한 작업을 재처리할 방법도 마련해야 한다.

### 외부 시스템

결제, 문자 발송, 지도, 배송사 API 등 직접 운영하지 않는 시스템이다.

외부 시스템은 느려지거나 실패할 수 있으므로 다음을 정해야 한다.

- 얼마나 기다릴 것인가?
- 실패하면 다시 요청해도 안전한가?
- 응답을 받지 못했을 때 실제 처리 여부를 어떻게 확인할 것인가?
- 사용자에게 어떤 상태를 보여줄 것인가?

## 대표적인 아키텍처 스타일

아키텍처 스타일은 문제를 풀기 위한 구조적 접근이다. 서로 배타적인 선택지만 있는 것은 아니며, 하나의 시스템에서 여러 스타일을 함께 사용할 수 있다.

### 계층형 아키텍처

역할에 따라 코드를 여러 계층으로 나눈다.

```
표현 계층       요청과 응답 처리
    ↓
애플리케이션 계층 업무 흐름 조정
    ↓
도메인 계층     핵심 업무 규칙
```

데이터베이스나 외부 API 연동은 별도의 인프라 영역에서 담당할 수 있다. 실제 의존 방향은 사용하는 설계 방식에 따라 달라진다.

예를 들어 주문 요청을 받았을 때 다음처럼 책임을 나눈다.

|영역|역할|
|---|---|
|컨트롤러|요청을 읽고 응답 형식을 만든다|
|애플리케이션 서비스|주문 생성 과정을 조정한다|
|도메인 로직|주문 가능 여부와 가격 규칙을 판단한다|
|저장소 구현|주문을 데이터베이스에 저장한다|

이해하기 쉽고 일반적인 업무 시스템에 적용하기 좋다. 다만 모든 판단이 하나의 거대한 서비스 클래스에 모이지 않도록 주의해야 한다.

### 모놀리식 아키텍처

여러 기능을 하나의 애플리케이션으로 묶어 배포한다.

초기 개발과 운영이 비교적 단순하고, 같은 데이터베이스 안에서 트랜잭션을 처리하기 쉽다. 반면 기능이 커지면 작은 변경에도 전체 애플리케이션을 다시 배포해야 할 수 있다.

모놀리스라고 해서 코드가 반드시 뒤섞여 있는 것은 아니다. **내부 기능의 경계를 명확히 유지하는 모듈형 모놀리스**도 가능한다.

### 마이크로서비스 아키텍처

업무 기능을 독립적으로 배포할 수 있는 여러 서비스로 분리한다.

```
클라이언트
    ↓
API 진입점
    ├── 상품 서비스
    ├── 주문 서비스
    └── 결제 서비스
```

서비스별로 배포하거나 자원을 확장할 수 있다는 장점이 있다. 하지만 서비스 간 네트워크 통신, 데이터 일관성, 장애 추적, 배포 관리가 복잡해진다.

예를 들어 주문 서비스는 성공했는데 결제 서비스가 실패했다면, 전체 상태를 어떻게 정리할지 별도로 설계해야 한다.

**서비스를 분리하면 코드의 경계 일부를 네트워크와 운영의 경계로 바꾸게 된다.** 따라서 분리로 얻는 이익이 추가 복잡성보다 큰지 판단해야 한다.

### 이벤트 기반 아키텍처

어떤 일이 발생했다는 사실을 이벤트로 알리고, 관심 있는 구성 요소가 반응한다.

```
주문확정 이벤트
    ├── 배송 요청
    ├── 알림 발송
    └── 통계 갱신
```

이벤트를 발행하는 쪽은 후속 작업의 세부 구현을 덜 알아도 된다. 새로운 후속 기능을 추가하기에도 유리하다.

반면 전체 처리 흐름이 여러 곳에 흩어질 수 있고, 이벤트 순서와 중복, 실패 복구를 관리해야 한다. 사용자 화면에도 모든 결과가 즉시 반영되지 않을 수 있다.

### 클린 아키텍처와 헥사고날 아키텍처

두 접근은 세부 개념이 다르지만, **핵심 업무 규칙이 데이터베이스나 프레임워크 같은 외부 기술에 강하게 의존하지 않도록 한다**는 방향을 공유한다.

예를 들어 주문 로직이 특정 결제 회사의 API를 직접 사용하는 대신, 다음과 같은 인터페이스에 의존하게 한다.

```
주문 로직 → 결제 인터페이스 ← 결제사 API 어댑터
```

실행할 때는 어댑터가 실제 결제를 수행한다. 코드 의존성은 핵심 로직이 필요로 하는 인터페이스를 중심으로 정리된다.

이렇게 하면 결제사 연동 방식이 바뀌어도 주문 규칙에 미치는 영향을 줄일 수 있다. 다만 단순한 기능에 과도하게 적용하면 추상화와 파일 수만 늘어날 수 있다.

## 실제 예시

사용자가 상품을 주문하는 상황이라고 가정한다.

### 5.1 정상 흐름

1. 사용자가 상품과 수량을 선택하고 주문을 요청한다.
2. 서버가 사용자 권한, 상품 가격, 재고를 확인한다.
3. 결제 대기 상태의 주문을 저장한다.
4. 결제 시스템에 승인을 요청한다.
5. 결제 결과를 확인해 주문 상태를 변경한다.
6. 주문 확정에 따른 배송과 알림 작업을 시작한다.

이 흐름의 세부 순서는 재고 예약 정책이나 결제 방식에 따라 달라질 수 있다.

### 중요한 것은 실패 흐름이다

정상 흐름보다 설계가 어려운 부분은 중간 실패이다.

|상황|필요한 설계|
|---|---|
|사용자가 주문 버튼을 두 번 누름|중복 주문이나 결제를 막는 요청 식별|
|결제 승인 후 서버가 응답을 받지 못함|결제 상태 조회와 결과 대조|
|결제는 성공했지만 주문 상태 저장 실패|복구 작업 또는 취소·환불 처리|
|주문 확정 후 이메일 발송 실패|주문과 분리한 발송 재시도|
|같은 결제 완료 알림이 여러 번 도착|중복 반영을 막는 처리|
|주문 저장 후 이벤트 발행 실패|저장된 주문과 이벤트 전달을 연결하는 복구 방식|

여기서 자주 사용하는 개념이 **멱등성**이다. 같은 요청을 여러 번 처리해도 의도한 효과가 중복 발생하지 않게 만드는 성질이다.

또한 주문 저장과 이벤트 발행 사이의 실패를 줄이기 위해, 주문과 발행할 이벤트 기록을 같은 데이터베이스 트랜잭션에 저장한 뒤 별도 작업이 전달하는 **트랜잭셔널 아웃박스 패턴**을 사용할 수 있다. 이 경우에도 소비자의 중복 처리 방지는 필요하다.

## 좋은 아키텍처를 평가하는 기준

좋은 아키텍처는 특정 기술을 사용했는지가 아니라, 요구되는 품질을 얼마나 충족하는지로 평가한다.

|품질|확인할 질문|
|---|---|
|변경 용이성|기능 하나를 바꿀 때 얼마나 많은 부분을 수정해야 하는가?|
|신뢰성|일부 구성 요소가 실패해도 중요한 기능을 유지할 수 있는가?|
|성능|예상 부하에서 목표 응답 시간을 충족하는가?|
|확장성|부하가 증가할 때 필요한 부분을 확장할 수 있는가?|
|보안|접근 권한과 데이터 보호가 적절한 경계에서 보장되는가?|
|관측 가능성|장애 원인과 요청 흐름을 확인할 수 있는가?|
|운영 용이성|배포, 복구, 백업, 점검을 안정적으로 수행할 수 있는가?|
|비용|개발과 운영에 드는 비용이 얻는 가치에 비례하는가?|

이 기준들은 서로 충돌할 수 있다.

예를 들어 캐시는 응답 속도를 높일 수 있지만 데이터 갱신을 복잡하게 만든다. 서비스를 세분화하면 독립 배포가 쉬워질 수 있지만 운영 비용과 장애 지점이 늘어난다.

따라서 **무엇을 우선하고, 어떤 비용을 감수할지 명시하는 것**이 아키텍처 설계의 핵심이다.

## 아키텍처를 설계하는 순서

### 요구사항을 구체적으로 정리한다

“빠른 서비스”보다 측정 가능한 조건이 필요하다.

예를 들어 다음처럼 정한다.

- 주요 조회 요청의 95%가 300ms 안에 응답해야 한다.
- 결제가 중복 실행되면 안 된다.
- 알림은 주문 완료 후 1분 안에 전달되면 된다.
- 특정 서버가 중단되어도 주문 내역을 조회할 수 있어야 한다.

이런 조건이 있어야 캐시, 비동기 처리, 서버 이중화 등의 필요성을 판단할 수 있다.

### 업무 경계와 데이터 소유권을 정한다

주문, 결제, 배송처럼 서로 다른 규칙을 가진 영역을 구분한다.

각 데이터에 대해서는 **누가 변경할 권한과 책임을 갖는지** 정한다. 여러 모듈이 같은 데이터를 제각각 수정하는 구조는 변경과 장애 분석을 어렵게 만든다.

### 가장 단순한 구조에서 시작한다

필요한 요구사항을 충족하는 구조를 먼저 선택한다.

독립 배포나 서비스별 확장이 꼭 필요하지 않다면, 모듈 경계가 명확한 하나의 애플리케이션으로 시작할 수 있다. 이후 실제 병목이나 조직적 필요가 생기면 분리를 검토한다.

### 데이터 일관성과 실패 처리를 설계한다

정상 처리만 그리지 말고 각 단계에 다음 질문을 적용한다.

- 여기서 실패하면 어떤 상태가 남는가?
- 재시도해도 안전한가?
- 이전 작업을 되돌릴 수 있는가?
- 자동 복구가 불가능하면 누가 어떻게 확인하는가?

### 운영 방법까지 포함한다

로그, 지표, 요청 추적, 배포, 롤백, 백업 복원은 운영 단계에서 덧붙이는 장식이 아니다.

시스템의 실제 상태를 확인하고 복구할 수 있어야 아키텍처가 운영 환경에서도 의미를 가진다.

### 결정 이유를 기록하고 검증한다

구조도와 함께 중요한 결정의 이유를 남긴다.

예를 들어 “알림 발송 지연이 주문 응답에 영향을 주지 않도록 비동기 처리한다”는 기록은, 단순히 “메시지 큐를 사용한다”보다 유용하다.

검증도 위험에 맞춰 수행한다. 성능이 핵심이면 부하를 측정하고, 결제 복구가 핵심이면 타임아웃과 중복 알림 상황을 확인한다.

## 자주 생기는 오해

### “아키텍처는 기술 목록이다”

프레임워크, 데이터베이스, 클라우드 제품 이름은 기술 선택이다. 그 기술들이 어떤 책임을 맡고 어떻게 연결되며 실패 시 어떻게 동작하는지까지 설명해야 아키텍처가 된다.

### “마이크로서비스가 모놀리스보다 발전된 구조다”

두 구조는 서로 다른 비용과 이점을 가진다. 팀의 규모, 배포 방식, 업무 경계, 운영 역량에 따라 적합한 선택이 달라진다.

### “폴더를 나누면 책임도 분리된다”

폴더가 나뉘어 있어도 서로의 내부 데이터를 직접 수정하고 구현 세부사항에 의존한다면 결합도는 여전히 높다.

### “처음부터 미래의 모든 요구사항을 대비해야 한다”

예상만으로 복잡한 구조를 만들면 아직 필요하지 않은 비용을 먼저 지불하게 된다. 현재 요구사항을 충족하면서, 바뀔 가능성이 높은 부분의 경계를 명확히 하는 편이 실용적이다.
