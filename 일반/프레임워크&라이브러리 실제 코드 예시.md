핵심 차이는 “실행 흐름을 누가 주도하느냐”이다.

> 라이브러리: 내 코드가 필요할 때 호출한다.  
> 프레임워크: 프레임워크가 전체 흐름을 관리하면서 내 코드를 호출한다.

## 이 프로젝트에서의 프레임워크

대표적으로 Spring Boot/Spring MVC/Spring Data JPA/Spring Security가 프레임워크 역할을 한다.

### 식물 조회 API 흐름

`GET /plant/{plantId}` 요청이 들어오면 대략 다음과 같이 실행된다.

```
클라이언트 요청
    ↓
Spring Security 필터
    ↓
Spring MVC가 PlantController 메서드 호출
    ↓
QueryPlantService
    ↓
PlantReader
    ↓
Spring Data JPA가 만든 PlantRepository 구현체
    ↓
DB
```

Controller에는 메서드만 작성되어 있다.

```
@GetMapping("/{plantId}")
public PlantResponse getPlant(@PathVariable Long plantId) {
    return queryPlantService.getPlant(plantId);
}
```

개발자가 다음과 같은 코드를 작성하지 않았다는 점이 중요하다.

```
PlantController controller = new PlantController(...);
controller.getPlant(1L);
```

Spring이 하는 작업

- `@RestController`를 발견하고 객체를 생성
- 생성자를 통해 `QueryPlantService` 주입
- `GET /plant/{plantId}` 요청을 메서드에 연결
- `plantId` 문자열을 `Long`으로 변환
- 반환 객체를 JSON으로 변환

Spring이 실행 흐름을 가지고 있다가 우리 메서드를 호출한다. 이를 제어의 역전, IoC(Inversion of Control)라고 한다.

### 가장 선명한 사례: Repository

이 프로젝트의 `PlantRepository`에는 구현 코드가 전혀 없다.

```
public interface PlantRepository extends JpaRepository<Plant, Long> {
}
```

하지만 다음 코드가 정상적으로 동작한다.

```
plantRepository.findById(plantId);
plantRepository.findAll();
plantRepository.count();
```

Spring Data JPA가 애플리케이션 시작 시점에 `PlantRepository`의 구현체를 동적으로 만들고 주입하기 때문이다. 개발자는 프레임워크가 정한 확장 규칙인 `JpaRepository`를 상속하고, 실제 실행은 프레임워크에 맡긴다.

### 트랜잭션과 캐시

`QueryPlantService`에는 다음 선언이 있다.

```
@Transactional(readOnly = true)
@Service
public class QueryPlantService {
```

조회 메서드

```
@Cacheable(value = "plants")
public List<PlantResponse> getPlants() {
```

개발자가 직접 트랜잭션을 시작하거나 Redis 캐시를 확인하지 않는다. Spring이 서비스 앞에 프록시를 만들어 다음과 비슷한 흐름을 자동으로 수행한다.

```
Spring 프록시
 ├─ 트랜잭션 시작
 ├─ 캐시 확인
 ├─ QueryPlantService.getPlants() 호출
 ├─ 캐시 저장
 └─ 트랜잭션 종료
```

이 역시 프레임워크가 내 코드의 호출 전후를 제어하는 사례이다.

## 이 프로젝트에서의 라이브러리

### JJWT

JWT를 생성할 때 애플리케이션 코드가 JJWT API를 직접 호출한다.

```
return Jwts.builder()
        .setSubject(email)
        .claim("userId", userId)
        .claim("authority", authorities)
        .setExpiration(expireDate)
        .signWith(key, SignatureAlgorithm.HS256)
        .compact();
```

애플리케이션 코드의 작업

- 언제 JWT를 만들지 결정
- 어떤 claim을 넣을지 결정
- 어떤 서명 알고리즘을 사용할지 결정
- JJWT의 메서드를 순서대로 호출
- 예외를 어떻게 변환할지 결정

JJWT가 `JwtTokenProvider`를 찾아서 호출하는 것이 아니다. `JwtTokenProvider`가 필요할 때 JJWT를 호출합니다. 따라서 JJWT는 라이브러리이다.

### Apache POI

엑셀 생성도 같은 구조이다.

```
try (XSSFWorkbook workbook = new XSSFWorkbook()) {
    Sheet sheet = workbook.createSheet(sheetName);
    Row headerRow = sheet.createRow(0);
    workbook.write(out);
}
```

`ExcelGenerator`가 워크북을 언제 만들고, 시트와 셀을 어떤 순서로 생성할지 모두 결정한다. Apache POI는 요청받은 엑셀 작업만 수행하므로 라이브러리이다.

실제 호출 흐름은 다음과 같다.

```
Spring MVC
  → PlantAdminController.downloadPlantData()
  → QueryPlantService.downloadData()
  → ExcelGenerator.generate()
  → Apache POI 메서드 호출
```

앞부분의 HTTP 처리와 객체 관리는 Spring 프레임워크가 주도하지만, 마지막 엑셀 파일 생성은 애플리케이션 코드가 Apache POI 라이브러리를 호출한다.

### Lombok

`@RequiredArgsConstructor`도 라이브러리, 더 정확하게는 컴파일 타임 코드 생성 도구이다.

```
@RequiredArgsConstructor
public class PlantController {
    private final QueryPlantService queryPlantService;
}
```

컴파일할 때 Lombok이 다음과 같은 생성자를 만들어준다.

```
public PlantController(QueryPlantService queryPlantService) {
    this.queryPlantService = queryPlantService;
}
```

그렇게 생성된 생성자를 Spring 프레임워크가 사용해서 의존성을 주입한다.

## 둘을 함께 사용할 수도 있다

`ExcelGenerator`는 `@Component`가 붙어 있다.

```
@Component
public class ExcelGenerator {
```

이 경우 역할이 두 층으로 나뉜다.

- `ExcelGenerator` 객체의 생성과 주입: Spring 프레임워크
- 실제 엑셀 처리: Apache POI 라이브러리

JWT 인증

- 요청마다 `JwtFilter`를 실행하는 주체: Spring Security 프레임워크
- JWT 문자열을 생성하고 해석하는 도구: JJWT 라이브러리

JwtFilter.java의 `OncePerRequestFilter`를 상속한다. 개발자는 필터 규칙에 맞춰 `doFilterInternal()`을 구현하고, 실제로 언제 호출할지는 Spring Security가 결정한다.

## 프로젝트 의존성 분류

build.gradle을 기준

|의존성|주된 역할|
|---|---|
|Spring Boot, Spring MVC|애플리케이션 실행 및 HTTP 흐름을 주도하는 프레임워크|
|Spring Data JPA|Repository 구현과 영속성 흐름을 제공하는 프레임워크|
|Spring Security|보안 필터 체인과 인증 흐름을 주도하는 프레임워크|
|JJWT|JWT 생성·파싱 라이브러리|
|Apache POI|엑셀 파일 처리 라이브러리|
|AWS SDK|S3·SES API 호출 라이브러리|
|Lombok|컴파일 타임 코드 생성 라이브러리|
|MySQL Connector/J|JDBC 드라이버 라이브러리|
|`spring-boot-starter-*`|관련 프레임워크와 라이브러리를 묶어주는 의존성 패키지|

최종적으로 이 프로젝트에 적용하면 이렇게 기억할 수 있다.

```
Spring: “규칙에 맞게 코드를 작성해. 적절한 순간에 내가 호출할게.”

JJWT/POI: “필요한 기능이 있으면 네가 내 메서드를 호출해.”
```

다만 기술을 무조건 둘 중 하나로 영구 분류하기보다는, 현재 코드에서 누가 생명주기와 실행 흐름을 소유하는지를 보는 것이 가장 정확하다.
