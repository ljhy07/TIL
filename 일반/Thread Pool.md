# Thread Pool이란?

**Thread Pool(스레드 풀)은 미리 생성했거나 필요에 따라 생성한 스레드를 보관하고, 여러 작업에 재사용하는 실행 관리 방식**이다.

작업이 들어올 때마다 새 스레드를 만들고 종료하는 대신, 일정한 수의 스레드가 작업을 나누어 처리합니다. 이를 통해 **스레드 생성 비용을 줄이고, 동시에 실행되는 작업 수를 제어**할 수 있다.

식당에 비유하면 이해하기 쉽다.

- **작업(Task)**: 손님이 넣은 주문
- **작업 큐(Queue)**: 처리 대기 중인 주문 목록
- **스레드(Thread)**: 주문을 처리하는 직원
- **스레드 풀(Thread Pool)**: 직원과 주문 배분을 관리하는 시스템

주문이 들어올 때마다 직원을 새로 고용하는 대신, 기존 직원이 주문을 하나 끝내고 다음 주문을 처리하는 방식이다.

---

## Thread Pool가 필요한 이유

### 작업마다 스레드를 생성하면 비용이 발생한다

스레드는 단순한 함수 호출보다 생성과 관리에 더 많은 자원이 필요하다.

운영체제가 관리하는 일반적인 스레드를 기준으로 보면 다음 비용이 발생한다.

- 스레드 생성과 종료에 드는 처리 비용
- 스레드별 스택 등 메모리 사용
- 운영체제의 스케줄링 비용
- 여러 스레드 사이를 전환하는 **컨텍스트 스위칭 비용**

예를 들어 서버가 요청을 받을 때마다 새 스레드를 생성한다고 가정해 본다.

```
요청 1 → 스레드 생성 → 요청 처리 → 스레드 종료
요청 2 → 스레드 생성 → 요청 처리 → 스레드 종료
요청 3 → 스레드 생성 → 요청 처리 → 스레드 종료
```

요청이 적으면 큰 문제가 없을 수 있다. 하지만 요청이 급증하면 스레드 생성 자체가 부담이 되고, 메모리와 CPU 사용량도 통제하기 어려워진다.

스레드 풀을 사용하면 같은 스레드를 재사용한다.

```
스레드 A → 요청 1 처리 → 요청 4 처리 → 요청 7 처리
스레드 B → 요청 2 처리 → 요청 5 처리 → 요청 8 처리
스레드 C → 요청 3 처리 → 요청 6 처리 → 요청 9 처리
```

**작업이 끝나도 스레드가 바로 사라지지 않고 다음 작업을 맡는 것**이 핵심이다.

### 동시에 처리하는 작업 수를 제한할 수 있다

스레드 풀이 중요한 또 다른 이유는 **자원 사용량을 제어할 수 있기 때문**이다.

예를 들어 작업이 10,000개 들어와도 작업 스레드를 20개로 제한하면, 해당 풀에서는 최대 20개 작업이 동시에 실행된다. 나머지는 큐에서 기다리거나, 설정된 정책에 따라 거절된다.

이는 CPU와 메모리뿐 아니라 데이터베이스나 외부 API에 과도한 요청이 전달되는 것도 줄여 준다.

단, **스레드 수만 제한하고 대기 큐를 무제한으로 두면 메모리 사용량까지 제한되는 것은 아니다.**

## Thread Pool의 주요 구성 요소

|구성 요소|역할|
|---|---|
|작업(Task)|실행할 함수나 연산 단위|
|작업 스레드(Worker Thread)|큐에서 작업을 가져와 실행하는 스레드|
|작업 큐(Task Queue)|즉시 실행하지 못한 작업을 보관하는 공간|
|풀 관리 로직|스레드 생성·유지·축소와 작업 배분을 관리|
|포화 처리 정책|더 이상 작업을 수용할 수 없을 때의 동작을 결정|
|결과 전달 수단|작업 결과나 예외를 호출자에게 전달. 보통 `Future` 등을 사용|

여기서 **작업과 스레드는 서로 다른 개념**이다.

작업은 “무엇을 실행할 것인가”이고, 스레드는 “그 작업을 실행하는 흐름”이다. 하나의 스레드가 시간 순서대로 여러 작업을 처리할 수 있다.

## Thread Pool의 동작

작업 스레드가 3개 있는 풀을 예로 들어 본다.

### ① 작업을 제출한다

호출자는 실행할 작업을 풀에 전달한다.

```
작업 제출: A, B, C, D, E
```

### ② 사용 가능한 스레드가 작업을 실행한다

처음에는 3개 스레드가 각각 작업을 맡는다.

```
스레드 1: A 실행 중
스레드 2: B 실행 중
스레드 3: C 실행 중

대기 큐: [D, E]
```

### ③ 작업을 끝낸 스레드가 다음 작업을 가져온다

스레드 2가 B를 먼저 끝내면 D를 가져온다.

```
스레드 1: A 실행 중
스레드 2: D 실행 중
스레드 3: C 실행 중

대기 큐: [E]
```

작업을 끝낸 스레드는 일반적으로 큐에서 다음 작업을 기다린다. 구현과 설정에 따라 유휴 시간이 긴 스레드를 종료하기도 한다.

> **제출 순서와 완료 순서는 다를 수 있다.**  
> A를 B보다 먼저 제출했더라도 B의 실행 시간이 짧으면 B가 먼저 끝날 수 있다.

큐가 FIFO라고 해도, 여러 스레드가 실행하므로 작업의 완료 순서까지 보장하지는 않다.

## 동시성과 병렬성 차이

스레드 풀을 이해할 때 자주 혼동하는 개념이다.

### 동시성: 여러 작업을 진행 중인 상태로 관리한다

CPU 코어가 하나여도 운영체제가 스레드들을 번갈아 실행하면 여러 작업이 동시에 진행되는 것처럼 동작한다.

예를 들어 한 작업이 네트워크 응답을 기다리는 동안 다른 작업을 처리할 수 있다.

### 병렬성: 여러 작업을 실제로 같은 시점에 실행한다

여러 CPU 코어에서 각각의 작업이 같은 시점에 실행되는 경우이다.

**스레드가 많다고 그만큼 CPU 연산이 병렬로 실행되는 것은 아니다.** 실제 병렬 실행 가능성은 CPU 코어 수와 언어 런타임의 제약 등에 영향을 받는다.

## 스레드 풀의 크기

적절한 스레드 수는 작업의 특성에 따라 달라진다.

### CPU 중심 작업: CPU 처리량이 기준

CPU-bound 작업은 실행 시간 대부분을 계산에 사용하는 작업이다.

예시는 다음과 같다.

- 이미지 변환
- 데이터 압축
- 암호화 연산
- 대규모 수치 계산

이런 작업은 이미 CPU를 충분히 사용하고 있다면 스레드를 더 늘려도 처리량이 크게 늘지 않는다. 오히려 컨텍스트 스위칭과 자원 경합 때문에 성능이 나빠질 수 있다.

**런타임에서 CPU 병렬 실행이 가능하다는 전제하에, 사용할 수 있는 CPU 코어 수 근처를 출발점으로 잡고 측정**하는 방식이 일반적이다.

작업 내부에서 별도로 병렬 처리를 하거나, 다른 서비스와 CPU를 공유한다면 그 영향도 고려해야 한다.

### I/O 중심 작업: 대기 시간이 기준

I/O-bound 작업은 외부 자원의 응답을 기다리는 시간이 큰 작업이다.

예시는 다음과 같다.

- 데이터베이스 조회
- 외부 API 호출
- 파일 읽기·쓰기
- 네트워크 통신

**블로킹 I/O 방식**에서는 한 스레드가 응답을 기다리는 동안 다른 스레드가 작업할 수 있으므로, CPU 코어 수보다 많은 스레드가 도움이 될 수 있다.

대략적인 출발점으로 다음 관계를 사용하기도 한다.

```
스레드 수 ≈ CPU 코어 수 × 목표 CPU 이용률 × (1 + 대기 시간 / CPU 계산 시간)
```

예를 들어 다음 조건이라면:

```
CPU 코어 수: 8
목표 CPU 이용률: 1.0
작업당 CPU 계산 시간: 10ms
작업당 대기 시간: 90ms

추정 스레드 수 ≈ 8 × 1.0 × (1 + 90 / 10)
              ≈ 80
```

하지만 이는 **이상적인 조건에서의 추정치**이다. 데이터베이스 연결 수, 외부 서비스의 처리 한도, 메모리 사용량 등을 함께 고려해야 한다.

비동기 I/O처럼 대기 중인 작업이 스레드를 계속 점유하지 않는 방식에는 이 계산을 그대로 적용하면 안 된다.

---

## 대기 큐가 중요한 이유

스레드 수를 정하는 것만큼 **큐의 크기를 정하는 것**도 중요하다.

### 무제한 큐

작업을 사실상 제한 없이 쌓아 두는 방식이다.

구현은 단순하지만, 작업 유입 속도가 처리 속도보다 계속 빠르면 다음 문제가 발생한다.

- 대기 작업이 메모리를 차지한다.
- 사용자가 응답을 받기까지 시간이 계속 늘어난다.
- 이미 타임아웃된 요청의 작업을 뒤늦게 처리할 수 있다.
- 심한 경우 메모리 부족으로 장애가 발생한다.

### 제한된 큐

큐에 들어갈 수 있는 작업 수를 제한하는 방식이다.

예를 들어 작업 스레드가 10개이고 큐 용량이 100이면, 일반적인 고정 크기 풀에서는 실행 중인 10개와 대기 중인 100개까지 수용할 수 있다.

이를 초과한 작업은 정책에 따라 처리한다.

|정책|동작|주의점|
|---|---|---|
|즉시 거절|제출을 실패 처리한다|호출자가 실패에 대응해야 한다|
|호출자 실행|제출한 스레드가 직접 작업한다|호출자도 느려지며, 이벤트 루프 등에는 부적절할 수 있다|
|제출 대기|큐에 자리가 생길 때까지 기다린다|제출 측까지 정체될 수 있다|
|작업 폐기|새 작업이나 대기 작업을 버린다|유실을 허용하는 작업에만 적합하다|

이처럼 처리 용량을 초과한 유입을 늦추거나 제한하는 것을 **백프레셔(Backpressure)**라고 한다.

**큐는 순간적인 작업 증가를 흡수할 수 있지만, 지속적인 처리 용량 부족을 해결하지는 못한다.**

## Thread Pool을 써도 발생하는 문제들

### 공유 데이터의 경쟁 상태

스레드 풀은 여러 스레드가 공유 데이터에 동시에 접근하는 문제를 해결해 주지 않는다.

```
스레드 A: 공유 카운터 읽기 → 증가 → 저장
스레드 B: 공유 카운터 읽기 → 증가 → 저장
```

두 스레드가 같은 값을 읽으면 증가 결과 하나가 사라질 수 있다. 이러한 문제에는 락, 원자적 연산, 불변 데이터 등의 별도 설계가 필요하다.

### 같은 풀의 작업을 기다리다가 멈추는 문제

크기가 2인 풀에서 A와 B가 실행 중이라고 가정해 본다.

```
스레드 1: A 실행 → 같은 풀에 C 제출 → C 완료 대기
스레드 2: B 실행 → 같은 풀에 D 제출 → D 완료 대기

대기 큐: [C, D]
```

A와 B가 두 스레드를 모두 차지한 상태로 기다리면 C와 D를 실행할 스레드가 없다.

일반적인 고정 크기 풀에서는 이런 구조가 **스레드 고갈에 의한 교착 상태**를 일으킬 수 있다. 같은 풀에 제출한 하위 작업을 동기적으로 기다리는 설계는 주의해야 한다.

### 느린 작업이 다른 작업까지 지연시키는 문제

빠른 작업과 느린 작업을 하나의 풀에서 처리하면 느린 작업이 스레드를 모두 점유할 수 있다.

예를 들어 외부 API가 느려졌을 때, 같은 풀의 간단한 내부 작업까지 대기하게 된다.

작업 특성이나 중요도에 따라 풀을 분리하면 이런 영향을 줄일 수 있다. 다만 풀을 너무 많이 만들면 전체 스레드 수가 과도해질 수 있다.

### 스레드에 남은 상태가 다음 작업에 영향을 주는 문제

스레드를 재사용하므로 `ThreadLocal` 같은 스레드별 저장소에 넣은 값이 다음 작업에도 남을 수 있다.

요청 ID, 사용자 정보, 로그 컨텍스트 등을 설정했다면 작업 종료 시 정리하거나 적절하게 교체해야 한다.

## 결과, 예외, 타임아웃

스레드 풀에 작업을 제출하는 것과 작업이 성공하는 것은 별개이다.

많은 구현에서는 `Future` 같은 객체를 통해 결과를 받는다.

```
작업 제출 → Future 반환
             ↓
       작업 완료 후 결과 또는 예외 확인
```

사용할 때는 다음을 구분해야 한다.

- **제출 성공**: 풀이 작업을 받아들였다.
- **실행 완료**: 작업이 끝났다.
- **실행 성공**: 작업이 예외 없이 원하는 결과를 만들었다.

또한 **결과를 기다리다 타임아웃됐다고 실행 중인 작업이 자동으로 중단되는 것은 아니다.** 취소 요청이 실제 실행을 멈추는지도 구현과 작업의 취소 처리 방식에 따라 달라진다.

작업 결과를 확인하지 않으면 예외를 놓칠 수 있으므로, 실패를 관찰하고 기록하는 경로도 필요하다.

## 올바른 종료와 운영 지표

### 종료할 때는 대기 작업과 실행 중인 작업을 구분한다

일반적인 정상 종료 절차는 다음과 같다.

1. 새 작업의 제출을 중단한다.
2. 실행 중인 작업과 필요한 대기 작업의 완료를 기다린다.
3. 정해진 종료 시간을 넘기면 정책에 따라 취소를 요청한다.
4. 스레드와 관련 자원을 정리한다.

스레드를 즉시 강제로 종료하는 것은 안전하지 않을 수 있으며, 많은 환경에서는 작업이 취소에 협조하도록 설계해야 합니다.

### 운영 중에는 처리 시간뿐 아니라 대기 시간을 본다

특히 유용한 지표는 다음과 같다.

|지표|확인할 수 있는 문제|
|---|---|
|활성 스레드 수|풀의 실행 용량이 얼마나 사용되는지|
|대기 큐 길이|작업이 처리되지 못하고 쌓이는지|
|큐 대기 시간|실행을 시작하기까지 얼마나 지연되는지|
|작업 실행 시간|작업 자체나 외부 의존성이 느려졌는지|
|거절·타임아웃 건수|현재 용량을 초과하는 요청이 발생하는지|

사용자가 체감하는 시간에는 **큐에서 기다린 시간도 포함**된다.

```
응답 시간 ≈ 큐 대기 시간 + 작업 실행 시간 + 기타 처리 시간
```

작업 실행이 100ms여도 큐에서 5초를 기다리면 사용자에게는 느린 서비스이다.

## Thread Pool의 핵심

**Thread Pool의 핵심은 스레드를 재사용하면서 실행 용량을 관리하는 것이다.**

잘 설계하려면 세 가지를 함께 결정해야 한다.

- **몇 개를 동시에 실행할 것인가?** → 스레드 수
- **몇 개까지 기다리게 할 것인가?** → 큐 용량
- **더 이상 수용할 수 없으면 어떻게 할 것인가?** → 포화 처리 정책

스레드 수를 무조건 늘리기보다 작업의 CPU 사용량, I/O 대기 시간, 외부 시스템의 한도를 측정하고 이 세 가지를 함께 조정해야 한다.
