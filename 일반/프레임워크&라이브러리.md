## 요약

- 라이브러리: 개발자가 필요할 때 호출한다.
- 프레임워크: 프레임워크가 전체 구조와 실행 흐름을 관리하고, 개발자가 지정된 부분을 채운다.

## 라이브러리

라이브러리(Library)는 특정 기능을 재사용할 수 있도록 함수, 클래스, 모듈 등을 묶어 놓은 도구이다.

예를 들어 날짜 계산 라이브러리를 사용한다면 다음처럼 개발자가 직접 호출한다.

```
import dayjs from "dayjs";

const formattedDate = dayjs().format("YYYY-MM-DD");
```

여기서 중요한 점은 다음과 같다.

1. 프로그램의 시작점을 개발자가 작성한다.
2. 언제 라이브러리를 호출할지 개발자가 결정한다.
3. 라이브러리는 요청받은 기능을 수행하고 결과를 반환한다.
4. 사용하지 않아도 프로그램의 전체 구조는 유지된다.

대표적인 라이브러리의 예는 다음과 같다.

- React: 사용자 인터페이스 구성
- NumPy: Python 수치 계산
- pandas: 데이터 분석
- Lodash: JavaScript 데이터 처리
- Axios: HTTP 통신
- Requests: Python HTTP 통신

React는 실무에서 프레임워크처럼 활용되기도 하지만, 공식적으로는 UI 라이브러리이다. 라우팅, 데이터 요청, 빌드 방식 같은 애플리케이션 전체 구조를 React 자체가 모두 결정하지 않기 때문이다.

## 프레임워크

프레임워크(Framework)는 애플리케이션의 기본 구조, 실행 순서, 규칙을 제공하는 개발 환경이다.

예를 들어 Spring Boot에서는 개발자가 컨트롤러를 작성하지만, 해당 컨트롤러 객체를 생성하고 HTTP 요청과 연결해 호출하는 일은 프레임워크가 담당한다.

```
@RestController
public class UserController {

    @GetMapping("/users")
    public List<User> getUsers() {
        return List.of(new User("Kim"));
    }
}
```

개발자가 `getUsers()`를 직접 호출하지 않아도 요청이 들어오면 Spring이 호출한다.

프레임워크는 일반적으로 다음 기능을 제공한다.

- 프로젝트 디렉터리 구조
- 애플리케이션 시작과 종료
- 요청 처리 흐름
- 객체 생성과 의존성 관리
- 설정과 환경 관리
- 확장 지점과 플러그인 구조
- 오류 처리
- 보안, 로깅, 테스트 지원

대표적인 프레임워크에는 다음이 있다.

- Spring Boot: Java 백엔드
- Django: Python 웹 개발
- Ruby on Rails: Ruby 웹 개발
- Angular: 프런트엔드 애플리케이션
- Laravel: PHP 웹 개발
- .NET의 ASP.NET Core: 웹과 API 개발
- Flutter: 크로스 플랫폼 애플리케이션

## 핵심 비교

|구분|라이브러리|프레임워크|
|---|---|---|
|주도권|개발자|프레임워크|
|호출 관계|개발자가 라이브러리를 호출|프레임워크가 개발자 코드를 호출|
|제공 범위|특정 기능 중심|애플리케이션 전체 구조 중심|
|규칙과 제약|비교적 적음|비교적 많음|
|자유도|높음|상대적으로 낮음|
|초기 개발 속도|조합과 설계가 필요|기본 구조 덕분에 빠를 수 있음|
|교체 난이도|보통 비교적 낮음|애플리케이션 구조와 결합되어 높음|
|학습 대상|주로 API 사용법|구조, 생명주기, 규칙, 확장 방식|
|대표 사례|Axios, NumPy, pandas|Spring Boot, Django, Angular|

## 제어의 역전

프레임워크와 라이브러리의 차이를 설명할 때 가장 중요한 개념이 **제어의 역전(Inversion of Control, IoC)**이다.

라이브러리를 사용하는 일반적인 흐름은 다음과 같다.

```
내 코드 → 라이브러리 호출 → 결과 반환 → 내 코드 계속 실행
```

프레임워크를 사용하는 흐름은 다음과 같다.

```
프레임워크 실행
    → 요청이나 이벤트 감지
    → 내가 작성한 코드 호출
    → 결과 처리
```

즉, 일반적인 코드에서는 개발자가 전체 흐름을 제어하지만, 프레임워크를 사용하면 프레임워크가 흐름을 제어하고 개발자의 코드를 필요한 시점에 호출한다.

## 프레임워크의 장단점

### 장점
- 프로젝트 구조가 표준화된다.
- 반복적인 기반 코드를 줄일 수 있다.
- 여러 개발자가 일관된 방식으로 협업하기 쉽다.
- 보안, 로깅, 테스트 등 공통 기능이 통합되어 있다.
- 권장 방식이 존재하므로 큰 프로젝트를 관리하기 좋다.

### 단점
- 프레임워크의 규칙과 생명주기를 학습해야 한다.
- 내부 동작을 모르면 문제가 발생했을 때 원인을 찾기 어렵다.
- 특정 프레임워크에 대한 의존성이 커질 수 있다.
- 정해진 방식과 맞지 않는 요구사항에서는 오히려 복잡해질 수 있다.
- 프레임워크를 교체하려면 애플리케이션을 크게 수정해야 할 수 있다.

## 라이브러리의 장단점

### 장점
- 필요한 기능만 선택해서 사용할 수 있다.
- 개발자가 아키텍처와 실행 흐름을 직접 결정할 수 있다.
- 일반적으로 도입과 제거가 비교적 쉽다.
- 작은 프로그램이나 특수한 구조에 유연하게 대응할 수 있다.

### 단점
- 여러 라이브러리를 직접 조합해야 할 수 있다.
- 프로젝트 구조와 규칙을 개발팀이 정해야 한다.
- 라이브러리 사이의 호환성을 관리해야 한다.
- 선택지가 많아 기술 결정에 시간이 걸릴 수 있다.
- 일관된 기준이 없으면 프로젝트 구조가 복잡해질 수 있다.

## 경계

라이브러리와 프레임워크는 완전히 배타적인 분류가 아닙니다. 사용 방식이나 생태계에 따라 경계가 흐려진다.

### React와 Next.js

- React는 UI를 만들기 위한 라이브러리이다.
- Next.js는 React를 기반으로 라우팅, 렌더링, 빌드, 서버 기능 등을 제공하는 프레임워크이다.

```
Next.js 프레임워크
└── React 라이브러리
```

React만 사용하면 라우터나 빌드 환경 등을 직접 선택할 수 있다. Next.js를 사용하면 파일 구조, 라우팅, 서버 렌더링 방식 등에 프레임워크의 규칙이 적용된다.

### Flask와 Django

둘 다 Python 웹 개발에 사용되지만 성격이 다르다.

- Flask: 필요한 기능을 조합하는 경량 프레임워크
- Django: ORM, 관리자 화면, 인증 등 많은 기능을 포함한 종합 프레임워크

Flask도 기술적으로는 프레임워크이지만 라이브러리처럼 작고 유연하게 느껴질 수 있다.

## 프레임워크와 라이브러리 선택 기준

### 프레임워크
- 애플리케이션의 전체 구조가 필요할 때
- 팀 단위로 장기간 개발할 때
- 표준적인 웹 애플리케이션을 빠르게 만들 때
- 인증, 보안, 데이터베이스 등 통합 기능이 필요할 때
- 일관성과 유지보수성이 중요한 경우

### 라이브러리
- 특정 기능만 추가할 때
- 기존 프로젝트 구조를 유지해야 할 때
- 실행 흐름과 아키텍처를 세밀하게 통제해야 할 때
- 규모가 작거나 실험적인 프로그램을 만들 때
- 프레임워크가 제공하는 구조와 요구사항이 크게 다를 때

실무에서는 둘 중 하나만 사용하는 것이 아니라, 일반적으로 **프레임워크 위에서 여러 라이브러리를 함께 사용**한다.

예를 들면 다음과 같습니다.

```
Spring Boot 프레임워크
├── Jackson JSON 라이브러리
├── Logback 로깅 라이브러리
└── 데이터베이스 드라이버

Next.js 프레임워크
├── React 라이브러리
├── Zod 검증 라이브러리
└── Axios 통신 라이브러리
```
