## RBAC

RBAC(Role-Based Access Control, 역할 기반 접근 제어)는 **사용자에게 권한을 직접 부여하지 않고, 역할(Role)에 권한을 묶은 뒤 사용자를 역할에 배정하는 방식**이다.

```
사용자(User) → 역할(Role) → 권한(Permission) → 리소스(Resource)
```

예를 들어 쇼핑몰 관리자 시스템이 있다면:

- `고객지원 담당자`: 주문 조회, 환불 요청 접수
- `물류 담당자`: 배송 상태 변경
- `회계 담당자`: 결제 내역 조회, 환불 승인
- `시스템 관리자`: 사용자와 역할 관리

직원 A에게 `주문 조회`, `환불 요청 접수` 권한을 각각 부여하는 대신 `고객지원 담당자` 역할을 부여한다.

---

## 핵심 구성 요소

### 1. 사용자(User)

시스템에 접근하는 주체이다.

- 직원
- 고객
- 운영자
- 외부 파트너
- 서비스 계정
- 애플리케이션

### 2. 역할(Role)

업무 책임이나 직무를 나타내는 권한 집합이다.

예:

- `viewer`
- `editor`
- `billing_manager`
- `security_admin`

역할은 단순히 직급을 의미하지 않는다. 같은 팀장이라도 회계 시스템과 개발 시스템에서 필요한 역할은 다를 수 있다.

### 3. 권한(Permission)

특정 리소스에 특정 작업을 수행할 수 있는 능력입니다. 보통 다음과 같이 표현한다.

```
resource:action
```

예:

```
order:read
order:update
payment:refund
user:create
role:assign
```

### 4. 리소스(Resource)

접근 제어의 대상이다.

- 주문
- 문서
- 프로젝트
- 서버
- 데이터베이스
- 사용자 계정
- API 엔드포인트

### 5. 세션(Session)

사용자가 로그인한 뒤 실제로 활성화한 역할과 권한의 범위이다. 사용자가 여러 역할을 가지고 있더라도 특정 세션에서는 일부 역할만 활성화할 수 있다.

## 권한 확인 과정

사용자가 주문 환불을 요청하면 시스템은 대략 다음 순서로 판단한다.

```
1. 사용자가 인증되었는가?
2. 사용자에게 어떤 역할이 배정되어 있는가?
3. 해당 역할에 payment:refund 권한이 있는가?
4. 추가 제약 조건을 만족하는가?
5. 허용 또는 거부
```

의사 코드는 다음과 같다.

```
function can(user, action, resource) {
  const roles = getRoles(user);
  const permissions = getPermissions(roles);

  return permissions.some(
    permission =>
      permission.action === action &&
      permission.resource === resource.type
  );
}
```

여기서 중요한 차이는 다음과 같다.

- **인증(Authentication)**: 누구인가?
- **인가(Authorization)**: 무엇을 할 수 있는가?

RBAC는 주로 인가를 담당한다.

## 구체적인 예시

문서 관리 시스템

|역할|문서 조회|문서 작성|문서 삭제|역할 관리|
|---|---|---|---|---|
|Viewer|O|X|X|X|
|Editor|O|O|X|X|
|Manager|O|O|O|X|
|Admin|O|O|O|O|

사용자 배정

|사용자|역할|
|---|---|
|민수|Viewer|
|지영|Editor|
|수현|Manager|
|철수|Admin|

지영은 `Editor` 역할을 가지므로 문서를 읽고 작성할 수 있지만 삭제할 수는 없다. 이후 직무가 변경되면 개별 권한을 하나씩 수정하지 않고 역할만 교체할 수 있다.

## 역할 계층 구조

상위 역할이 하위 역할의 권한을 상속하게 만들 수 있다.

```
Admin
  └── Manager
        └── Editor
              └── Viewer
```

이에 따라:

- `Viewer`: 조회
- `Editor`: 조회 + 작성
- `Manager`: 조회 + 작성 + 삭제
- `Admin`: 모든 권한 + 역할 관리

역할 계층은 중복을 줄여주지만 너무 깊어지면 실제 권한을 파악하기 어려워진다. 일반적으로 얕고 명시적인 구조가 관리하기 쉽다.

## 직무 분리

RBAC의 중요한 목적 중 하나는 한 사람이 위험한 업무 전체를 수행하지 못하게 하는 것이다.

예를 들어:

- `환불 요청자`
- `환불 승인자`

두 역할을 한 사용자에게 동시에 부여하지 않으면, 본인이 만든 환불 요청을 본인이 승인하는 것을 방지할 수 있다.

### 정적 직무 분리

서로 충돌하는 역할을 애초에 동시에 보유하지 못하게 한다.

```
환불 요청자 + 환불 승인자 → 배정 금지
```

### 동적 직무 분리

두 역할을 모두 보유할 수는 있지만 같은 세션이나 같은 거래에서는 동시에 사용하지 못하게 한다.

```
요청을 생성한 사용자는 같은 요청을 승인할 수 없음
```

정적 분리는 단순하고 강력하며, 동적 분리는 유연하지만 구현과 감사가 더 복잡하다.

## 표준적인 RBAC 모델

RBAC는 일반적으로 네 단계로 구분할 수 있다.

### Core RBAC

가장 기본적인 형태다.

```
사용자 ↔ 역할 ↔ 권한
```

### Hierarchical RBAC

역할 간 상속 관계가 있다.

```
관리자 역할이 일반 사용자 역할의 권한을 상속
```

### Static Separation of Duty

충돌하는 역할을 동시에 배정하지 못하게 한다.

### Dynamic Separation of Duty

상황이나 세션에 따라 충돌 역할의 동시 사용을 제한한다.

## 데이터베이스 구조 예시

일반적인 관계형 데이터베이스에서는 다대다 관계로 구성한다.

```
users
- id
- name

roles
- id
- name

permissions
- id
- resource
- action

user_roles
- user_id
- role_id

role_permissions
- role_id
- permission_id
```

역할 계층이 필요하면 다음 테이블을 추가할 수 있다.

```
role_hierarchy
- parent_role_id
- child_role_id
```

테넌트별 권한이 필요하면 사용자 역할에 범위를 포함할 수 있다.

```
user_roles
- user_id
- role_id
- tenant_id
```

이 경우 동일한 사용자가 A 회사에서는 `admin`, B 회사에서는 `viewer`일 수 있다.

## 역할과 권한의 설계 원칙

### 최소 권한 원칙

사용자에게 업무 수행에 필요한 최소 권한만 부여한다.

좋지 않은 방식:

```
문제가 생기면 일단 admin 부여
```

권장 방식:

```
필요한 작업을 확인하고 최소 역할을 임시 또는 영구 부여
```

### 기본 거부

명시적으로 허용되지 않은 작업은 거부해야 한다.

```
권한이 확인됨 → 허용
그 외 모든 경우 → 거부
```

### 권한 이름을 구체적으로 정의

모호한 권한

```
manage_orders
```

명확한 권한

```
order:read
order:create
order:update
order:cancel
order:refund
```

다만 너무 세분화하면 관리가 복잡해집니다. 실제 보안 경계와 업무 단위를 기준으로 나누는 것이 좋다.

### 역할을 사람 기준으로 만들지 않기

좋지 않은 예:

```
김대리_권한
박팀장_특수권한
```

권장 예:

```
customer_support_agent
customer_support_manager
refund_approver
```

역할은 특정 개인이 아니라 반복 가능한 업무 책임을 나타내야 한다.

## 범위를 포함한 RBAC

단순 RBAC는 “무엇을 할 수 있는가”는 표현하지만 “어느 범위에서 할 수 있는가”를 표현하기 어렵다.

예를 들어 프로젝트 관리자는 자신이 담당하는 프로젝트만 수정해야 한다.

```
사용자: 민수
역할: project_admin
범위: project-123
```

권한 판단은 다음과 같다.

```
민수는 project_admin인가?
그리고 요청한 프로젝트가 project-123인가?
```

이를 보통 Scoped RBAC 또는 Tenant-aware RBAC라고 부른다. SaaS와 멀티테넌트 시스템에서는 범위 검사가 특히 중요하다. 역할만 확인하고 `tenant_id` 또는 `organization_id` 검사를 빠뜨리면 다른 고객의 데이터에 접근하는 심각한 취약점이 생길 수 있다.

---

## RBAC의 장점

- 사용자마다 권한을 개별 관리하는 것보다 단순하다.
- 입사, 이동, 퇴사에 따른 권한 변경이 쉽다.
- 최소 권한 원칙을 적용하기 좋다.
- 직무 분리와 내부 통제를 구현할 수 있다.
- 감사 시 누가 어떤 권한을 가졌는지 설명하기 쉽다.
- 조직의 직무 체계와 자연스럽게 연결된다.

---

## 단점과 한계

### 역할 폭증

부서, 지역, 프로젝트, 직급을 모두 역할로 표현하면 역할 수가 급격히 증가한다.

```
서울_영업_팀장
부산_영업_팀장
서울_영업_일반
부산_영업_일반
...
```

이를 `Role Explosion`이라고 한다.

### 상황별 조건 표현이 어려움

다음과 같은 정책은 순수 RBAC만으로 표현하기 어렵다.

- 업무 시간에만 허용
- 본인이 작성한 문서만 수정
- 같은 부서의 데이터만 조회
- 1억 원 미만 결제만 승인
- 회사 관리 기기에서만 접근
- 특정 국가에서의 접속 차단

이런 조건은 ABAC나 별도 정책 엔진과 결합하는 것이 적절하다.

### 역할이 실제 조직과 불일치할 수 있음

역할을 계속 추가하고 제거하지 않으면 시간이 지나면서 사용자의 실제 직무보다 훨씬 많은 권한이 남게 된다. 이를 권한 누적 또는 Permission Creep이라고 한다.

## RBAC, ACL, ABAC, ReBAC 비교

|방식|판단 기준|적합한 사례|
|---|---|---|
|ACL|리소스별 사용자 권한 목록|파일 공유, 개별 문서 공유|
|RBAC|사용자의 역할|기업 업무 시스템, 관리자 콘솔|
|ABAC|사용자·리소스·환경 속성|복잡한 조건부 정책|
|ReBAC|사용자와 리소스의 관계|소셜 서비스, 협업 시스템|

### ACL

각 문서에 접근 가능한 사용자를 직접 기록한다.

```
document-1:
- 민수: read
- 지영: edit
```

개별 공유에는 좋지만 사용자가 많아지면 관리가 어렵다.

### ABAC

속성을 이용해 판단한다.

```
user.department == document.department
AND user.level >= document.required_level
AND current_time within business_hours
```

유연하지만 정책 이해와 디버깅이 어렵다.

### ReBAC

관계를 기준으로 판단한다.

```
사용자가 문서의 소유자다
사용자가 소유자의 팀원이다
사용자가 프로젝트 구성원이다
```

Google Drive나 소셜 네트워크처럼 관계 중심 서비스에 적합하다.

실무에서는 하나만 고집하기보다 함께 사용하는 경우가 많다.

```
RBAC: 사용자가 editor 역할인가?
ABAC: 같은 조직에 속하는가?
ReBAC: 해당 프로젝트의 구성원인가?
```

## 구현할 때 자주 발생하는 문제

### 프런트엔드에서만 권한 검사

버튼을 숨기는 것은 사용자 경험을 위한 조치일 뿐 보안 통제가 아니다. API 서버에서도 반드시 권한을 검사해야 한다.

### URL이나 요청 값을 신뢰

```
GET /organizations/another-company/orders
```

사용자가 `organization_id`를 바꿔 요청할 수 있으므로 서버가 실제 소속 범위를 확인해야 한다.

### 관리자 역할을 지나치게 광범위하게 사용

`admin` 하나로 모든 권한을 해결하면 계정 침해 시 피해 범위가 커진다. 운영 관리자, 결제 관리자, 보안 관리자 등을 분리하는 것이 좋다.

### 역할 변경 후 기존 세션 유지

권한을 회수해도 오래된 토큰에 기존 역할이 남아 있을 수 있다. 중요한 변경에서는 세션 무효화, 짧은 토큰 수명 또는 실시간 권한 재확인이 필요하다.

### 거부 정책과 허용 정책의 충돌

가능하면 기본 거부와 명시적 허용을 중심으로 설계하는 것이 좋다. 여러 단계의 `allow`와 `deny`가 혼합되면 우선순위를 명확하게 정의해야 한다.

## 운영 시 필요한 관리 절차

RBAC는 코드뿐 아니라 지속적인 운영이 중요하다.

- 입사 시 직무에 맞는 기본 역할 부여
- 부서 이동 시 기존 역할 제거 후 신규 역할 부여
- 퇴사 시 계정과 세션 즉시 비활성화
- 고위험 역할은 승인 절차 적용
- 임시 권한에는 만료 시간 설정
- 역할 및 권한 변경 이력 기록
- 정기적인 접근 권한 검토
- 사용되지 않는 역할과 권한 제거
- 서비스 계정 권한 별도 관리
- 고위험 작업에 다중 승인 적용

감사 로그에는 최소한 다음 정보가 필요한다.

```
누가
언제
어떤 역할로
어떤 리소스에
무슨 작업을 요청했고
허용 또는 거부되었는지
```
