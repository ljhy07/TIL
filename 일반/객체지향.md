## 객체란

객체는 프로그램 안에서 **상태와 행동을 가진 하나의 단위**이다.

예를 들어 은행 계좌를 객체로 표현하면 다음과 같다.

| 구분  | 계좌의 예               |
| --- | ------------------- |
| 상태  | 계좌번호, 소유자, 잔액       |
| 행동  | 입금하기, 출금하기, 잔액 조회하기 |

여기서 상태는 데이터이고, 행동은 그 데이터를 사용하거나 변경하는 기능이다.

```
class BankAccount:
    def __init__(self, owner, balance=0):
        if balance < 0:
            raise ValueError("초기 잔액은 음수일 수 없습니다.")

        self.owner = owner
        self._balance = balance

    def deposit(self, amount):
        if amount <= 0:
            raise ValueError("입금액은 0보다 커야 합니다.")

        self._balance += amount

    def withdraw(self, amount):
        if amount <= 0:
            raise ValueError("출금액은 0보다 커야 합니다.")

        if amount > self._balance:
            raise ValueError("잔액이 부족합니다.")

        self._balance -= amount

    @property
    def balance(self):
        return self._balance
```

이 객체는 잔액을 저장하는 데서 끝나지 않는다. 입금액이 양수인지, 출금할 잔액이 충분한지 확인하는 **계좌의 규칙**도 함께 담당한다.

즉, 객체는 **관련 데이터와 그 데이터에 대한 책임을 함께 가진 단위**이다.

## 클래스와 인스턴스의 차이

클래스와 객체는 밀접하지만 같은 개념은 아니다.

- **클래스(Class)**: 어떤 상태와 행동을 가질지 정의한 틀이다.
- **인스턴스(Instance)**: 클래스를 바탕으로 실제 생성한 객체이다.

앞서 작성한 `BankAccount`는 클래스이다.

```
account_a = BankAccount("민수", 10000)
account_b = BankAccount("지연", 20000)

account_a.deposit(5000)

print(account_a.balance)  # 15000
print(account_b.balance)  # 20000
```

`account_a`와 `account_b`는 같은 클래스로 만들었지만, 각자 독립적인 상태를 갖는다.

|개념|예|
|---|---|
|클래스|`BankAccount`|
|인스턴스|`account_a`, `account_b`|
|속성|`owner`, `_balance`|
|메서드|`deposit()`, `withdraw()`|

**메서드(method)**는 객체나 클래스에 속한 함수이다. 위 코드의 `self`는 메서드가 호출된 객체 자신을 가리킨다.

예를 들어 `account_a.deposit(5000)`을 호출하면, 그 메서드 안의 `self`는 `account_a`이다.

참고로 모든 객체지향 언어가 클래스를 반드시 사용하는 것은 아니다.

## 절차지향과 객체지향 차이

차이는 주로 **프로그램을 나누고 책임을 배치하는 기준**에 있다.

### 절차지향: 처리 순서를 중심으로 구성

절차지향에서는 데이터를 어떤 순서로 처리할지에 초점을 맞춘다.

```
account = {
    "owner": "민수",
    "balance": 10000
}

def withdraw(account, amount):
    if amount <= 0:
        raise ValueError("출금액은 0보다 커야 합니다.")

    if amount > account["balance"]:
        raise ValueError("잔액이 부족합니다.")

    account["balance"] -= amount
```

계좌 데이터와 이를 처리하는 함수가 분리되어 있다.

### 객체지향: 책임을 가진 객체를 중심으로 구성

객체지향에서는 계좌가 자신의 데이터를 관리하도록 설계한다.

```
account = BankAccount("민수", 10000)
account.withdraw(3000)
```

사용하는 쪽은 출금 처리를 계좌 객체에 요청한다. 계좌는 요청을 받아 자신의 규칙에 따라 상태를 변경한다.

|비교|절차지향|객체지향|
|---|---|---|
|주된 분해 기준|함수와 처리 절차|객체와 책임|
|데이터와 동작|분리해서 구성하는 경우가 많음|관련된 것끼리 묶음|
|설계의 주요 질문|어떤 순서로 처리할까?|누가 이 일을 책임질까?|

절차지향에서도 데이터를 잘 보호하고 모듈화할 수 있다. 객체지향 프로그램 안에서도 메서드의 내부는 순차적인 절차로 실행된다. 두 방식은 실무에서 함께 사용되기도 한다.

## 객체지향의 대표적인 네 가지 특징

일반적으로 객체지향을 설명할 때 **캡슐화, 추상화, 상속, 다형성**을 이야기한다.

### 캡슐화: 객체가 자신의 상태와 규칙 관리

캡슐화는 관련 데이터와 동작을 하나로 묶고, 외부에서 객체를 사용하는 경계를 정하는 것이다.

계좌 잔액을 외부에서 마음대로 변경할 수 있다고 해본다.

```
account.balance = -1000000
```

이런 변경이 허용되면 “잔액은 음수일 수 없다”는 규칙이 깨질 수 있다.

그래서 앞의 `BankAccount`는 잔액 조회만 제공하고, 변경은 `deposit()`과 `withdraw()`를 통해 하도록 설계한다.

```
account.deposit(5000)
account.withdraw(3000)
```

이렇게 하면 상태가 바뀌는 지점에서 규칙을 검사할 수 있다.

**캡슐화의 목적은 단순히 변수를 숨기는 것이 아니라, 객체가 자신의 유효한 상태를 유지하도록 하는 것이다.**

다만 Python의 `_balance`처럼 밑줄 하나를 붙이는 방식은 “내부 구현이니 직접 접근하지 말자”는 관례이다. 언어 차원에서 직접 접근을 완전히 차단하지는 않는다. Java의 `private`처럼 접근을 제한하는 기능을 제공하는 언어도 있다.

### 추상화: 사용하는 데 필요한 핵심만

추상화는 복잡한 세부사항 중에서, 현재 목적에 필요한 개념과 기능을 골라 표현하는 것이다.

자동차를 운전할 때는 엔진의 연소 과정을 전부 알 필요가 없다. 운전자는 가속페달, 브레이크, 핸들처럼 운전에 필요한 기능을 사용한다.

프로그램에서도 비슷한다.

```
account.withdraw(3000)
```

호출하는 쪽은 내부에서 잔액을 어떤 변수에 저장하는지 알 필요가 없다. “이 계좌에서 3,000원을 출금한다”는 동작을 이해하면 된다.

캡슐화와 추상화는 연결되지만 초점이 다르다.

|개념|핵심 질문|
|---|---|
|캡슐화|내부 상태와 규칙을 어떻게 보호하고 관리할까?|
|추상화|사용하는 쪽에 어떤 개념과 기능을 보여줄까?|

추상화는 반드시 `abstract` 같은 문법을 써야 성립하는 것은 아니다. 잘 설계한 일반 함수나 클래스도 추상화를 제공한다.

### 상속: 기존 타입을 확장해 새로운 타입 제작

상속은 기존 클래스의 속성과 동작을 바탕으로 새로운 클래스를 정의하는 기능이다.

```
class Animal:
    def breathe(self):
        print("숨을 쉽니다.")


class Dog(Animal):
    def bark(self):
        print("멍멍!")


dog = Dog()

dog.breathe()  # 부모 클래스에서 물려받은 기능
dog.bark()     # 자식 클래스에 추가한 기능
```

여기서 `Animal`은 부모 클래스, `Dog`는 자식 클래스이다.

상속은 보통 **“Dog는 Animal의 한 종류다”**와 같은 관계를 표현한다. 이를 _is-a 관계_라고 부른다.

하지만 코드가 비슷하다는 이유만으로 상속하면 문제가 생길 수 있다.

예를 들어 자동차가 엔진 기능을 이용한다고 해서 `Car`가 `Engine`을 상속하는 것은 자연스럽지 않다. 자동차는 엔진의 한 종류가 아니기 때문이다. 이런 경우에는 자동차 객체가 엔진 객체를 가지도록 설계하는 편이 적절하다.

또한 상속받은 클래스는 부모 클래스가 약속한 동작을 지켜야 한다. 부모 타입을 기대하는 코드에 자식 객체를 넣었을 때 기존 코드가 올바르게 동작할 수 있어야 한다.

### 다형성: 같은 요청을 객체마다 다르게 수행

다형성은 **같은 사용 방식으로 서로 다른 객체를 다룰 수 있는 성질**이다.

예를 들어 여러 알림 수단이 모두 `send()` 기능을 제공한다고 해본다.

```
class EmailNotifier:
    def send(self, message):
        print(f"이메일 발송: {message}")


class SmsNotifier:
    def send(self, message):
        print(f"문자 발송: {message}")


def notify_user(notifier, message):
    notifier.send(message)
```

다음과 같이 같은 함수에 서로 다른 객체를 전달할 수 있다.

```
notify_user(EmailNotifier(), "주문이 완료되었습니다.")
notify_user(SmsNotifier(), "배송이 시작되었습니다.")
```

`notify_user()`는 전달받은 객체가 이메일인지 문자인지 구분하지 않다. `send(message)`라는 약속에 따라 사용한다.

다형성을 활용하면 새 알림 수단을 추가할 때도 기존 호출 코드를 유지할 수 있다.

```
class PushNotifier:
    def send(self, message):
        print(f"앱 푸시 발송: {message}")


notify_user(PushNotifier(), "새 메시지가 도착했습니다.")
```

위 예제에는 상속이 없다. Python에서는 필요한 동작을 제공하는 객체를 사용하는 방식으로도 다형성을 구현할 수 있다. 이를 흔히 **덕 타이핑(duck typing)**이라고 한다.

물론 메서드 이름만 같다고 충분한 것은 아니다. 인자, 반환값, 동작의 의미도 호출하는 쪽의 기대와 맞아야 한다.

## 객체의 협력

실제 프로그램에서는 객체 하나가 모든 일을 처리하지 않는다. 각 객체가 자신의 책임을 맡고, 필요한 기능을 다른 객체에 요청한다.

예를 들어 주문 알림 기능을 생각해본다.

- 주문 객체는 주문번호와 주문 상태를 관리한다.
- 알림 객체는 메시지 전달을 담당한다.
- 주문 서비스는 주문 처리 흐름을 조정한다.

```
class Order:
    def __init__(self, order_id):
        self.order_id = order_id
        self._status = "pending"

    @property
    def status(self):
        return self._status

    def complete(self):
        if self._status != "pending":
            raise ValueError("대기 중인 주문만 완료할 수 있습니다.")

        self._status = "completed"


class OrderService:
    def __init__(self, notifier):
        self.notifier = notifier

    def complete_order(self, order):
        order.complete()
        self.notifier.send(
            f"주문 {order.order_id}이 완료되었습니다."
        )
```

사용하는 코드는 다음과 같다.

```
order = Order("ORDER-001")

service = OrderService(EmailNotifier())
service.complete_order(order)
```

이 구조에서는 역할이 구분된다.

|객체|책임|
|---|---|
|`Order`|주문 상태와 상태 변경 규칙 관리|
|`EmailNotifier`|이메일 알림 처리|
|`OrderService`|주문 완료와 알림 호출의 흐름 조정|

`OrderService`는 메시지를 이메일로 보낼지 문자로 보낼지 직접 결정하지 않는다. 생성할 때 전달받은 객체를 사용한다. 이처럼 필요한 객체를 외부에서 전달하는 방식을 **의존성 주입**이라고 한다.

예제는 협력 구조를 설명하기 위한 것이다. 실제 서비스에서는 알림 전송 실패와 재시도 같은 상황도 별도로 설계해야 한다.

## 상속보다 ‘합성’을 먼저 고려하는 이유

**합성(composition)**은 다른 객체를 포함하거나 참조해 기능을 구성하는 방식이다.

앞의 예제에서 `OrderService`는 알림 객체를 가지고 있다.

```
class OrderService:
    def __init__(self, notifier):
        self.notifier = notifier
```

이처럼 필요한 객체를 조합하면 기능을 쉽게 바꿀 수 있다.

```
email_service = OrderService(EmailNotifier())
sms_service = OrderService(SmsNotifier())
```

상속과 합성을 비교하면 다음과 같다.

|방식|관계|예|
|---|---|---|
|상속|A는 B의 한 종류다|개는 동물이다|
|합성|A가 B를 가지고 있거나 사용한다|주문 서비스가 알림 객체를 사용한다|

상속은 부모 클래스와 자식 클래스를 강하게 연결한다. 부모의 변경이 여러 자식에게 영향을 줄 수 있고, 상속 단계가 깊어지면 동작을 따라가기 어려워진다.

합성은 기능을 작은 객체로 나누고 조합하기 때문에 교체와 테스트에 유리한 경우가 많다. 그래서 설계할 때는 **합성으로 해결할 수 있는지 먼저 살펴보고, 명확한 타입 관계와 공통 계약이 있을 때 상속을 고려하는 접근**이 유용하다.

## 좋은 객체지향 설계의 기준

### 책임이 명확해야 한다

객체가 어떤 일을 맡는지 간단히 설명할 수 있어야 한다.

예를 들어 `Order`가 주문 상태 관리뿐 아니라 이메일 발송, 파일 저장, 통계 계산, 화면 출력까지 모두 담당한다면 변경 이유가 너무 많아진다.

서로 다른 이유로 바뀌는 기능을 적절히 나누면 수정 범위를 이해하기 쉬워진다.

### 응집도는 높이고 결합도는 낮춘다

- **응집도**: 한 객체 안의 데이터와 기능이 얼마나 밀접하게 관련되어 있는가.
- **결합도**: 다른 객체의 구체적인 구조와 동작에 얼마나 의존하는가.

계좌의 잔액과 입출금 규칙을 함께 두면 응집도가 높아진다.

주문 서비스가 특정 이메일 업체의 복잡한 내부 구현 대신 `send()`라는 작은 기능에 의존하면 결합도를 낮출 수 있다.

결합도를 낮춘다는 것은 의존성을 모두 없앤다는 뜻이 아니다. **필요한 협력은 유지하면서, 서로의 내부 사정을 너무 많이 알지 않게 하는 것**이다.

### 객체에 일을 요청한다

다음과 같이 외부 코드가 객체 내부 상태를 직접 조작하면 규칙이 여러 곳으로 흩어지기 쉽다.

```
if account._balance >= amount:
    account._balance -= amount
```

계좌에 출금을 요청하면 규칙을 계좌 안에 모을 수 있다.

```
account.withdraw(amount)
```

다만 모든 데이터 조회를 없애야 한다는 뜻은 아니다. 보고서나 화면 표시에는 상태 조회가 필요하다. 중요한 것은 **상태 변경 규칙의 책임이 어디에 있는가**이다.

## SOLID 원칙

SOLID는 객체지향 설계를 검토할 때 자주 사용하는 다섯 가지 원칙의 앞 글자이다.

|원칙|의미|
|---|---|
|**S — 단일 책임 원칙**|클래스에 서로 다른 변경 이유가 뒤섞이지 않게 한다.|
|**O — 개방·폐쇄 원칙**|예상되는 기능 확장을 기존 코드의 수정을 적게 하면서 수용하도록 설계한다.|
|**L — 리스코프 치환 원칙**|자식 타입은 부모 타입의 계약을 지켜, 부모가 쓰이던 자리에 들어갈 수 있어야 한다.|
|**I — 인터페이스 분리 원칙**|사용하는 쪽에 필요 없는 기능까지 의존하도록 강요하지 않는다.|
|**D — 의존성 역전 원칙**|핵심 정책이 구체적인 구현 세부사항에 직접 묶이지 않도록 추상적인 계약에 의존한다.|

이 원칙들은 무조건 따라야 하는 공식이 아니다. 단순한 기능을 위해 인터페이스와 클래스를 지나치게 늘리면 오히려 이해하기 어려워진다.

먼저 구체적인 변경 가능성과 책임을 파악하고, 실제 문제를 줄이는 데 필요한 만큼 적용하는 것이 좋다.

## 객체지향의 장점과 한계

### 장점

- **변경 범위를 줄일 수 있다.** 내부 구현을 바꿔도 외부에 제공하는 계약을 유지하면 영향을 제한할 수 있다.
- **데이터의 규칙을 모을 수 있다.** 잔액이나 주문 상태처럼 조건이 있는 데이터를 일관되게 관리하기 좋다.
- **구현을 교체하기 쉽다.** 같은 계약을 지키는 객체를 이용해 알림, 저장소, 결제 수단 등을 교체할 수 있다.
- **테스트에 도움이 된다.** 실제 외부 시스템 대신 테스트용 객체를 전달해 특정 동작을 확인할 수 있다.

### 한계

- **설계가 과해질 수 있다.** 간단한 처리를 여러 클래스와 계층으로 나누면 이해 비용이 커진다.
- **실행 흐름이 흩어질 수 있다.** 메서드 호출과 객체 관계를 따라가야 전체 동작이 보이는 경우가 있다.
- **상태 관리가 복잡해질 수 있다.** 여러 곳에서 같은 변경 가능한 객체를 공유하면 예상하지 못한 영향이 발생할 수 있다.
- **항상 가장 적합한 방식은 아니다.** 단순한 계산, 일회성 스크립트, 데이터 변환은 함수 중심으로 표현하는 편이 더 명료할 수 있다.

객체지향의 장점은 클래스를 썼다는 사실에서 자동으로 나오지 않는다. 책임과 의존성을 어떻게 나누었는지가 중요하다.
