SSE는 보통 **Server-Sent Events**를 뜻한다. 서버가 HTTP 연결을 계속 열어둔 채, 새로운 데이터가 생길 때마다 브라우저에 이벤트를 보내는 단방향 실시간 통신 방식이다.

채팅의 새 메시지, 알림, 주가·환율, 로그 스트리밍, 작업 진행률처럼 **서버 → 클라이언트 방향의 지속적인 업데이트**에 특히 적합하다.

## 기본 동작 원리

일반적인 HTTP 요청은 다음처럼 한 번의 응답으로 끝난다.

```
클라이언트 ── 요청 ──▶ 서버
클라이언트 ◀─ 응답 ─── 서버
                 연결 종료
```

SSE에서는 서버가 응답을 종료하지 않는다.

```
클라이언트 ── GET 요청 ──▶ 서버
클라이언트 ◀─ 이벤트 1 ─── 서버
클라이언트 ◀─ 이벤트 2 ─── 서버
클라이언트 ◀─ 이벤트 3 ─── 서버
                    ...
```

전체 과정은 다음과 같다.

1. 브라우저가 서버의 SSE 엔드포인트에 HTTP `GET` 요청을 보낸다.
2. 서버는 응답의 `Content-Type`을 `text/event-stream`으로 설정한다.
3. 서버는 연결을 닫지 않고 유지한다.
4. 데이터가 생길 때마다 정해진 텍스트 형식으로 응답 스트림에 기록한다.
5. 브라우저는 데이터가 도착하는 즉시 이벤트를 발생시킨다.
6. 연결이 끊어지면 브라우저가 기본적으로 자동 재연결을 시도한다.

SSE는 별도의 독자적인 전송 프로토콜이라기보다, **HTTP 응답 스트리밍과 표준화된 이벤트 형식**을 이용하는 기술이다.

## SSE 메시지 형식

SSE 이벤트는 일반 텍스트 기반이며 대표적으로 다음 필드를 사용한다.

```
event: notification
id: 42
retry: 5000
data: {"message":"새 알림이 있습니다"}
```

각 필드의 의미는 다음과 같다.

|필드|의미|
|---|---|
|`data`|클라이언트에 전달할 데이터|
|`event`|사용자 정의 이벤트 이름|
|`id`|이벤트 식별자|
|`retry`|재연결을 시도할 대기 시간(ms)|
|`:`|주석 또는 연결 유지용 메시지|

### `data`

가장 중요한 필드이다.

```
data: hello
```

`EventSource`의 `message` 이벤트로 전달된다.

```
source.onmessage = (event) => {
  console.log(event.data); // hello
};
```

SSE 자체가 JSON을 강제하지는 않는다. 객체를 보내려면 서버에서 JSON 문자열로 변환하고, 클라이언트에서 다시 파싱해야 한다.

```
data: {"name":"Kim","count":3}
```

```
source.onmessage = (event) => {
  const data = JSON.parse(event.data);
  console.log(data.name);
};
```

### `event`

이벤트 종류를 구분할 때 사용한다.

```
event: notification
data: 새 알림

event: progress
data: 70
```

클라이언트에서는 `addEventListener()`로 받는다.

```
source.addEventListener("notification", (event) => {
  console.log("알림:", event.data);
});

source.addEventListener("progress", (event) => {
  console.log("진행률:", event.data);
});
```

`event` 필드가 없으면 기본 이벤트 이름은 `message`이다.

### `id`

이벤트마다 식별자를 지정할 수 있다.

```
id: 101
data: 첫 번째 이벤트

id: 102
data: 두 번째 이벤트
```

브라우저는 마지막으로 처리한 ID를 기억한다. 연결이 끊긴 뒤 재연결할 때 서버에 다음 헤더를 보낼 수 있다.

```
Last-Event-ID: 102
```

서버는 이 값을 사용해 103번 이후의 이벤트부터 다시 전송할 수 있다. 다만 실제 복구를 지원하려면 서버가 이벤트를 데이터베이스, 메시지 브로커 또는 메모리에 일정 기간 보관해야 한다.

### `retry`

자동 재연결 간격을 지정한다.

```
retry: 5000
```

연결이 끊어지면 약 5초 후 재연결을 시도하라는 의미이다.

### 주석과 하트비트

콜론으로 시작하는 줄은 클라이언트가 무시한다.

```
: keep-alive
```

프록시나 로드 밸런서가 비활성 연결을 종료하지 않도록 서버가 주기적으로 보내는 하트비트로 자주 사용된다.

## 자동 재연결

SSE의 큰 장점 중 하나는 브라우저가 재연결을 기본 지원한다는 것이다.

서버가 잠시 중단되거나 네트워크가 끊겨도 `EventSource`는 연결을 다시 시도한다.

```
const source = new EventSource("/events");

source.onerror = () => {
  console.log("연결에 문제가 발생했습니다. 재연결을 기다립니다.");
};
```

`error` 이벤트가 발생했다고 해서 항상 영구적으로 종료된 것은 아니다. 상태는 `readyState`로 확인할 수 있다.

```
console.log(source.readyState);
```

|값|상수|의미|
|---|---|---|
|`0`|`EventSource.CONNECTING`|연결 중 또는 재연결 중|
|`1`|`EventSource.OPEN`|연결됨|
|`2`|`EventSource.CLOSED`|완전히 종료됨|

클라이언트에서 연결을 명시적으로 종료하려면 다음을 호출한다.

```
source.close();
```

`close()` 이후에는 자동 재연결하지 않는다.

## SSE와 WebSocket 비교

둘 다 실시간 통신에 사용되지만 목적이 다르다.

|항목|SSE|WebSocket|
|---|---|---|
|통신 방향|서버 → 클라이언트|양방향|
|기반|HTTP 스트리밍|WebSocket 프로토콜|
|브라우저 API|`EventSource`|`WebSocket`|
|데이터 형식|UTF-8 텍스트|텍스트와 바이너리|
|자동 재연결|브라우저 기본 지원|직접 구현|
|이벤트 ID 복구|표준 지원|직접 설계|
|구현 복잡도|비교적 단순|상대적으로 높음|
|일반 HTTP 인프라 호환성|좋음|환경별 설정 필요|
|클라이언트 → 서버 전송|별도 HTTP 요청 필요|동일 연결로 전송|

다음과 같은 경우 SSE가 적합하다.

- 알림 피드
- AI 응답 스트리밍
- 서버 작업 진행률
- 시스템 로그
- 뉴스·가격·상태 업데이트
- 대시보드 지표
- 배포 상태 모니터링

다음과 같은 경우에는 WebSocket이 더 적합하다.

- 실시간 채팅에서 송수신이 모두 매우 빈번한 경우
- 멀티플레이 게임
- 실시간 공동 편집
- 음성·영상·바이너리 데이터
- 매우 낮은 지연의 양방향 메시징

단, 채팅이라고 무조건 WebSocket이 필요한 것은 아니다. 메시지를 보낼 때는 일반 `POST` 요청을 사용하고, 새 메시지를 받을 때만 SSE를 사용하는 구조도 충분히 가능하다.

```
메시지 전송: POST /messages
새 메시지 수신: GET /events
```

## SSE와 일반 폴링 비교

폴링은 클라이언트가 주기적으로 서버에 질문하는 방식이다.

```
10:00:00 새 데이터 있나요?
10:00:05 새 데이터 있나요?
10:00:10 새 데이터 있나요?
```

SSE는 서버가 데이터가 생겼을 때 바로 알려준다.

```
연결 유지
        서버: 새 데이터가 생겼습니다
```

### 폴링의 문제점

- 새 데이터가 없어도 요청이 계속 발생한다.
- 폴링 간격만큼 지연될 수 있다.
- 폴링 간격을 줄이면 서버 부하가 커진다.

### SSE의 장점

- 불필요한 반복 요청이 적다.
- 데이터 발생 직후 전송할 수 있다.
- 하나의 HTTP 연결을 유지한다.

다만 업데이트 빈도가 매우 낮고 인프라가 장기 연결을 지원하기 어려운 환경에서는 단순 폴링이 운영하기 편할 수도 있다.

## 인증에서 주의할 점

브라우저의 기본 `EventSource`는 임의의 요청 헤더를 설정하는 기능이 없다. 따라서 다음 코드는 지원되지 않는다.

```
// 기본 EventSource에서는 불가능
new EventSource("/events", {
  headers: {
    Authorization: "Bearer token"
  }
});
```

주로 다음 방법을 사용한다.

### 쿠키 기반 인증

같은 출처라면 기존 세션 쿠키가 함께 전송된다.

다른 출처에서 인증 쿠키를 보낼 때는 다음 옵션을 사용한다.

```
const source = new EventSource("https://api.example.com/events", {
  withCredentials: true
});
```

서버도 적절한 CORS 및 credentials 설정을 해야 한다.

### 짧은 수명의 URL 토큰

```
const source = new EventSource(
  `/events?ticket=${encodeURIComponent(shortLivedTicket)}`
);
```

장기 액세스 토큰을 URL에 직접 넣는 것은 권장되지 않는다. URL은 브라우저 기록, 프록시 로그, 서버 접근 로그 등에 남을 수 있기 때문이다.

### `fetch()` 스트리밍

`Authorization` 헤더가 꼭 필요하다면 `EventSource` 대신 `fetch()`와 `ReadableStream`을 사용할 수 있습니다.

```
const response = await fetch("/events", {
  headers: {
    Authorization: `Bearer ${token}`
  }
});

const reader = response.body.getReader();
const decoder = new TextDecoder();

while (true) {
  const { value, done } = await reader.read();

  if (done) break;

  console.log(decoder.decode(value, { stream: true }));
}
```

다만 이 방식에서는 SSE 이벤트 구문 분석과 재연결을 직접 구현하거나 관련 라이브러리를 사용해야 한다.

## 프록시와 버퍼링 문제

SSE 서버가 올바르게 데이터를 보내더라도 Nginx, CDN, 애플리케이션 서버 또는 압축 미들웨어가 응답을 버퍼링하면 이벤트가 실시간으로 전달되지 않을 수 있다.

예를 들어 서버는 1초마다 이벤트를 기록하지만, 프록시가 여러 이벤트를 모아 30초 후 한꺼번에 전달할 수 있다.

일반적으로 확인할 항목은 다음과 같다.

- 응답 버퍼링 비활성화
- 캐시 비활성화
- 충분히 긴 idle timeout
- 스트리밍 응답에 대한 압축 설정
- 주기적인 하트비트
- 플랫폼의 최대 요청 지속 시간
- 서버나 프록시가 HTTP chunk를 즉시 전달하는지 여부

Nginx 환경에서는 애플리케이션이 다음 헤더를 사용하는 경우가 있다.

```
X-Accel-Buffering: no
```

서버 응답은 보통 다음과 같이 구성한다.

```
Content-Type: text/event-stream
Cache-Control: no-cache
X-Accel-Buffering: no
```

`Connection: keep-alive`는 HTTP/1.1 환경에서 흔히 보이지만, HTTP/2에서는 연결 관리 방식이 다르므로 핵심 요건은 아니다.

## 서버 확장성

SSE 연결은 짧은 HTTP 요청보다 오래 유지된다. 사용자가 10만 명이면 최대 10만 개에 가까운 장기 연결을 관리해야 할 수 있다.

확장할 때 고려할 요소는 다음과 같다.

- 서버당 동시 연결 수
- 파일 디스크립터 제한
- 메모리 사용량
- 비동기 I/O 지원 여부
- 로드 밸런서의 연결 제한과 timeout
- 여러 서버 인스턴스 사이의 이벤트 공유
- 재연결 시 누락 이벤트 복구

서버가 여러 인스턴스로 구성되어 있다면 이벤트를 Redis Pub/Sub, Redis Streams, Kafka, NATS 같은 메시지 시스템을 통해 각 인스턴스에 전달하는 구조를 사용할 수 있다.

```
업무 시스템
    │
    ▼
메시지 브로커
 ┌──┼──────────┐
 ▼  ▼          ▼
SSE 서버 A  SSE 서버 B  SSE 서버 C
 │             │
 ▼             ▼
클라이언트들   클라이언트들
```

`Last-Event-ID`를 이용한 신뢰성 있는 복구가 필요하다면 단순 Pub/Sub보다는 일정 기간 이벤트가 보존되는 스트림이나 로그 기반 시스템이 더 적합하다.

## 이벤트 유실과 전달 보장

SSE가 자동 재연결을 지원한다고 해서 이벤트 전달이 자동으로 보장되는 것은 아니다.

연결이 끊어진 동안 다음 이벤트가 발생했다고 가정해 본다.

```
클라이언트가 받은 마지막 이벤트: 100
연결이 끊긴 동안 발생한 이벤트: 101, 102, 103
재연결 후 현재 이벤트: 104
```

서버가 과거 이벤트를 저장하지 않으면 클라이언트는 101~103을 잃을 수 있다.

보다 신뢰성 있게 구현하려면 다음 과정이 필요하다.

1. 서버가 이벤트에 증가하는 ID를 부여한다.
2. 이벤트를 일정 기간 보관한다.
3. 클라이언트 재연결 요청의 `Last-Event-ID`를 확인한다.
4. 누락된 이벤트부터 다시 보낸다.
5. 클라이언트가 중복 이벤트를 안전하게 처리하도록 설계한다.

네트워크 장애 경계에서는 같은 이벤트가 다시 전달될 수 있으므로, 중요한 처리라면 이벤트 ID를 기준으로 중복을 제거하는 것이 좋다.
