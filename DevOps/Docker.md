# Docker

**Docker는 애플리케이션과 실행에 필요한 환경을 이미지로 묶고, 이를 ‘컨테이너’라는 격리된 환경에서 실행하도록 돕는 플랫폼이다.**

예를 들어 Python 웹 서비스를 실행하려면 소스 코드뿐 아니라 Python, 라이브러리, 시스템 패키지, 실행 설정 등이 필요하다. Docker를 사용하면 이러한 실행 환경을 일정하게 구성하고 다른 컴퓨터에서도 재사용하기 쉬워진다.

아래의 내용은 **Linux 컨테이너**를 기준이다.

## Docker가 필요한 이유

개발하다 보면 다음과 같은 문제가 자주 생긴다.

> “제 컴퓨터에서는 잘 되는데, 서버에서는 실행되지 않아요.”

원인은 코드 외부에 있을 수 있다.

| 환경 차이                  | 발생할 수 있는 문제              |
| ---------------------- | ------------------------ |
| Python이나 Node.js 버전 차이 | 문법 또는 기능 호환성 문제          |
| 라이브러리 버전 차이            | 함수 동작이나 인터페이스 차이         |
| 시스템 패키지 누락             | 프로그램 실행 실패               |
| 서로 다른 설치 설정            | 경로나 권한 문제                |
| 여러 프로젝트의 의존성 충돌        | 한 프로젝트를 수정하다 다른 프로젝트가 고장 |

Docker를 사용하면 프로젝트별로 실행 환경을 분리할 수 있다. 프로젝트 A에는 필요한 버전의 Python을, 프로젝트 B에는 다른 버전을 넣어 각각 실행하는 방식이다.

팀원과 서버가 같은 이미지를 사용하면 환경 차이에서 생기는 문제를 줄일 수 있다. 다만 외부 데이터베이스, 환경 변수, CPU 구조, 커널 등의 차이까지 자동으로 없애 주는 것은 아니다.

## 가장 중요한 개념: 이미지와 컨테이너

Docker를 이해할 때 가장 먼저 구분해야 하는 두 가지이다.

### 이미지(Image): 실행 환경을 담은 원본

이미지는 컨테이너를 만들 때 사용하는 **읽기 전용 템플릿**이다.

일반적으로 다음 내용이 들어 있다.

- 애플리케이션 코드
- Python, Node.js 같은 런타임
- 필요한 라이브러리와 시스템 파일
- 기본 실행 명령과 일부 설정

이미지는 단독으로 실행 중인 프로그램이 아닙니다. 실행할 준비가 된 패키지에 가깝다.

### 컨테이너(Container): 이미지로 만든 실행 인스턴스

컨테이너는 이미지를 바탕으로 생성한 인스턴스이다. 실행하거나 중지하고, 다시 시작하거나 삭제할 수 있다.

하나의 이미지로 여러 컨테이너를 만들 수 있다.

```
웹 애플리케이션 이미지
    ├── 컨테이너 A
    ├── 컨테이너 B
    └── 컨테이너 C
```

각 컨테이너에는 별도의 실행 상태와 쓰기 가능한 파일 영역이 있다. 컨테이너 안에서 파일을 변경한다고 원본 이미지가 바뀌지는 않는다.

| 구분    | 이미지         | 컨테이너                |
| ----- | ----------- | ------------------- |
| 역할    | 실행 환경의 원본   | 원본으로 만든 인스턴스        |
| 실행 상태 | 없음          | 실행·중지 등의 상태가 있음     |
| 관계    | 여러 컨테이너의 기반 | 특정 이미지에서 생성         |
| 비유    | 프로그램 설치 패키지 | 설치 후 실행하는 프로그램 인스턴스 |

## Docker와 가상 머신 차이

가상 머신과 컨테이너 모두 환경을 분리하지만, 분리하는 방식이 다르다.

**가상 머신은 자체 운영체제 커널을 가진 가상 컴퓨터를 실행한다. 컨테이너는 커널을 공유하면서 프로세스와 실행 환경을 격리한다.**

커널은 CPU, 메모리, 파일 시스템 등 하드웨어 자원을 관리하는 운영체제의 핵심이다.

|항목|가상 머신(VM)|컨테이너|
|---|---|---|
|기본 단위|가상 컴퓨터|격리된 프로세스 실행 환경|
|운영체제 커널|각 VM이 자체 커널 사용|같은 실행 호스트의 커널 공유|
|시작 과정|운영체제 부팅 필요|주로 애플리케이션 프로세스 시작|
|자원 부담|일반적으로 상대적으로 큼|일반적으로 상대적으로 작음|
|주요 활용|별도 OS 운영, 강한 환경 분리|앱 패키징, 배포, 개발 환경 통일|

따라서 컨테이너는 보통 더 빠르게 시작하고 자원을 효율적으로 사용한다. 하지만 **컨테이너의 격리가 가상 머신과 동일한 수준이라는 뜻은 아니다.** 두 기술은 함께 사용되기도 합니다. 클라우드 VM 안에서 여러 컨테이너를 실행하는 구성이 흔하다.

## Docker의 구성 요소

|구성 요소|역할|
|---|---|
|**Docker CLI**|터미널에서 `docker` 명령을 입력하는 도구|
|**Docker Engine**|이미지, 컨테이너, 네트워크 등을 관리하고 실행하는 기반|
|**Docker Desktop**|로컬 개발을 위해 Docker 실행 환경과 관리 UI 등을 제공하는 제품|
|**Dockerfile**|이미지를 만드는 방법을 작성한 파일|
|**Registry**|이미지를 저장하고 배포하는 저장소|
|**Docker Hub**|널리 사용하는 이미지 레지스트리 서비스|
|**Docker Compose**|여러 컨테이너의 실행 구성을 파일로 관리하는 도구|

일반적인 작업 흐름은 다음과 같다.

```
소스 코드 + Dockerfile
          │
      docker build
          ▼
        이미지
          │
       docker run
          ▼
       컨테이너
```

이미지를 레지스트리에 올리면 다른 개발자나 서버가 내려받아 컨테이너를 실행할 수 있다. 이미지를 올리는 작업을 `push`, 내려받는 작업을 `pull`이라고 합니다.

## 컨테이너 실행 예시

Docker가 설치되어 실행 중이라면 다음 명령으로 Nginx 웹 서버를 실행할 수 있다.

```
docker run -d \
  --name my-web \
  -p 127.0.0.1:8080:80 \
  nginx:stable
```

각 부분의 의미는 다음과 같다.

|부분|의미|
|---|---|
|`docker run`|새 컨테이너를 만들고 실행|
|`-d`|백그라운드에서 실행|
|`--name my-web`|컨테이너 이름 지정|
|`-p 127.0.0.1:8080:80`|내 컴퓨터의 로컬 8080 포트를 컨테이너의 80 포트에 연결|
|`nginx:stable`|사용할 이미지와 태그|

이미지가 로컬에 없다면 Docker가 내려받는다. 실행한 뒤 브라우저에서 [localhost:8080](http://localhost:8080)에 접속하면 된다.

포트 연결은 다음처럼 이해하면 된다.

```
브라우저
   │
   ▼
내 컴퓨터의 8080 포트
   │
   ▼
컨테이너의 80 포트
   │
   ▼
Nginx
```

`8080:80`처럼 호스트 IP를 생략하면 기본적으로 모든 네트워크 인터페이스에 포트를 게시한다. 위 예시는 로컬 실습용으로 `127.0.0.1`에만 연결했다.

### 자주 사용하는 관리 명령

```
# 실행 중인 컨테이너 조회
docker ps

# 중지된 컨테이너까지 조회
docker ps -a

# 로그 확인
docker logs my-web

# 컨테이너 중지
docker stop my-web

# 기존 컨테이너 다시 시작
docker start my-web

# 중지된 컨테이너 삭제
docker rm my-web
```

**`docker run`은 새 컨테이너를 만들고, `docker start`는 이미 만들어진 컨테이너를 시작한다.**

## Dockerfile로 직접 이미지 만들기

Dockerfile에는 이미지 생성 과정을 작성한다.

간단한 HTML 페이지를 제공하는 예시를 본다.

### 파일 구성

```
my-site/
├── Dockerfile
└── index.html
```

`index.html`:

```
<!doctype html>
<html lang="ko">
  <meta charset="utf-8">
  <title>Docker 실습</title>
  <h1>Docker로 실행한 웹사이트입니다.</h1>
</html>
```

`Dockerfile`:

```
FROM nginx:stable

COPY index.html /usr/share/nginx/html/index.html

EXPOSE 80
```

각 명령은 다음 역할을 한다.

- **`FROM`**: 기반이 될 이미지를 지정합니다.
- **`COPY`**: 파일을 이미지 내부로 복사합니다.
- **`EXPOSE`**: 애플리케이션이 사용할 포트를 표시합니다.

이 예시는 기반 Nginx 이미지에 정의된 실행 명령을 그대로 사용한다. 다른 앱에서는 `RUN`으로 의존성을 설치하고, `WORKDIR`로 작업 디렉터리를 지정하며, `CMD`로 기본 실행 명령을 설정하기도 한다.

### 이미지 빌드 및 실행

`my-site` 폴더에서 실행한다.

```
docker build -t my-site:1.0 .
```

- `-t my-site:1.0`: 이미지 이름과 태그를 지정한다.
- 마지막 `.`: 현재 폴더를 빌드에 사용할 파일의 기준 범위로 지정한다.

이어서 컨테이너를 실행한다.

```
docker run -d \
  --name my-site-demo \
  -p 127.0.0.1:8081:80 \
  my-site:1.0
```

[localhost:8081](http://localhost:8081)에 접속하면 작성한 페이지를 볼 수 있다.

**`EXPOSE 80`만 작성해도 컴퓨터의 포트가 열리는 것은 아니다.** 호스트에서 접근하려면 위 예시처럼 `-p`로 포트를 연결해야 한다.

## 데이터 저장: 볼륨과 바인드 마운트

컨테이너에서 데이터베이스나 파일 업로드 기능을 운영한다면 저장 방식을 이해해야 한다.

### 컨테이너 중지와 삭제는 다르다

컨테이너의 쓰기 가능한 영역에 저장한 파일은 **중지만 해서는 사라지지 않는다.** 같은 컨테이너를 다시 시작하면 남아 있다.

하지만 **컨테이너를 삭제하면 해당 쓰기 영역도 삭제된다.** 따라서 오래 보관해야 할 데이터는 컨테이너와 별도로 관리해야 한다.

### 볼륨(Volume)

Docker가 관리하는 저장 공간이다. 컨테이너를 교체해도 같은 볼륨을 연결해 데이터를 사용할 수 있다.

```
기존 DB 컨테이너 ──┐
                   ├── 데이터 볼륨
새 DB 컨테이너 ────┘
```

주로 데이터베이스 파일처럼 계속 보관해야 하는 데이터에 사용한다.

### 바인드 마운트(Bind mount)

호스트의 특정 파일이나 폴더를 컨테이너에 직접 연결하는 방식이다.

예를 들어 개발 중인 소스 코드 폴더를 컨테이너에 연결하면, 호스트에서 수정한 파일을 컨테이너에서도 볼 수 있다.

|구분|볼륨|바인드 마운트|
|---|---|---|
|저장 위치 관리|Docker가 관리|사용자가 호스트 경로 지정|
|주요 용도|DB 데이터 등 지속 저장|소스 코드, 설정 파일 공유|
|호스트 폴더 구조 의존성|상대적으로 낮음|높음|

볼륨은 컨테이너와 별도 수명을 가지지만, **백업을 대신하지는 않는다.** 볼륨 자체를 삭제하거나 저장 장치가 고장 나면 데이터가 손실될 수 있다.

## Docker Compose: 여러 컨테이너를 함께 관리하기

실제 애플리케이션은 여러 서비스로 구성되는 경우가 많다.

```
웹 서버 + API 서버 + 데이터베이스 + 캐시
```

각 서비스를 매번 긴 `docker run` 명령으로 실행하는 대신, **Compose 파일에 전체 구성을 기록**할 수 있다.

다음은 웹 서버와 Redis를 실행하는 간단한 구성이다.

```
# compose.yaml
services:
  web:
    image: nginx:stable
    ports:
      - "127.0.0.1:8082:80"

  cache:
    image: redis:7
    command: ["redis-server", "--appendonly", "yes"]
    volumes:
      - cache-data:/data

volumes:
  cache-data:
```

이 예시는 두 서비스를 함께 실행하는 방법을 보여 준다. Nginx가 Redis를 사용하도록 설정한 애플리케이션 예시는 아니다.

파일이 있는 폴더에서 다음 명령을 사용한다.

```
# 서비스 생성 및 백그라운드 실행
docker compose up -d

# 상태 확인
docker compose ps

# 로그 확인
docker compose logs -f

# 컨테이너와 기본 네트워크 정리
docker compose down
```

일반적인 `docker compose down`은 위에서 선언한 이름 있는 볼륨을 삭제하지 않는다. `-v`를 추가하면 볼륨도 삭제할 수 있으므로 데이터가 필요한지 확인해야 한다.

**Dockerfile은 이미지를 만드는 방법을, Compose 파일은 서비스를 실행하는 구성을 정의한다.**

## Docker가 특히 유용한 상황

| 상황              | 얻는 이점                   |
| --------------- | ----------------------- |
| 새 팀원이 프로젝트에 참여  | 개발 환경 설정 과정을 공유하기 쉬움    |
| 여러 프로젝트를 동시에 개발 | 프로젝트별 의존성 충돌 감소         |
| 테스트용 DB가 필요     | 별도 컨테이너로 실행하고 정리 가능     |
| 개발 환경에서 서버로 배포  | 같은 이미지를 전달해 환경 차이 감소    |
| 여러 서비스를 함께 실행   | Compose로 구성을 기록하고 재현 가능 |

Docker의 핵심 가치는 단순히 프로그램을 실행하는 데 있지 않다. **실행 환경을 코드와 이미지로 관리하고, 반복해서 재현하기 쉽게 만드는 데 있다.**
