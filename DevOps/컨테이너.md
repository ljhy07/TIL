## 컨테이너란

**컨테이너(Container)는 애플리케이션과 실행에 필요한 파일·라이브러리를 묶어, 다른 프로세스와 격리된 환경에서 실행하는 기술**이다.

Docker, Kubernetes에서 사용하는 **소프트웨어 컨테이너**를 기준으로 설명이다.

예를 들어 Python 웹 서버를 실행하려면 소스 코드뿐 아니라 다음 요소가 필요하다.

- Python 런타임
- Flask, Django 같은 라이브러리
- 운영체제의 일부 라이브러리
- 실행 명령과 환경 설정

컨테이너는 이런 실행 환경을 일정하게 만들어 준다. 덕분에 개발자의 컴퓨터, 테스트 서버, 운영 서버 사이에서 발생하는 **“내 컴퓨터에서는 되는데 서버에서는 안 돼요”** 문제를 줄일 수 있다.

---

## 컨테이너 필요 이유

### 기존 방식: 서버에 실행 환경을 직접 설치

컨테이너 없이 애플리케이션을 배포한다면 보통 서버에 직접 필요한 프로그램을 설치한다.

```
서버
├── Python 설치
├── 시스템 라이브러리 설치
├── 프로젝트 의존성 설치
├── 소스 코드 복사
└── 애플리케이션 실행
```

문제는 여러 애플리케이션이 같은 서버를 사용할 때 발생한다.

|상황|발생할 수 있는 문제|
|---|---|
|A 서비스는 Python 3.10, B 서비스는 Python 3.12 사용|실행 환경 관리가 복잡해짐|
|개발 서버와 운영 서버의 라이브러리 버전이 다름|특정 환경에서만 오류 발생|
|서버를 새로 추가함|설치와 설정 작업을 반복해야 함|
|배포 중 서버 설정을 수동으로 변경함|실제 실행 환경을 재현하기 어려워짐|

### 컨테이너 방식: 서비스별 실행 환경을 분리

```
서버
├── 컨테이너 A
│   ├── Python 3.10
│   ├── A 서비스의 라이브러리
│   └── A 서비스
│
└── 컨테이너 B
    ├── Python 3.12
    ├── B 서비스의 라이브러리
    └── B 서비스
```

각 서비스가 필요한 파일과 라이브러리를 별도로 가지므로 충돌을 줄일 수 있다.

다만 **컨테이너를 사용한다고 모든 환경 차이가 사라지는 것은 아니다.** CPU 아키텍처, 호스트 커널, 네트워크, 외부 서비스와 설정 등은 여전히 영향을 준다.

---

## 컨테이너의 실제 정체는 ‘격리된 프로세스’다

컨테이너를 작은 가상 컴퓨터로 생각하기 쉽지만, 기술적으로는 **호스트 운영체제 위에서 실행되는 격리된 프로세스 또는 프로세스 집합**에 가깝다.

일반적인 Linux 컨테이너는 다음 구조로 동작한다.

```
┌──────────────────┐  ┌──────────────────┐
│ 컨테이너 A        │  │ 컨테이너 B        │
│ 애플리케이션      │  │ 애플리케이션      │
│ 라이브러리·파일   │  │ 라이브러리·파일   │
└──────────────────┘  └──────────────────┘
──────────────────────────────────────────
            호스트 Linux 커널
──────────────────────────────────────────
                  하드웨어
```

여기서 **커널(Kernel)**은 CPU, 메모리, 디스크, 네트워크 같은 자원을 관리하는 운영체제의 핵심이다.

컨테이너마다 독립적인 파일과 실행 환경을 가질 수 있지만, **커널은 호스트와 공유**한다.

### Ubuntu 컨테이너 안에 Ubuntu 전체가 있는 건가

일반적인 Ubuntu 컨테이너 이미지에는 Ubuntu의 사용자 공간 파일과 도구가 들어 있다. 별도의 Ubuntu 커널을 부팅하는 것은 아니다.

즉, 컨테이너 내부에서 Ubuntu 도구를 사용하더라도 실제 시스템 호출은 호스트의 Linux 커널이 처리합니다.

## 가상머신과 컨테이너 차이

**가상머신(VM)은 각자 운영체제 커널을 실행하고, 일반적인 컨테이너는 호스트 커널을 공유한다.**

### 가상머신 구조

```
하드웨어
└── 하이퍼바이저
    ├── VM A
    │   ├── 게스트 OS와 커널
    │   └── 애플리케이션
    └── VM B
        ├── 게스트 OS와 커널
        └── 애플리케이션
```

### 컨테이너 구조

```
하드웨어
└── 호스트 OS와 커널
    └── 컨테이너 실행 환경
        ├── 컨테이너 A: 애플리케이션과 의존성
        └── 컨테이너 B: 애플리케이션과 의존성
```

|구분|가상머신|일반적인 컨테이너|
|---|---|---|
|격리 방식|가상 하드웨어와 별도 커널|프로세스와 자원 접근 격리|
|커널|VM마다 별도로 실행|호스트와 공유|
|시작 과정|운영체제 부팅 필요|주로 애플리케이션 프로세스 시작|
|자원 사용|상대적으로 큼|상대적으로 작음|
|운영체제 선택|VM별 다른 OS 실행 가능|호스트 커널과의 호환성 필요|
|격리 경계|일반적으로 더 강함|공유 커널의 영향을 받음|
|주요 용도|OS 단위 분리, 강한 격리|애플리케이션 배포와 실행|

둘은 함께 쓰기도 한다. **클라우드 VM 여러 대를 만들고, 그 안에서 컨테이너를 실행하는 구성**은 흔하다.

Mac이나 Windows에서 Linux 컨테이너를 실행할 때도 보통 Linux VM 또는 WSL 2 같은 Linux 실행 환경이 중간에 있다.

## 이미지와 컨테이너의 차이

컨테이너를 이해할 때 가장 중요한 구분이다.

### 이미지: 실행 환경을 담은 원본

**이미지(Image)**는 컨테이너를 만들기 위한 파일과 실행 설정을 담은 읽기 전용 패키지이다.

보통 다음을 포함한다.

- 애플리케이션 코드
- 언어 런타임
- 필요한 라이브러리
- 기본 파일 시스템
- 기본 실행 명령

이미지 자체가 실행 중인 프로그램은 아니다.

### 컨테이너: 이미지로 만든 실행 인스턴스

**컨테이너는 이미지를 바탕으로 생성한 인스턴스**이다. 실행할 수도 있고, 중지된 상태로 존재할 수도 있다.

```
웹 서버 이미지
├── 컨테이너 1 → 실행 중
├── 컨테이너 2 → 실행 중
└── 컨테이너 3 → 중지 상태
```

같은 이미지로 여러 컨테이너를 만들 수 있으며, 각 컨테이너는 별도의 실행 상태와 쓰기 가능한 파일 계층을 가진다.

> **이미지는 배포할 원본이고, 컨테이너는 그 원본으로 만든 실행 단위이다.**

---

## Docker와 컨테이너

**컨테이너는 기술과 실행 단위이고, Docker는 이를 만들고 실행하고 배포하는 도구이다.**

주요 용어를 구분하면 다음과 같다.

|용어|의미|
|---|---|
|컨테이너|격리된 애플리케이션 실행 단위|
|Docker|이미지 빌드와 컨테이너 관리를 제공하는 도구|
|Dockerfile|이미지 생성 과정을 적은 파일|
|이미지|애플리케이션과 실행 환경을 담은 패키지|
|레지스트리|이미지를 저장하고 내려받는 저장소|
|Docker Compose|여러 컨테이너의 구성을 선언하고 함께 관리하는 도구|
|Kubernetes|여러 서버에 걸쳐 컨테이너 배포와 운영을 관리하는 시스템|

Docker 외에도 컨테이너 관련 도구는 있다. 컨테이너를 실행하는 런타임으로는 containerd, CRI-O 등이 사용된다.

## 내부 격리 동작

Linux 컨테이너는 여러 운영체제 기능을 조합해 만들어진다.

### ① Namespaces: 보이는 범위를 분리

Namespace는 프로세스가 바라보는 시스템의 범위를 분리한다.

예를 들어 컨테이너마다 다음 항목을 다르게 보이게 할 수 있다.

- 프로세스 목록
- 네트워크 인터페이스와 포트
- 파일 시스템 마운트
- 호스트 이름
- 사용자 ID와 그룹 ID의 매핑

컨테이너 안에서는 자기 프로세스만 보이게 할 수 있지만, 호스트에서는 해당 프로세스들을 관찰할 수 있다.

### ② cgroups: 사용할 수 있는 자원을 제어

cgroups는 프로세스 그룹의 자원 사용을 추적하고 제한하는 기능이다.

예를 들어 다음과 같은 정책을 적용할 수 있다.

```
컨테이너 A
├── 메모리 제한: 512MB
└── CPU 사용량 제한: CPU 1개에 해당하는 처리량
```

**컨테이너라는 이유만으로 CPU와 메모리가 자동으로 적절히 제한되지는 않습니다.** 필요한 한도를 설정해야 한다.

### ③ 파일 시스템 계층: 원본은 공유하고 변경은 분리

Docker 이미지에는 여러 읽기 전용 계층이 사용된다.

```
컨테이너의 쓰기 가능한 계층
──────────────────────────
애플리케이션 코드 계층
라이브러리 계층
런타임·기본 파일 계층
```

여러 컨테이너가 같은 이미지 계층을 재사용할 수 있어 저장 공간과 전송량을 줄일 수 있다. 컨테이너에서 발생한 파일 변경은 보통 그 컨테이너의 쓰기 계층에 기록된다.

### ④ 보안 기능: 허용된 동작을 제한

Capabilities, seccomp, AppArmor, SELinux 등의 기능으로 권한과 시스템 호출을 제한할 수 있다.

격리는 단일 기능이 아니라 **여러 기능이 함께 만드는 경계**이다.

## 컨테이너 안에 저장한 데이터

### 중지와 삭제는 다르다

|작업|컨테이너의 쓰기 계층|
|---|---|
|컨테이너 중지|유지됨|
|같은 컨테이너 다시 시작|기존 변경 내용이 남아 있음|
|컨테이너 삭제|함께 삭제됨|
|같은 이미지로 새 컨테이너 생성|이전 컨테이너의 변경 내용은 없음|

따라서 **데이터베이스 데이터나 업로드 파일을 컨테이너의 쓰기 계층에만 저장하면 안 된다.**

### 영구 데이터는 별도 저장소에 보관

대표적인 방법은 다음 두 가지이다.

|방식|설명|주요 용도|
|---|---|---|
|볼륨(Volume)|Docker가 관리하는 저장 공간을 연결|DB 데이터 등 영구 저장|
|바인드 마운트(Bind mount)|호스트의 특정 파일이나 디렉터리를 연결|개발 소스 공유, 설정 파일 연결|

```
DB 컨테이너 ──연결── 데이터 볼륨
    ↓ 삭제               ↓
컨테이너 교체       데이터는 유지
    ↓                    ↑
새 DB 컨테이너 ─────── 연결
```

볼륨도 별도로 삭제할 수 있으므로 백업은 여전히 필요하다.

## 컨테이너의 네트워크 연결

컨테이너는 별도의 네트워크 환경을 가질 수 있다.

### 외부에서 접근하려면 포트를 연결한다

컨테이너 내부의 웹 서버가 `80`번 포트를 사용한다고 가정해 본다.

```
docker run -d --name web -p 8080:80 nginx
```

여기서 `8080:80`의 의미는 다음과 같다.

```
호스트의 8080번 포트 → 컨테이너의 80번 포트
```

로컬 환경에서는 `http://localhost:8080`으로 접속할 수 있다.

### 컨테이너끼리는 네트워크를 통해 통신한다

예를 들어 웹 서버와 데이터베이스를 별도 컨테이너로 실행할 수 있다.

```
사용자
  ↓
웹 컨테이너
  ↓
DB 컨테이너
```

Docker Compose의 기본 네트워크에서는 일반적으로 서비스 이름으로 서로 접근할 수 있다. DB 서비스 이름이 `db`라면 웹 애플리케이션은 `db:5432` 같은 주소를 사용할 수 있다.

**일반적으로 컨테이너 내부의 `localhost`는 그 컨테이너 자신을 가리킨다.** 다른 컨테이너나 호스트를 뜻하지 않는다.

## 실제로 만들고 실행하는 과정

간단한 Python HTTP 서버를 컨테이너로 만든다고 가정해 본다.

### ① Dockerfile 작성

```
FROM python:3.12-slim

WORKDIR /app

COPY . .

EXPOSE 8000

CMD ["python", "-m", "http.server", "8000"]
```

각 명령은 다음 역할을 한다.

|명령|역할|
|---|---|
|`FROM`|기반이 되는 이미지 지정|
|`WORKDIR`|작업 디렉터리 지정|
|`COPY`|빌드할 파일을 이미지 안으로 복사|
|`EXPOSE`|사용하는 포트 정보를 표시|
|`CMD`|컨테이너의 기본 실행 명령 지정|

`EXPOSE` 자체가 호스트에 포트를 공개하지는 않는다. 실제 포트 연결은 실행할 때 `-p` 등으로 설정한다.

이 예제는 `/app`의 파일을 제공하는 학습용 서버이다.

### ② 이미지 빌드

```
docker build -t my-web:1.0 .
```

현재 디렉터리를 빌드 컨텍스트로 사용해 `my-web:1.0` 이미지를 만든다.

실제 프로젝트에서는 `.dockerignore`로 비밀 파일, 불필요한 데이터, 로컬 의존성 폴더 등을 빌드 대상에서 제외한다.

### ③ 컨테이너 실행

```
docker run -d --name my-web -p 8000:8000 my-web:1.0
```

### ④ 상태와 로그 확인

```
docker ps
docker logs my-web
```

### ⑤ 중지와 삭제

```
docker stop my-web
docker rm my-web
```

컨테이너를 삭제해도 이미지는 남아 있으므로 같은 이미지로 다시 만들 수 있다.

## 배포할 때의 흐름

일반적인 배포 과정은 다음과 같다.

```
코드 작성
    ↓
테스트
    ↓
컨테이너 이미지 빌드
    ↓
레지스트리에 이미지 업로드
    ↓
운영 서버에서 이미지 다운로드
    ↓
새 컨테이너 실행
    ↓
상태 확인 후 트래픽 전환
    ↓
이전 컨테이너 종료
```

중요한 점은 **검증한 이미지를 운영 환경에서도 그대로 사용할 수 있다는 것**이다.

운영 중인 컨테이너에 들어가 직접 코드를 수정하는 방식보다, 변경된 코드로 새 이미지를 만들고 컨테이너를 교체하는 방식이 일반적이다.

다만 태그는 다른 이미지를 가리키도록 변경될 수 있다. 정확히 동일한 이미지인지 보장하려면 이미지의 **digest라는 콘텐츠 식별값**을 사용할 수 있다.

## Kubernetes 필요 이유

컨테이너 수와 서버 수가 늘어나면 다음 문제를 관리해야 한다.

- 어떤 서버에서 컨테이너를 실행할 것인가?
- 프로세스나 서버에 장애가 생기면 어떻게 복구할 것인가?
- 요청이 늘면 실행 수를 어떻게 늘릴 것인가?
- 새 버전을 어떻게 순차적으로 배포할 것인가?
- 서비스 주소와 트래픽을 어떻게 관리할 것인가?

Kubernetes는 이러한 운영을 자동화하는 시스템이다.

예를 들어 “웹 애플리케이션 인스턴스 3개를 유지하라”는 상태를 선언하면, Kubernetes의 컨트롤러가 실제 상태를 그 선언에 맞추려고 동작한다.

정확히는 Kubernetes가 직접 배치하는 기본 단위는 **Pod**이며, 하나의 Pod에 하나 이상의 컨테이너가 들어간다.

**컨테이너를 사용한다고 반드시 Kubernetes가 필요한 것은 아니다.** 규모와 운영 요구에 따라 단일 서버와 Docker Compose만으로 충분할 수도 있다.

## 장점과 한계

### 주요 장점

- **실행 환경의 일관성:** 코드와 의존성을 함께 배포할 수 있다.
- **빠른 시작과 교체:** 별도 OS 부팅 없이 애플리케이션을 시작헌다.
- **서비스별 의존성 분리:** 서로 다른 런타임과 라이브러리를 사용하기 쉽다.
- **자동화에 적합:** 빌드·테스트·배포 과정을 코드로 관리하기 좋다.
- **수평 확장에 유리:** 같은 이미지로 인스턴스를 여러 개 만들 수 있다.

### 알아둘 한계

- **커널을 공유합니다.** 컨테이너 격리는 보안 구성에 영향을 받는다.
- **영구 데이터는 별도로 설계해야 합니다.** 저장소, 백업, 복구가 필요하다.
- **운영 복잡성이 추가됩니다.** 이미지, 네트워크, 볼륨, 로그를 관리해야 한다.
- **모든 플랫폼에서 같은 이미지가 실행되지는 않습니다.** CPU와 OS 호환성이 필요한다.
- **확장이 자동으로 해결되지는 않습니다.** 세션, 데이터베이스, 동시 처리 구조도 함께 고려해야 한다.

## 자주 하는 오해

| 오해                             | 실제로는                                          |
| ------------------------------ | --------------------------------------------- |
| 컨테이너는 작은 VM이다                  | 일반적으로 호스트 커널을 공유하는 격리된 프로세스이다.                |
| Docker가 곧 컨테이너다                | Docker는 컨테이너를 다루는 도구 중 하나이다.                  |
| 중지하면 데이터가 사라진다                 | 같은 컨테이너를 중지하는 것과 삭제하는 것은 다르다.                 |
| 컨테이너를 쓰면 자동으로 안전하다             | 권한, 마운트, 이미지, 커널 등의 보안 관리가 필요하다.              |
| 이미지에는 모든 운영 설정을 넣어야 한다         | 비밀번호 같은 비밀 정보와 환경별 설정은 실행 시 별도로 공급하는 편이 적절하다. |
| 컨테이너 하나에는 프로세스가 반드시 하나만 있어야 한다 | 여러 프로세스도 가능하지만, 하나의 주된 역할을 맡도록 구성하면 관리하기 쉽다.  |
| 컨테이너를 쓰려면 Kubernetes가 필수다      | 규모와 요구에 따라 다른 운영 방식도 가능하다.                    |

컨테이너의 핵심은 **이미지로 실행 환경을 묶고, 격리된 프로세스로 실행하며, 영구 데이터는 별도로 관리한다**는 세 가지아다.
