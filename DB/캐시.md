# 캐시(Cache)란

**캐시는 자주 사용하거나 다시 계산하기에 비용이 큰 데이터를, 빠르게 꺼내 쓸 수 있는 곳에 임시로 저장하는 방식**이다. 저장된 데이터나 그 저장 공간을 가리키기도 한다.

핵심 목적은 **같은 작업을 반복하지 않아 응답 속도를 높이고 자원 사용을 줄이는 것**이다.

예를 들어, 웹사이트에 처음 접속할 때 내려받은 로고 이미지를 기기에 저장해 두면, 다음 방문에서는 서버에서 다시 받지 않고 저장된 이미지를 사용할 수 있다.

---

## 캐시가 필요한 이유

컴퓨터에서 모든 데이터에 접근하는 비용이 같지는 않다.

- CPU가 가까운 메모리에서 값을 읽는 일은 매우 빠르다.
- 저장 장치에서 큰 파일을 읽는 일은 상대적으로 오래 걸린다.
- 네트워크를 통해 다른 서버에서 데이터를 가져오면 통신 시간도 필요하다.
- 복잡한 계산이나 데이터베이스 조회는 처리 자원을 많이 사용하기도 한다.

매번 이런 작업을 처음부터 수행하면 응답이 느려지고 시스템 부담이 커진다.

캐시는 이전 결과를 재사용해 다음과 같은 효과를 낸다.

| 효과         | 설명                                |
| ---------- | --------------------------------- |
| 응답 속도 향상   | 원본을 다시 가져오거나 계산하는 시간을 줄인다.        |
| 서버 부하 감소   | 같은 요청을 반복해서 처리할 필요가 줄어든다.         |
| 네트워크 사용 감소 | 이미 받은 데이터를 재사용해 전송량을 줄인다.         |
| 처리 비용 절감   | 데이터베이스 조회나 외부 API 호출 횟수를 줄일 수 있다. |

다만 캐시를 저장하고 관리하는 데에도 메모리와 처리 비용이 들어간다.

## 캐시 동작

일반적인 캐시의 동작은 다음과 같다.

```
데이터 요청
    ↓
캐시에 필요한 데이터가 있는가?
    ├─ 있고, 사용할 수 있음 → 캐시에서 반환
    └─ 없거나 유효하지 않음 → 원본 조회 또는 계산
                                  ↓
                              캐시에 저장
                                  ↓
                              결과 반환
```

상품 정보를 조회하는 서비스를 예로 들어본다.

### 처음 조회할 때

1. 사용자가 상품 정보를 요청한다.
2. 캐시에서 해당 상품을 찾는다.
3. 캐시에 없으면 데이터베이스에서 조회한다.
4. 조회한 정보를 캐시에 저장한다.
5. 사용자에게 결과를 반환한다.

### 다시 조회할 때

1. 같은 상품 정보를 요청한다.
2. 캐시에 저장된 정보가 있고 사용 가능한지 확인한다.
3. 사용 가능하면 데이터베이스를 조회하지 않고 반환한다.

이처럼 **첫 요청에서 수행한 작업을 다음 요청들이 재사용**하는 것이 기본 원리이다. 구현에 따라 미리 데이터를 채워 두기도 한다.

## 기본 용어

### 캐시 적중: Cache Hit

요청한 데이터를 캐시에서 찾아 사용할 수 있는 상태이다.

예를 들어, 브라우저에 저장된 이미지를 재사용하는 경우이다.

### 캐시 미스: Cache Miss

요청을 캐시만으로 처리할 수 없는 상태이다.

대표적인 이유는 다음과 같다.

- 처음 요청하는 데이터이다.
- 저장된 데이터가 만료되었다.
- 공간 부족으로 캐시에서 제거되었다.
- 요청을 구분하는 키가 이전과 다르다.

### 적중률: Hit Rate

전체 요청 중 캐시로 처리한 요청의 비율이다.

```
캐시 적중률 = 캐시 적중 횟수 ÷ 전체 요청 횟수 × 100
```

1,000번의 요청 중 900번을 캐시에서 처리했다면 적중률은 90%이다.

보통 적중률이 높을수록 유리하지만, **캐시 조회 자체의 비용과 줄어든 원본 처리 비용도 함께 봐야 한다.**

### 캐시 키: Cache Key

캐시에 저장된 데이터를 찾는 식별자이다.

```
키: product:123
값: 123번 상품의 정보
```

같은 상품이라도 언어나 통화에 따라 응답이 달라진다면 키에도 그 차이를 반영해야 한다.

```
product:123:ko:KRW
product:123:en:USD
```

키를 잘못 설계하면 서로 다른 요청이 같은 결과를 받아 오류가 생길 수 있다.

## 캐시 사용

캐시는 특정 프로그램의 기능이 아니라, 컴퓨터 시스템 여러 계층에서 사용하는 공통 기법이다.

|종류|저장하는 대상|목적|
|---|---|---|
|CPU 캐시|메모리 데이터와 명령어 일부|CPU가 RAM을 기다리는 시간을 줄임|
|운영체제 페이지 캐시|파일에서 읽은 데이터 등|저장 장치 접근을 줄임|
|브라우저 캐시|이미지, CSS, JavaScript, 응답 등|웹페이지 재방문 속도를 높임|
|DNS 캐시|도메인 이름 조회 결과|같은 주소를 반복해서 조회하는 일을 줄임|
|CDN 캐시|이미지, 영상 조각, 웹 응답 등|사용자와 가까운 서버에서 콘텐츠 제공|
|애플리케이션 캐시|조회 결과, 계산 결과 등|서비스 내부의 반복 작업을 줄임|

### CPU 캐시

CPU는 일반적으로 RAM보다 훨씬 빠르게 작동한다. 따라서 자주 사용하는 데이터와 명령어를 CPU에 가까운 작은 저장 공간에 보관한다.

대표적으로 L1, L2, L3 계층이 있으며, 일반적으로 CPU 코어에 가까운 계층일수록 작고 빠르다. 구체적인 구성은 프로세서마다 다르다.

### 브라우저 캐시

브라우저가 웹 리소스를 저장해 재사용하는 기능이다.

캐시 정책에 따라 저장된 리소스를 바로 사용하거나, 서버에 변경 여부를 확인한 뒤 재사용할 수 있다. 따라서 **캐시를 사용한다고 항상 네트워크 요청이 사라지는 것은 아니다.**

### CDN 캐시

CDN은 여러 지역의 서버를 통해 콘텐츠를 전달하는 시스템이다.

사용자가 원본 서버까지 매번 접근하는 대신 가까운 CDN 서버의 캐시를 이용하면 통신 지연과 원본 서버 부하를 줄일 수 있다.

### 애플리케이션 캐시

서비스가 직접 관리하는 캐시이다.

예를 들어, 매번 계산하기에 비싼 인기 게시글 목록을 일정 시간 저장해 여러 사용자에게 제공할 수 있다. 프로그램 내부 메모리에 두거나, Redis 같은 별도 시스템에 저장하기도 한다.

## 캐시가 효과적인 이유: 지역성

캐시는 데이터 접근에 반복되는 패턴이 있다는 점을 활용한다. 이를 **지역성(Locality)**이라고 한다.

### 시간 지역성

**최근 사용한 데이터를 가까운 미래에 다시 사용할 가능성이 높다**는 특성이다.

예를 들어 다음과 같다.

- 인기 상품의 상세 정보가 반복해서 조회된다.
- 반복문에서 같은 변수를 여러 번 사용한다.
- 여러 페이지에서 같은 로고 이미지를 사용한다.

### 공간 지역성

**사용한 데이터와 가까이 있는 데이터를 곧 사용할 가능성이 높다**는 특성이다.

예를 들어 배열의 첫 번째 요소를 읽은 뒤 두 번째, 세 번째 요소를 순서대로 읽는 경우이다.

CPU 캐시는 이러한 특성을 활용해 데이터를 일정한 크기의 블록 단위로 가져온다.

모든 캐시가 두 특성을 똑같이 활용하는 것은 아니다. 애플리케이션 캐시는 주로 요청의 반복성을 활용하고, CPU 캐시는 시간·공간 지역성을 모두 적극적으로 활용한다.

## 원본 변경

캐시는 원본의 복사본이나 원본에서 계산한 결과를 저장하는 경우가 많다. 따라서 원본과 캐시가 달라질 수 있다.

예를 들어 다음 상황을 생각해 볼 수 있다.

1. 상품 가격 10,000원을 캐시에 저장한다.
2. 데이터베이스의 가격이 12,000원으로 바뀐다.
3. 캐시는 여전히 10,000원을 가지고 있다.
4. 사용자가 오래된 가격을 보게 된다.

이런 데이터를 **오래된 데이터(Stale Data)**라고 한다.

따라서 캐시 설계에서는 “얼마나 빨라지는가”만큼 **“얼마나 오래된 정보까지 허용할 것인가”**가 중요하다.

### 유효 시간 설정: TTL

TTL은 캐시 항목의 유효 기간이다.

```
상품 정보 TTL = 60초
→ 정해진 유효 기간이 지나면 갱신하거나 다시 조회
```

- TTL이 짧으면 최신 정보를 반영하기 쉽지만 원본 조회가 늘어난다.
- TTL이 길면 캐시를 더 오래 재사용하지만 오래된 정보를 제공할 가능성이 커진다.

만료된 항목이 저장 공간에서 실제로 삭제되는 시점은 구현에 따라 다를 수 있다.

### 변경 시 무효화

원본이 변경되면 관련 캐시를 삭제하거나 사용할 수 없도록 표시한다.

```
상품 정보 수정
    ↓
데이터베이스 반영
    ↓
해당 상품 캐시 삭제
    ↓
다음 조회에서 새로운 정보 저장
```

이를 **캐시 무효화(Cache Invalidation)**라고 한다.

다만 관련 캐시를 빠짐없이 찾아야 하고, 동시에 들어오는 읽기와 쓰기 요청의 순서도 고려해야 한다.

### 캐시 값 갱신

원본 변경 시 캐시도 새 값으로 바꾼다.

새 값을 빠르게 제공할 수 있지만, 데이터베이스와 캐시 중 한쪽만 갱신되는 실패 상황을 처리해야 한다.

### 버전이 있는 주소나 키 사용

내용이 바뀔 때 캐시 키나 파일 주소도 변경한다.

```
기존: /assets/app.a1b2.js
변경: /assets/app.c3d4.js
```

새 버전이 다른 주소를 사용하므로 이전 캐시와 구분된다. 정적 파일 배포에서 자주 쓰는 방식이다.

## 캐시의 읽기/쓰기

다음 용어들은 캐시와 원본을 연결하는 대표적인 접근 방식이다. 읽기 방식과 쓰기 방식은 조합해서 사용할 수 있다.

### Cache-Aside: 애플리케이션이 캐시를 관리

1. 캐시를 조회한다.
2. 없으면 원본을 조회한다.
3. 결과를 캐시에 저장한다.

단순하고 필요한 데이터만 저장할 수 있지만, 애플리케이션이 만료와 무효화를 관리해야 한다. 캐시 미스가 발생한 요청은 원본 조회 시간까지 기다려야 한다.

### Read-Through: 캐시 계층이 원본 조회까지 담당

애플리케이션은 캐시 계층에 데이터를 요청한다. 데이터가 없으면 캐시 계층이 원본을 조회하고 저장해 반환한다.

Cache-Aside와 흐름은 비슷하지만, **원본 조회를 누가 책임지는지**가 다르다.

### Write-Through: 쓰기를 원본에도 동기적으로 반영

쓰기 요청을 처리할 때 캐시와 원본 저장소에 동기적으로 반영한다.

쓰기 완료까지 기다리는 시간이 늘 수 있으며, 실패나 동시 요청 처리 방식에 따라 일관성이 달라진다.

### Write-Behind: 원본에는 나중에 반영

캐시에 먼저 쓰고, 원본 저장소에는 비동기적으로 반영한다.

빠르게 응답하거나 여러 쓰기를 묶어서 처리할 수 있지만, 원본에 반영되기 전 장애가 발생하면 데이터가 유실될 수 있어 내구성 설계가 필요하다.

## 캐시 공간의 초과

캐시 공간은 유한하므로 일부 데이터를 제거해야 한다. 이때 사용하는 규칙을 **교체 정책 또는 퇴거 정책(Eviction Policy)**이라고 한다.

| 정책     | 제거 기준              | 특징                |
| ------ | ------------------ | ----------------- |
| LRU    | 가장 오랫동안 사용하지 않은 항목 | 최근에 사용한 데이터를 남긴다. |
| LFU    | 사용 빈도가 가장 낮은 항목    | 자주 사용되는 데이터를 남긴다. |
| FIFO   | 가장 먼저 저장한 항목       | 저장 순서를 기준으로 제거한다. |
| Random | 임의의 항목             | 선택 방식이 단순하다.      |

**만료와 퇴거는 목적이 다르다.**

- **만료:** 유효 기간이 지나서 더 이상 그대로 사용할 수 없다.
- **퇴거:** 공간 확보 등을 위해 캐시에서 제거한다.

따라서 TTL이 남아 있어도 공간 부족으로 먼저 제거될 수 있다.

## 캐시를 사용하면 생길 수 있는 문제

### 오래된 데이터 제공

원본 변경이 캐시에 즉시 반영되지 않을 수 있다.

정보별로 허용 가능한 지연 시간을 정하고, TTL과 무효화 방식을 선택해야 한다.

### 동시 미스로 인한 요청 폭증

인기 데이터의 캐시가 만료되는 순간 수많은 요청이 원본으로 몰릴 수 있다. 이를 **캐시 스탬피드(Cache Stampede)**라고 한다.

대표적인 대응 방법은 다음과 같다.

- 같은 데이터의 갱신 작업을 하나로 합친다.
- 여러 항목의 만료 시점이 겹치지 않도록 TTL에 작은 무작위 차이를 둔다.
- 만료 전에 미리 갱신한다.
- 잠시 오래된 데이터를 제공하면서 백그라운드에서 갱신한다.

마지막 방식은 오래된 응답을 잠깐 허용할 수 있는 데이터에 적합하다.

### 사용자별 데이터 혼동

개인화된 응답을 저장하면서 사용자나 권한 차이를 제대로 구분하지 않으면 다른 사용자의 정보가 반환될 수 있다.

캐시 키와 공유 범위에 응답을 바꾸는 조건을 반영해야 한다.

### 캐시 장애가 원본 장애로 이어짐

캐시가 정상일 때 대부분의 요청을 처리하던 서비스는, 캐시가 중단되면 원본 서버에 요청이 갑자기 몰릴 수 있다.

따라서 캐시 장애 시 원본이 감당할 부하와 요청 제한 방식도 고려해야 한다.

### 기대보다 낮은 효과

매번 요청 내용이 달라서 재사용이 거의 없거나, 원본 작업이 이미 매우 저렴하다면 캐시 효과가 작을 수 있다.

캐시 조회·저장·직렬화 비용 때문에 오히려 느려지는 경우도 있다.

## 캐시와 비슷한 개념의 차이

| 개념     | 주된 목적                            | 캐시와의 차이                          |
| ------ | -------------------------------- | -------------------------------- |
| 데이터베이스 | 데이터를 저장하고 조회                     | 보통 데이터의 기준이 되는 원본을 관리한다.         |
| 버퍼     | 처리 속도나 단위가 다른 작업 사이에서 데이터를 잠시 보관 | 이미 얻은 결과의 재사용보다 전달과 처리 조율이 목적이다. |
| 쿠키     | 브라우저가 작은 값을 저장하고 조건에 맞춰 서버로 전달   | 로그인 상태나 설정 등을 전달하는 수단이다.         |
| 세션     | 여러 요청 사이에서 사용자 상태를 유지            | 데이터 재사용보다 상태 관리가 목적이다.           |
| 메모이제이션 | 같은 함수 입력에 대해 이전 계산 결과를 재사용       | 함수 결과에 적용한 캐싱 기법이다.              |

예를 들어 영상 재생 중 앞으로 사용할 데이터를 미리 받아 두는 것은 버퍼링이고, 받은 데이터를 나중에 다시 사용하려고 보관하는 것은 캐싱이다. 하나의 시스템에서 두 역할을 함께 수행할 수도 있다.

또한 Redis처럼 같은 기술을 캐시나 세션 저장소 등 여러 용도로 사용할 수 있다. **기술의 이름보다 어떤 역할로 사용하는지가 중요하다.**

## 캐시 삭제

정상적으로 설계된 캐시는 보통 원본에서 다시 만들 수 있는 데이터를 담눈다.

캐시를 삭제하면 다음과 같은 일이 일어난다.

- 다음 요청에서 원본을 다시 가져오거나 계산한다.
- 캐시가 다시 채워질 때까지 일시적으로 느려질 수 있다.
- 네트워크와 원본 서버 사용량이 늘어날 수 있다.
- 오래되거나 손상된 캐시 때문에 발생한 문제가 해결되기도 한다.

브라우저의 **캐시 삭제**와 **쿠키·사이트 데이터 삭제**는 구분해야 한다. 캐시만 삭제하면 보통 로그인은 유지되지만, 쿠키나 사이트 데이터를 함께 지우면 로그인이 풀리거나 저장된 설정이 사라질 수 있다.

## 캐시 데이터 구분

다음 특성을 가진 데이터는 캐시의 효과를 보기 쉽다.

- 같은 데이터가 반복해서 요청된다.
- 원본 조회나 계산 비용이 크다.
- 변경 빈도가 낮다.
- 일정 수준의 갱신 지연을 허용할 수 있다.
- 저장 공간 대비 재사용 효과가 크다.

예를 들면 공통 이미지, 상품 설명, 반복되는 집계 결과 등이 있다.

반대로 재고나 결제 상태처럼 최신 상태가 중요한 데이터는 캐시 사용 범위를 신중하게 정해야 한다. 화면 표시에 캐시를 활용하더라도, 주문 확정 같은 작업에서는 원본을 기준으로 다시 검증할 수 있다.
