## N+1 문제

N+1 문제는 연관관계가 있는 엔티티를 조회할 때,

1. 부모 데이터를 조회하는 SQL이 1번 실행되고
2. 조회된 부모 N개 각각에 대해 자식 데이터를 조회하는 SQL이 추가로 N번 실행되는 현상이다.

즉, 원래 한 번이나 소수의 쿼리로 처리할 수 있는 작업에 총 `1 + N`번의 쿼리가 발생한다.

예를 들어 팀과 회원의 관계가 다음과 같다고 가정하면

```
@Entity
public class Team {

    @Id
    @GeneratedValue
    private Long id;

    private String name;

    @OneToMany(mappedBy = "team", fetch = FetchType.LAZY)
    private List<Member> members = new ArrayList<>();
}
```

```
@Entity
public class Member {

    @Id
    @GeneratedValue
    private Long id;

    private String name;

    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "team_id")
    private Team team;
}
```

팀을 조회한 뒤 각 팀의 회원 목록에 접근한다고 한다.

```
List<Team> teams = teamRepository.findAll();

for (Team team : teams) {
    System.out.println(team.getMembers().size());
}
```

처음에는 팀 전체를 조회하는 쿼리가 실행된다.

```
SELECT *
FROM team;
```

팀이 100개 조회되고, 반복문에서 각 팀의 `members`에 접근하면 팀별 회원 조회 쿼리가 추가로 실행된다.

```
SELECT * FROM member WHERE team_id = 1;
SELECT * FROM member WHERE team_id = 2;
SELECT * FROM member WHERE team_id = 3;
...
SELECT * FROM member WHERE team_id = 100;
```

결과적으로 SQL이 총 101번 실행된다.

```
팀 조회 1번 + 회원 조회 100번 = 총 101번
```

## 발생 원인

핵심 원인은 **객체 그래프를 탐색하는 방식과 관계형 데이터베이스가 데이터를 조회하는 방식의 차이**이다.

애플리케이션에서는 다음처럼 자연스럽게 연관 객체에 접근한다.

```
team.getMembers();
member.getTeam();
```

하지만 데이터베이스는 연관 객체가 자동으로 따라오는 구조가 아니므로 필요한 데이터를 가져오려면 별도의 SQL이 필요하다.

특히 지연 로딩을 사용하면 처음 엔티티를 조회할 때 연관 데이터를 가져오지 않다. 이후 연관 필드에 실제로 접근하는 순간 추가 SQL이 실행된다.

```
@ManyToOne(fetch = FetchType.LAZY)
private Team team;
```

중요한 점은 **LAZY 자체가 잘못된 것은 아니라는 것**이다. 지연 로딩은 불필요한 데이터를 조회하지 않도록 해주는 일반적으로 권장되는 전략이다. 문제는 여러 엔티티를 조회한 다음 반복문에서 연관 데이터를 하나씩 초기화할 때 발생한다.

### EAGER

```
@ManyToOne(fetch = FetchType.EAGER)
private Team team;
```

단순히 즉시 로딩으로 변경한다고 해서 N+1이 항상 해결되는 것은 아니다.

JPA가 연관 엔티티를 반드시 함께 로딩하도록 만들 뿐, 하나의 조인 SQL로 조회한다는 보장은 없기 때문이다. 상황에 따라 부모를 먼저 조회하고 연관 엔티티를 추가 SQL로 가져와 여전히 N+1이 발생할 수 있다.

또한 EAGER는 해당 연관관계가 필요하지 않은 API에서도 데이터를 무조건 로딩하게 만들며, 연관관계가 복잡해질수록 불필요한 조회와 예측하기 어려운 SQL을 유발한다.

따라서 보통 다음 원칙을 사용한다.

> 엔티티의 연관관계는 기본적으로 LAZY로 설정하고, 필요한 조회에서만 명시적으로 함께 가져온다.

## 주요 해결 방법

### Fetch Join

JPQL의 `fetch join`을 사용해 부모와 연관 데이터를 하나의 SQL로 조회하는 방식이다.

```
@Query("""
    SELECT DISTINCT t
    FROM Team t
    JOIN FETCH t.members
""")
List<Team> findAllWithMembers();
```

대략 다음과 같은 SQL이 실행된다.

```
SELECT t.*, m.*
FROM team t
JOIN member m ON m.team_id = t.id;
```

부모와 자식을 한 번에 조회하므로 반복문에서 `members`에 접근해도 추가 쿼리가 발생하지 않는다.

```
List<Team> teams = teamRepository.findAllWithMembers();

for (Team team : teams) {
    System.out.println(team.getMembers().size());
}
```

#### `DISTINCT`

일대다 관계를 조인하면 데이터베이스 조회 결과는 자식 수만큼 부모 행이 중복된다.

```
Team A - Member 1
Team A - Member 2
Team A - Member 3
```

그래서 JPQL에 `DISTINCT`를 사용해 반환되는 부모 엔티티의 중복을 제거한다.

```
SELECT DISTINCT t
FROM Team t
JOIN FETCH t.members
```

#### 장점

- 한 번의 쿼리로 필요한 데이터를 조회할 수 있다.
- 조회되는 SQL을 비교적 명확하게 통제할 수 있다.
- 특정 화면이나 API의 조회 요구사항을 표현하기 좋다.
- 단일 연관관계를 조회할 때 성능이 좋다.

#### 단점과 주의점

- 컬렉션 fetch join과 페이징을 함께 사용하기 어렵다.
- 여러 개의 일대다 컬렉션을 동시에 fetch join하면 카테시안 곱으로 조회 결과가 급격히 증가할 수 있다.
- Hibernate에서는 여러 `List` 형태의 bag 컬렉션을 동시에 fetch join할 경우 `MultipleBagFetchException`이 발생할 수 있다.
- 조회 메서드마다 JPQL을 작성해야 할 수 있다.

### `@EntityGraph`

Spring Data JPA에서 특정 조회 시 함께 로딩할 연관관계를 선언적으로 지정하는 방법이다.

```
@EntityGraph(attributePaths = {"members"})
@Query("SELECT t FROM Team t")
List<Team> findAllWithMembers();
```

간단한 조회라면 다음처럼 쿼리 메서드에도 적용할 수 있다.

```
@EntityGraph(attributePaths = {"members"})
List<Team> findByName(String name);
```

중첩 관계도 지정할 수 있다.

```
@EntityGraph(attributePaths = {
    "members",
    "members.profile"
})
List<Team> findAllWithMembersAndProfile();
```

#### 장점

- JPQL fetch join보다 선언적으로 표현할 수 있다.
- Spring Data JPA 쿼리 메서드와 쉽게 결합할 수 있다.
- 엔티티 매핑의 기본 fetch 전략을 바꾸지 않고 조회별 로딩 전략을 정할 수 있다.

#### 단점

- 복잡한 조건, 동적 쿼리 또는 세밀한 조인을 표현하기에는 제한적이다.
- 여러 컬렉션을 가져오면 fetch join과 마찬가지로 결과 행이 크게 증가할 수 있다.
- 실제 생성되는 SQL을 확인하지 않으면 성능을 잘못 판단하기 쉽다.

### Batch Fetching

연관 엔티티를 하나씩 조회하지 않고, 여러 엔티티의 식별자를 모아 `IN` 쿼리로 한꺼번에 조회하는 방식이다.

Hibernate 설정으로 전역 배치 크기를 지정할 수 있다.

```
spring:
  jpa:
    properties:
      hibernate:
        default_batch_fetch_size: 100
```

또는 특정 연관관계에만 설정할 수 있다.

```
@OneToMany(mappedBy = "team")
@BatchSize(size = 100)
private List<Member> members = new ArrayList<>();
```

배치 크기가 설정되어 있으면 다음처럼 팀별 쿼리를 각각 실행하지 않는다.

```
SELECT *
FROM member
WHERE team_id IN (1, 2, 3, ..., 100);
```

쿼리 수는 대략 다음과 같이 줄어든다.

```
기존: 1 + N
배치 적용: 1 + ceil(N / batchSize)
```

팀이 1,000개이고 배치 크기가 100이라면 대략 부모 조회 1번과 자식 조회 10번으로 처리할 수 있다.

#### 장점

- N+1을 소수의 쿼리로 줄일 수 있다.
- 페이징과 컬렉션 조회를 함께 처리하기 좋다.
- 여러 곳에서 발생하는 지연 로딩 쿼리를 전반적으로 최적화할 수 있다.
- fetch join처럼 하나의 거대한 결과 집합을 만들지 않다.

#### 단점

- 쿼리가 정확히 1번으로 줄어드는 것은 아다.
- 배치 크기를 지나치게 크게 설정하면 긴 `IN` 절이 만들어진다.
- 한 번에 조회되는 데이터량과 DB 제한을 고려해 크기를 조절해야 한다.
- N+1 문제를 완전히 없애기보다 완화하는 방식에 가깝다.

### DTO 직접 조회

API 응답에 필요한 데이터만 DTO로 직접 조회하는 방식이다.

```
public record MemberSummary(
    Long memberId,
    String memberName,
    Long teamId,
    String teamName
) {
}
```

```
@Query("""
    SELECT new com.example.MemberSummary(
        m.id,
        m.name,
        t.id,
        t.name
    )
    FROM Member m
    JOIN m.team t
""")
List<MemberSummary> findMemberSummaries();
```

QueryDSL을 사용하면 다음과 같은 방식으로 구현할 수 있다.

```
return queryFactory
    .select(Projections.constructor(
        MemberSummary.class,
        member.id,
        member.name,
        team.id,
        team.name
    ))
    .from(member)
    .join(member.team, team)
    .fetch();
```

#### 장점

- API에 필요한 컬럼만 조회할 수 있다.
- 영속성 컨텍스트와 지연 로딩의 영향을 비교적 적게 받는다.
- 대량 조회나 조회 전용 API에서 성능을 세밀하게 최적화할 수 있다.
- 엔티티 구조가 API 응답 구조에 직접 노출되는 것을 막을 수 있다.

#### 단점

- DTO와 조회 코드가 추가된다.
- 화면이나 응답 형태가 바뀌면 쿼리도 수정해야 할 수 있다.
- 조회 결과를 수정한 뒤 자동으로 변경 감지하는 엔티티 방식과는 목적이 다르다.
- 일대다 데이터를 계층형 DTO로 조립하려면 추가 그룹화가 필요할 수 있다.

### Hibernate Subselect Fetch

한 컬렉션을 초기화할 때, 앞에서 조회한 여러 부모의 컬렉션을 서브쿼리를 이용해 함께 로딩하는 방법이다.

```
@OneToMany(mappedBy = "team")
@Fetch(FetchMode.SUBSELECT)
private List<Member> members = new ArrayList<>();
```

대략 다음과 같은 SQL 형태가 만들어질 수 있다.

```
SELECT *
FROM member
WHERE team_id IN (
    SELECT id
    FROM team
);
```

특정 상황에서는 유용하지만 조회 범위를 예상하기 어렵고 Hibernate에 종속되므로, 일반적인 첫 번째 선택으로 사용하기보다는 SQL을 충분히 검증한 뒤 제한적으로 적용하는 편이 좋다.

## 선택 기준

| 상황                                        | 적합한 방법                            |
| ----------------------------------------- | --------------------------------- |
| 단건 또는 소규모 목록에서 연관 엔티티가 반드시 필요함            | Fetch Join                        |
| Spring Data JPA의 간단한 조회 메서드에서 연관관계만 추가 로딩 | `@EntityGraph`                    |
| 일대다 컬렉션과 페이징을 함께 사용                       | Batch Fetching                    |
| 대량 조회 또는 읽기 전용 API                        | DTO 직접 조회                         |
| 조회 조건이 복잡하고 동적임                           | QueryDSL DTO 조회 또는 조건부 Fetch Join |
| 여러 컬렉션을 동시에 조회                            | Fetch Join 남용을 피하고 Batch/분리 조회 고려 |
| 단순한 `ManyToOne`, `OneToOne` 연관관계          | Fetch Join이 비교적 안전                |
| 조회마다 필요한 연관관계가 다름                         | LAZY 유지 후 조회별 전략 지정               |


## N+1 문제 발견 방법

N+1은 코드만 보고 놓칠 수 있으므로 실제 실행되는 SQL을 확인해야 한다.

개발 환경에서 SQL 로그와 통계를 활성화할 수 있다.

```
spring:
  jpa:
    show-sql: true
    properties:
      hibernate:
        format_sql: true
        generate_statistics: true
```

확인할 사항은 다음과 같다.

- 한 번의 API 요청에서 같은 형태의 SQL이 반복되는가?
- 반복 횟수가 조회된 엔티티 수에 비례하는가?
- 반복문이나 DTO 변환 과정에서 지연 로딩이 발생하는가?
- JSON 직렬화 과정에서 연관 객체가 자동으로 탐색되는가?
- 쿼리 수는 적더라도 조인 결과 행이 지나치게 많지 않은가?

테스트에서 쿼리 실행 횟수를 검증하는 것도 좋다.

```
statistics.clear();

service.getTeams();

assertThat(statistics.getPrepareStatementCount())
    .isLessThanOrEqualTo(2);
```
