# N+1 문제란?

N+1 문제는 데이터 목록을 조회하기 위해 **쿼리 1번**을 실행한 뒤, 목록의 각 항목에 연결된 데이터를 가져오려고 **항목 수 N만큼 추가 쿼리**를 실행하는 성능 문제이다.

예를 들어 게시글 100개와 각 게시글의 작성자를 보여준다고 가정하면.

1. 게시글 100개를 가져오는 쿼리: 1번
2. 각 게시글의 작성자를 가져오는 쿼리: 100번
3. 총 쿼리 수: `1 + 100 = 101번`

여기서 목록의 항목 수가 `N`이므로 이를 **N+1 문제**라고 부른다.

---

## 기본 예시

다음과 같은 테이블이 존재하면

```
CREATE TABLE users (
    id BIGINT PRIMARY KEY,
    name VARCHAR(100)
);

CREATE TABLE posts (
    id BIGINT PRIMARY KEY,
    title VARCHAR(200),
    user_id BIGINT,
    FOREIGN KEY (user_id) REFERENCES users(id)
);
```

게시글 목록과 작성자 이름을 출력하는 애플리케이션 코드를 단순하게 작성하면 다음과 같은 흐름이 될 수 있다.

```
posts = db.query("SELECT * FROM posts")

for post in posts:
    user = db.query(
        "SELECT * FROM users WHERE id = ?",
        post.user_id
    )

    print(post.title, user.name)
```

실제로 실행되는 SQL은 다음과 비슷하다.

```
-- 최초 목록 조회: 1번
SELECT * FROM posts;

-- 게시글마다 작성자 조회: N번
SELECT * FROM users WHERE id = 1;
SELECT * FROM users WHERE id = 2;
SELECT * FROM users WHERE id = 3;
-- ...
```

게시글이 10개라면 11번, 1,000개라면 최대 1,001번의 쿼리가 실행될 수 있다.

---

# 문제 이유

단순히 쿼리 개수가 많다는 것만이 문제는 아니다. 쿼리마다 여러 비용이 발생한다.

- 애플리케이션과 DB 사이의 네트워크 왕복
- DB 연결 획득 및 반환
- SQL 파싱과 실행 계획 처리
- 인덱스 탐색
- 결과 직렬화와 역직렬화
- ORM 객체 생성
- 트랜잭션과 락 관련 부하

개별 쿼리가 1ms밖에 걸리지 않더라도 1,000번 실행하면 상당한 지연이 생긴다. 특히 애플리케이션 서버와 DB가 서로 다른 네트워크에 있으면 왕복 비용이 커진다.

또한 데이터가 늘어날수록 쿼리 수가 함께 증가한다.

```
데이터 10개    → 11개 쿼리
데이터 100개   → 101개 쿼리
데이터 1,000개 → 1,001개 쿼리
```

개발 환경에서는 데이터가 적어 문제가 드러나지 않다가 운영 환경에서 갑자기 느려지는 경우가 많은 이유이다.

# ORM에서 자주 발생하는 이유

N+1 문제는 SQL 자체의 문제라기보다, 주로 ORM의 연관관계 로딩 방식 때문에 발생한다.

예를 들어 게시글과 작성자가 다음과 같은 객체 관계를 가진다고 하면

```
@Entity
public class Post {

    @Id
    private Long id;

    private String title;

    @ManyToOne(fetch = FetchType.LAZY)
    private User author;
}
```

게시글 조회 시

```
List<Post> posts = postRepository.findAll();
```

이 시점에는 다음 쿼리만 실행될 수 있다.

```
SELECT * FROM posts;
```

`author`가 지연 로딩되어 있으면 아직 사용자 데이터는 조회되지 않는다. 이후 작성자 이름에 접근할 때 추가 쿼리가 실행된다.

```
for (Post post : posts) {
    System.out.println(post.getAuthor().getName());
}
```

개념적으로 다음 SQL이 반복된다.

```
SELECT * FROM users WHERE id = ?;
```

ORM은 코드상으로는 객체 필드를 읽는 것처럼 보이게 만들기 때문에, 개발자가 추가 SQL 실행을 놓치기 쉽다.

# Lazy Loading과 Eager Loading

## 지연 로딩

지연 로딩은 연관된 객체가 실제로 필요할 때 조회하는 방식이다.

```
post.getAuthor().getName();
```

필요하지 않은 데이터를 미리 가져오지 않는다는 장점이 있지만, 반복문 안에서 접근하면 N+1 문제를 만들기 쉽다.

지연 로딩 자체가 나쁜 것은 아닙니다. 문제는 **여러 객체의 지연 로딩을 개별적으로 발생시키는 것**이다.

## 즉시 로딩

즉시 로딩은 부모 객체를 조회할 때 연관된 객체도 바로 불러오는 방식이다.

```
@ManyToOne(fetch = FetchType.EAGER)
private User author;
```

하지만 즉시 로딩으로 변경한다고 항상 N+1 문제가 해결되는 것은 아니다. ORM 구현과 조회 방식에 따라 최초 쿼리 후 연관 데이터를 각각 별도 쿼리로 가져올 수도 있다.

또한 모든 연관관계를 즉시 로딩으로 설정하면 다음과 같은 다른 문제가 생다.

- 사용하지 않는 데이터까지 항상 조회
- 예상하기 어려운 대형 JOIN 발생
- 객체 그래프가 커지면서 메모리 사용 증가
- 순환 연관관계 처리 문제
- 페이지네이션과 중복 데이터 문제

따라서 전역적으로 즉시 로딩을 설정하기보다, **특정 조회 요구사항에 맞춰 로딩 전략을 지정하는 방식**이 일반적으로 안전하다.

# 대표적인 해결 방법

## 1. JOIN으로 한 번에 조회

가장 직접적인 해결책은 부모와 연관 데이터를 JOIN하여 한 번에 가져오는 것이다.

```
SELECT
    p.id,
    p.title,
    u.id AS user_id,
    u.name AS user_name
FROM posts p
JOIN users u ON u.id = p.user_id;
```

이제 게시글이 몇 개이든 쿼리는 한 번만 실행된다.

```
기존: 1 + N개 쿼리
JOIN: 1개 쿼리
```

JPA/Hibernate에서는 `JOIN FETCH`를 사용할 수 있다.

```
@Query("""
    SELECT p
    FROM Post p
    JOIN FETCH p.author
""")
List<Post> findAllWithAuthor();
```

일반 `JOIN`과 `FETCH JOIN`은 목적이 조금 다르다.

```
SELECT p
FROM Post p
JOIN p.author a
```

일반 JOIN은 작성자를 조건이나 정렬에 사용할 수 있지만, 반드시 작성자 엔티티까지 로딩하는 것은 아니다.

```
SELECT p
FROM Post p
JOIN FETCH p.author
```

FETCH JOIN은 연관된 작성자까지 함께 로딩하라고 ORM에 명시한다.

### 장점

- 쿼리 횟수가 크게 감소
- 필요한 연관 데이터를 명확하게 조회
- 다대일이나 일대일 관계에서 효과적

### 주의점

일대다 컬렉션을 JOIN하면 부모 행이 자식 수만큼 중복될 수 있다.

게시글 하나에 댓글이 100개라면 결과 집합에는 게시글 정보도 100번 반복된다.

```
SELECT p.*, c.*
FROM posts p
LEFT JOIN comments c ON c.post_id = p.id;
```

ORM에서는 중복 엔티티를 제거하기 위해 `DISTINCT`를 사용하기도 한다.

```
SELECT DISTINCT p
FROM Post p
LEFT JOIN FETCH p.comments
```

하지만 SQL 결과의 크기 자체가 줄어드는지는 ORM과 쿼리 설정에 따라 다르다. 특히 여러 개의 일대다 컬렉션을 동시에 JOIN하면 결과 행 수가 곱셈으로 증가할 수 있다.

```
게시글 1개
댓글 100개
태그 20개

댓글과 태그를 모두 JOIN → 최대 100 × 20 = 2,000행
```

이런 현상을 카테시안 곱 또는 JOIN 결과 폭증 문제라고 한다.

## 2. IN 쿼리로 일괄 조회

부모 목록을 먼저 조회하고, 부모가 참조하는 연관 데이터의 ID를 모아서 한 번에 조회할 수도 있다.

```
-- 1. 게시글 조회
SELECT * FROM posts;

-- 2. 게시글 작성자를 일괄 조회
SELECT *
FROM users
WHERE id IN (1, 2, 3, 4, 5);
```

총 쿼리는 보통 2번입니다.

```
기존: 1 + N
배치 조회: 1 + 1
```

애플리케이션에서는 조회한 사용자를 맵으로 만들어 결합할 수 있다.

```
posts = get_posts()

user_ids = {post.user_id for post in posts}
users = get_users_by_ids(user_ids)

users_by_id = {
    user.id: user
    for user in users
}

for post in posts:
    post.author = users_by_id[post.user_id]
```

### 장점

- JOIN 결과 중복을 줄일 수 있음
- 여러 부모가 같은 연관 객체를 참조할 때 효율적
- 컬렉션 관계와 페이지네이션을 함께 처리하기 편함
- DataLoader나 ORM 배치 로딩의 기반이 됨

### 주의점

ID가 매우 많으면 `IN` 절이 지나치게 커질 수 있습니다. 이때는 일정 크기로 나누어 조회해야 한다.

```
ID 10,000개
→ 500개씩 20번 조회
```

쿼리가 한 번은 아니지만, N번보다 훨씬 적고 DB 제한에도 대응할 수 있다.

## 3. ORM의 Batch Fetching 사용

Hibernate 같은 ORM은 여러 프록시나 컬렉션을 일정 크기로 묶어 조회하는 배치 기능을 제공한다.

예를 들어 Hibernate/JPA에서는 다음과 같이 설정할 수 있다.

```
hibernate.default_batch_fetch_size=100
```

또는 특정 연관관계에 적용할 수 있다.

```
@BatchSize(size = 100)
@OneToMany(mappedBy = "post")
private List<Comment> comments;
```

기존에는 다음처럼 실행되던 것이:

```
SELECT * FROM comments WHERE post_id = 1;
SELECT * FROM comments WHERE post_id = 2;
SELECT * FROM comments WHERE post_id = 3;
```

다음처럼 묶일 수 있다.

```
SELECT *
FROM comments
WHERE post_id IN (1, 2, 3);
```

배치 크기가 100이고 부모가 1,000개라면 대략 다음과 같이 줄어든다.

```
기존: 1 + 1,000개 쿼리
배치: 1 + 10개 쿼리
```

FETCH JOIN을 적용하기 어려운 컬렉션이나 페이지 조회에서 유용하다.

---

## 4. Entity Graph 사용

JPA에서는 Entity Graph로 특정 조회에서 로딩할 연관관계를 지정할 수 있다.

```
@EntityGraph(attributePaths = {"author"})
List<Post> findAll();
```

또는 여러 관계를 지정할 수 있습니다.

```
@EntityGraph(attributePaths = {
    "author",
    "category"
})
List<Post> findAll();
```

JPQL에 FETCH JOIN을 직접 작성하지 않고도 조회별 로딩 전략을 선언할 수 있다는 장점이 있다.

다만 Entity Graph도 내부적으로 JOIN이나 추가 쿼리를 사용할 수 있으므로, 실제 SQL을 확인해야 한다.

## 5. DTO Projection 사용

화면이나 API에 필요한 데이터가 일부뿐이라면 엔티티 전체를 로딩하지 않고 DTO 형태로 직접 조회하는 방법이 효과적이다.

```
SELECT
    p.id,
    p.title,
    u.name AS author_name
FROM posts p
JOIN users u ON u.id = p.user_id;
```

JPA에서는 다음과 같이 작성할 수 있다.

```
@Query("""
    SELECT new com.example.PostSummary(
        p.id,
        p.title,
        a.name
    )
    FROM Post p
    JOIN p.author a
""")
List<PostSummary> findPostSummaries();
```

### 장점

- 필요한 열만 조회
- 불필요한 엔티티와 연관관계 로딩 방지
- 읽기 전용 API나 목록 화면에서 효율적
- 쿼리 실행 시점을 예측하기 쉬움

### 단점

- 조회 요구사항별 DTO와 쿼리가 늘어날 수 있음
- 엔티티 변경 감지 같은 ORM 기능을 직접 활용할 수 없음
- 범용성이 낮아질 수 있음

목록 화면에서는 엔티티 그래프 전체보다 DTO Projection이 더 적합한 경우가 많다.

## 6. DataLoader 패턴

GraphQL에서는 필드 리졸버가 각각 독립적으로 실행되면서 N+1 문제가 자주 발생한다.

```
query {
  posts {
    id
    title
    author {
      name
    }
  }
}
```

단순 리졸버는 게시글마다 작성자를 조회할 수 있다.

```
Post: {
  author(post) {
    return userRepository.findById(post.userId);
  }
}
```

DataLoader는 같은 요청 사이클에서 발생한 여러 ID 조회를 모아서 배치 처리한다.

```
const userLoader = new DataLoader(async (ids) => {
  const users = await userRepository.findByIds(ids);
  const usersById = new Map(users.map(user => [user.id, user]));

  return ids.map(id => usersById.get(id));
});
```

리졸버에서는 다음처럼 사용한다.

```
Post: {
  author(post, args, context) {
    return context.userLoader.load(post.userId);
  }
}
```

작성자 조회 요청들이 모여 다음과 같은 쿼리 하나로 실행된다.

```
SELECT *
FROM users
WHERE id IN (...);
```

DataLoader는 일반적으로 다음 두 기능을 제공한다.

- 여러 개별 요청을 한 번의 배치 요청으로 결합
- 동일 요청 안에서 같은 키에 대한 결과 캐싱

DataLoader 캐시는 보통 요청 단위로 생성해야 한다. 전역으로 공유하면 사용자별 권한이나 데이터 최신성 문제가 생길 수 있다.

# 일대다 관계에서의 N+1

N+1 문제는 다대일뿐 아니라 컬렉션 조회에서도 발생한다.

```
List<Post> posts = postRepository.findAll();

for (Post post : posts) {
    System.out.println(post.getComments().size());
}
```

실행되는 SQL은 다음과 비슷하다.

```
SELECT * FROM posts;

SELECT * FROM comments WHERE post_id = 1;
SELECT * FROM comments WHERE post_id = 2;
SELECT * FROM comments WHERE post_id = 3;
-- ...
```

이를 해결하는 방법은 요구사항에 따라 다르다.

### 댓글 전체가 필요하다면

배치 조회를 사용할 수 있다.

```
SELECT *
FROM comments
WHERE post_id IN (1, 2, 3, ...);
```

### 댓글 개수만 필요하다면

댓글을 모두 로딩할 필요 없이 집계 쿼리를 사용한다.

```
SELECT
    p.id,
    p.title,
    COUNT(c.id) AS comment_count
FROM posts p
LEFT JOIN comments c ON c.post_id = p.id
GROUP BY p.id, p.title;
```

단순히 `comments.size()`를 호출하면 ORM 설정에 따라 댓글 객체 전체를 가져올 수 있다. 필요한 것이 개수뿐이라면 `COUNT`가 더 적절하다.

# 페이지네이션과 FETCH JOIN 문제

다대일 관계는 FETCH JOIN을 사용하면서 페이지네이션하기 비교적 쉽다.

```
SELECT p.*, u.*
FROM posts p
JOIN users u ON u.id = p.user_id
ORDER BY p.id DESC
LIMIT 20;
```

하지만 일대다 컬렉션을 FETCH JOIN하면 문제가 생길 수 있다.

게시글 1개에 댓글이 10개라면 SQL 결과에는 게시글이 10행으로 나타납니다. 이 상태에서 `LIMIT 20`을 적용하면 게시글 20개가 아니라 JOIN 결과 20행이 선택된다.

따라서 다음과 같은 2단계 방식이 자주 사용된다.

```
-- 1. 페이지에 해당하는 게시글 조회
SELECT *
FROM posts
ORDER BY id DESC
LIMIT 20 OFFSET 0;

-- 2. 해당 게시글들의 댓글 일괄 조회
SELECT *
FROM comments
WHERE post_id IN (...);
```

또는 다음 전략을 사용할 수 있다.

- 먼저 부모 ID만 페이지 조회
- 조회한 ID를 이용해 필요한 데이터를 다시 JOIN
- 컬렉션은 배치 로딩
- 목록에서는 댓글 개수만 조회
- 상세 화면에서만 댓글 전체 조회

# 여러 단계의 N+1

연관관계가 중첩되면 N+1이 여러 단계에서 발생할 수 있다.

```
주문 목록
 ├─ 주문 고객
 └─ 주문 상품 목록
     └─ 각 상품 정보
```

예를 들어:

1. 주문 100개 조회: 1번
2. 주문별 고객 조회: 최대 100번
3. 주문별 주문 항목 조회: 100번
4. 주문 항목별 상품 조회: 수백 번

이를 단순히 하나의 거대한 JOIN으로 해결하면 결과 행이 지나치게 많아질 수 있다. 이 경우 관계별 전략을 조합해야 한다.

```
주문 + 고객       → JOIN
주문 항목         → IN 배치 조회
상품              → IN 배치 조회
목록에 필요한 값  → DTO Projection
```

핵심은 “모든 것을 한 쿼리로 가져오기”가 아니라, **전체 데이터양과 쿼리 왕복을 균형 있게 줄이는 것**이다.

# N+1을 발견하는 방법

## 1. SQL 로그 확인

개발 환경에서 ORM SQL 로그를 켜고 동일한 형태의 쿼리가 반복되는지 확인한다.

```
SELECT ... FROM users WHERE id = ?
SELECT ... FROM users WHERE id = ?
SELECT ... FROM users WHERE id = ?
```

파라미터만 바뀌는 동일 쿼리가 반복된다면 N+1 가능성이 높다.

단, SQL 로그에는 개인정보나 비밀값이 포함될 수 있으므로 운영 환경에서 파라미터 로깅을 켤 때는 주의해야 한다.

## 2. 요청당 쿼리 수 측정

단순 실행 시간보다 요청별 쿼리 수를 측정하는 것이 더 빠르게 문제를 찾는 데 도움이 된다.

예를 들어 게시글 목록 API의 기대값을 다음처럼 정할 수 있다.

```
게시글 수와 관계없이:
- 게시글 조회 1회
- 작성자 조회 1회
- 댓글 개수 조회 1회

총 3회 이하
```

## 3. APM과 DB 모니터링

운영 환경에서는 다음 지표를 확인한다.

- HTTP 요청별 DB 호출 횟수
- 동일 SQL의 반복 실행 횟수
- DB 총 소요 시간
- 느린 트랜잭션
- 커넥션 풀 대기 시간
- 특정 엔드포인트의 쿼리 증가 추세

## 4. 데이터 수를 늘려 테스트

데이터 3개로 테스트하면 N+1 문제가 잘 드러나지 않습니다. 100개나 1,000개를 넣고 쿼리 횟수와 실행 시간을 비교해야 한다.

## 5. 쿼리 수를 테스트로 고정

성능 회귀를 막기 위해 통합 테스트에서 쿼리 횟수를 검증할 수 있다.

개념적인 예시는 다음과 같다.

```
@Test
void 게시글_목록은_작성자와_함께_정해진_쿼리_수로_조회된다() {
    queryCounter.reset();

    postService.getPosts();

    assertThat(queryCounter.getCount()).isLessThanOrEqualTo(2);
}
```

데이터 수가 늘어나도 쿼리 수가 일정한지 검증하는 것이 중요하다.

```
게시글 10개  → 2개 쿼리
게시글 100개 → 2개 쿼리
```

# 캐시 해결

캐시는 N+1 문제의 영향을 줄일 수 있지만, 일반적으로 근본적인 해결책은 아니다.

같은 작성자를 여러 게시글이 참조하면 1차 캐시나 요청 단위 캐시 덕분에 동일 작성자를 반복 조회하지 않을 수 있다. 하지만 작성자가 모두 다르면 여전히 N개의 조회가 발생한다.

또한 캐시는 다음 문제를 추가한다.

- 캐시 무효화
- 오래된 데이터
- 메모리 사용량
- 권한별 데이터 분리
- 캐시 미스 시 성능 급락

따라서 먼저 JOIN, Projection, 배치 로딩 등으로 데이터 접근 방식을 개선하고, 캐시는 별도의 성능 최적화 수단으로 사용하는 것이 좋다.

# 인덱스 추가

인덱스는 각 개별 쿼리를 빠르게 만들 수 있지만, 쿼리가 N번 실행되는 구조 자체는 바꾸지 못한다.

```
CREATE INDEX idx_posts_user_id ON posts(user_id);
```

인덱스는 JOIN이나 `WHERE ... IN (...)` 조회에도 중요하지만 다음 두 문제는 구분해야 한다.

```
인덱스 문제 → 한 쿼리 자체가 느림
N+1 문제   → 작은 쿼리가 너무 많이 실행됨
```

실제 시스템에서는 두 문제가 동시에 존재할 수 있으므로 실행 계획과 쿼리 횟수를 함께 살펴봐야 한다.

# 해결 전략 선택 기준

|상황|적합한 방법|
|---|---|
|다대일·일대일 데이터를 함께 표시|FETCH JOIN, Entity Graph|
|목록에 일부 필드만 필요|DTO Projection|
|일대다 컬렉션을 여러 부모에 대해 조회|Batch Fetching, IN 조회|
|컬렉션과 페이지네이션을 함께 사용|부모 페이지 조회 후 컬렉션 배치 조회|
|GraphQL 필드 리졸버|DataLoader|
|연관 데이터의 개수만 필요|`COUNT` 집계 쿼리|
|연관관계가 여러 단계로 중첩|JOIN과 배치 조회 조합|
|반복 조회 데이터가 매우 안정적|구조 개선 후 캐시 검토|

# 주의점

## 모든 관계를 EAGER로 변경

당장의 N+1은 줄어들 수 있지만 불필요한 데이터까지 항상 로딩하거나 더 복잡한 쿼리를 만들 수 있다. 조회별로 필요한 관계를 명시하는 편이 좋다.

## 모든 관계를 한 번에 FETCH JOIN

여러 컬렉션을 동시에 JOIN하면 결과 행이 폭발할 수 있다. 데이터양과 관계의 카디널리티를 먼저 확인해야 한다.

## Repository 호출만 확인

쿼리는 Repository 메서드가 실행될 때만 발생하지 않는다. 다음 시점에도 지연 로딩이 발생할 수 있다.

- DTO 변환
- JSON 직렬화
- 로그 출력
- 템플릿 렌더링
- `toString()`
- 디버거에서 필드 확인
- 객체 매퍼 실행

특히 엔티티를 API 응답으로 직접 반환하면 JSON 직렬화 과정에서 연관 필드에 접근하여 예상하지 못한 쿼리가 실행될 수 있다.

## 개발 데이터만으로 판단

개발 DB의 데이터가 적으면 문제를 발견하기 어렵습니다. 데이터가 증가했을 때 쿼리 수도 증가하는지 확인해야 한다.

# 접근 순서

N+1 문제를 발견했을 때는 다음 순서로 접근하면 좋다.

1. 어떤 코드에서 반복 쿼리가 발생하는지 확인
2. 실제 화면이나 API에 필요한 데이터가 무엇인지 정리
3. 전체 엔티티가 필요한지, 일부 필드만 필요한지 판단
4. 다대일이면 JOIN 또는 Projection을 우선 검토
5. 일대다면 배치 조회나 2단계 조회를 검토
6. 페이지네이션과 JOIN 중복 여부를 확인
7. 쿼리 횟수뿐 아니라 결과 행 수와 전송 데이터양도 측정
8. 인덱스와 실행 계획을 확인
9. 데이터 수를 늘린 테스트로 개선 결과를 검증
10. 쿼리 수 테스트나 모니터링으로 재발을 방지
