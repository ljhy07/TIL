## Redis란

**Redis는 데이터를 주로 메모리에 저장하고, 다양한 자료구조를 빠르게 읽고 수정할 수 있는 데이터 저장소이다.**

보통 MySQL이나 PostgreSQL 앞에 두는 **캐시**로 많이 사용하지만, 로그인 세션 관리, 실시간 순위, 요청 횟수 제한, 이벤트 처리 등에도 활용한다.

Redis는 핵심이 세 가지이다.

- **메모리 중심:** 자주 접근하는 데이터를 빠르게 처리한다.
- **Key–Value 구조:** 키를 통해 데이터를 조회한다.
- **자료구조 지원:** 문자열뿐 아니라 집합, 정렬된 집합, 해시 등을 서버에서 직접 조작한다.

---

## Redis는 데이터 저장 방식

관계형 데이터베이스가 테이블과 행을 중심으로 데이터를 표현한다면, Redis는 **키와 그 키에 대응하는 값**을 중심으로 표현한다.

```
키                       값
─────────────────────────────────────────
user:100:name            "민수"
product:42:views         1532
session:abc123           로그인 세션 정보
ranking:weekly           사용자별 점수 목록
```

예를 들어 다음 명령은 이름을 저장하고 조회한다.

```
SET user:100:name "민수"
GET user:100:name
```

결과:

```
"민수"
```

`user:100:name`처럼 콜론으로 구분하는 것은 **개발자가 정하는 이름 규칙**이다. 실제로 폴더나 테이블이 생성되는 것은 아니다.

### 단순한 문자열 저장소보다 기능이 많다

Redis에서는 값의 형태에 맞춰 연산할 수 있다.

```
INCR product:42:views
```

이 명령은 조회수를 1 증가시킨다.

애플리케이션이 값을 가져와 계산한 뒤 다시 저장할 필요 없이, **Redis 안에서 증가 연산이 완료된다.**

## Redis가 빠른 이유

### 일반적인 데이터 접근이 메모리에서 이루어진다

디스크에 접근하는 작업보다 메모리 접근이 일반적으로 빠르다. Redis는 데이터셋을 주로 메모리에 유지하므로 낮은 지연시간을 제공할 수 있다.

다만 MySQL이나 PostgreSQL도 버퍼 캐시를 활용한다. 따라서 “Redis는 메모리, 관계형 DB는 매번 디스크”라고 구분하면 부정확하다.

### 접근 방식과 연산이 단순하다

키로 값을 찾거나, 카운터를 증가시키거나, 집합에 원소를 추가하는 작업에 최적화되어 있다.

복잡한 SQL 실행 계획이나 여러 테이블의 조인을 거치지 않아도 되는 작업이 많다.

### 명령 실행 모델이 비교적 단순하다

일반적인 Redis 명령 실행은 주로 메인 스레드에서 순차적으로 처리된다. 이 구조는 명령 실행 과정의 복잡한 잠금 경쟁을 줄이는 데 도움이 된다.

다만 **“Redis의 모든 작업이 단일 스레드로 실행된다”는 설명은 부정확하다.** 네트워크 I/O나 백그라운드 작업에는 다른 스레드 또는 프로세스가 사용될 수 있다.

반대로 실행 시간이 긴 명령은 다른 요청도 지연시킬 수 있다. 실제 성능은 명령의 복잡도, 데이터 크기, 네트워크 왕복, 영속성 설정 등에 영향을 받는다.

## 주요 자료구조와 사용 사례

Redis의 강점은 **데이터 형태에 맞는 자료구조를 선택할 수 있다는 것**이다.

| 자료구조       | 특징                 | 대표 활용         |
| ---------- | ------------------ | ------------- |
| String     | 문자열·바이너리·숫자 형태의 값  | 캐시, 카운터, 토큰   |
| Hash       | 필드와 값으로 구성된 객체     | 사용자 정보, 상품 속성 |
| List       | 순서가 있고 중복을 허용하는 목록 | 최근 항목, 간단한 큐  |
| Set        | 중복 없는 원소 집합        | 좋아요 사용자, 태그   |
| Sorted Set | 원소마다 점수를 가진 집합     | 순위표, 점수 기반 조회 |
| Stream     | ID가 붙은 이벤트 기록      | 이벤트 처리, 작업 소비 |

아래는 널리 쓰이는 기본 자료구조 중심의 설명이다. 전체 지원 기능은 Redis 버전과 배포 구성에 따라 확인해야 한다.

### String: 캐시와 카운터

```
SET product:42:name "기계식 키보드"
GET product:42:name

SET product:42:views 0
INCR product:42:views
```

숫자 카운터도 String으로 다룬다.

JSON 문자열을 그대로 저장할 수도 있다.

```
SET user:100 '{"name":"민수","level":3}'
```

이 경우 일반 String 명령 관점에서는 JSON 내부 필드가 아니라 **문자열 전체**를 저장한 것이다.

### Hash: 객체의 필드를 개별 관리

```
HSET user:100 name "민수" level 3
HGET user:100 name
HINCRBY user:100 level 1
HGETALL user:100
```

필드 하나만 읽거나 수정할 때 편리하다.

### List: 순서가 있는 목록

```
RPUSH jobs "job-1" "job-2"
LPOP jobs
```

오른쪽에 넣고 왼쪽에서 꺼내면 먼저 들어온 항목부터 처리할 수 있다.

다만 단순히 꺼내는 방식은 소비자가 처리 중 죽었을 때 작업이 유실될 수 있어, 신뢰성이 필요한 큐는 별도 처리 설계가 필요한다.

### Set: 중복 제거

```
SADD post:10:likes user:100 user:200 user:100
SCARD post:10:likes
```

같은 원소는 한 번만 저장되므로 결과는 `2`이다.

### Sorted Set: 순위표

```
ZADD ranking:weekly 1200 user:100
ZADD ranking:weekly 1800 user:200
ZRANGE ranking:weekly 0 9 REV WITHSCORES
```

점수가 높은 순서로 최대 10명을 조회한다.

### Stream: 이벤트 기록

```
XADD order:events * type created orderId 1001
```

이벤트에 ID를 붙여 저장한다. 소비자 그룹을 이용하면 여러 작업자가 메시지를 나눠 처리하고 처리 완료를 확인할 수 있다.

**소비자 그룹을 쓴다고 정확히 한 번 처리가 자동 보장되지는 않는다.** 재처리될 수 있으므로 소비자 로직은 중복 실행을 고려해야 한다.

## 데이터베이스 캐시

캐시는 **다시 계산하거나 조회하는 비용을 줄이기 위해 복사본을 보관하는 것**이다.

예를 들어 상품 상세 페이지를 열 때마다 데이터베이스에서 같은 상품을 조회한다면, 결과를 Redis에 잠시 저장할 수 있다.

### Cache-Aside 방식

애플리케이션이 캐시를 직접 조회하고 채우는 방식이다.

```
사용자 요청
    ↓
애플리케이션 → Redis 조회
                  │
                  ├─ 데이터 있음 → 바로 응답
                  │
                  └─ 데이터 없음 → DB 조회
                                      ↓
                                  Redis에 저장
                                      ↓
                                     응답
```

처리 순서는 다음과 같다.

1. Redis에서 상품 정보를 찾는다.
2. 있으면 바로 반환한다. 이를 **캐시 히트**라고 한다.
3. 없으면 DB에서 조회한다. 이를 **캐시 미스**라고 한다.
4. 조회 결과를 Redis에 저장한다.
5. 사용자에게 반환한다.

예시:

```
SET cache:product:42 '{"name":"키보드","price":89000}' EX 300
```

이 값은 300초 동안 유효하다.

### 캐시 장점

동일한 데이터를 반복해서 읽는 서비스에서는 다음 효과를 기대할 수 있다.

- DB 조회량 감소
- 응답시간 단축
- 순간적인 트래픽 증가에 대한 부담 완화

다만 캐시 효율은 **조회 결과의 재사용 빈도와 데이터 변경 빈도**에 크게 좌우된다.

### 캐시 갱신

DB에서 가격을 수정했는데 Redis에 이전 가격이 남아 있으면 오래된 정보가 반환된다.

흔한 접근은 다음과 같다.

```
DB 변경을 커밋
    ↓
관련 캐시 삭제
    ↓
다음 조회에서 DB의 새 값으로 캐시 생성
```

하지만 DB와 Redis의 변경은 하나의 트랜잭션으로 자동 묶이지 않는다. 삭제 실패나 동시 요청으로 오래된 값이 다시 들어가는 상황까지 고려해야 한다.

**TTL은 오래된 값이 남아 있는 시간을 제한하지만, 즉시 일관성을 보장하지는 않는다.**

## TTL: 데이터에 유효기간 설정하기

TTL은 **Time To Live**, 즉 데이터가 유효한 남은 시간이다.

```
SET verification:email:100 "482193" EX 180
```

180초 동안 유효한 데이터를 저장한다.

기존 키에 만료시간을 설정할 수도 있다.

```
EXPIRE user:100 3600
TTL user:100
```

주로 다음 데이터에 활용한다.

- 일시적인 캐시
- 로그인 세션
- 인증번호
- 요청 제한용 카운터

### 만료와 실제 메모리 정리는 구분된다

유효기간이 지난 키는 읽을 때 만료 처리되거나 주기적인 정리 과정에서 제거된다.

따라서 TTL을 **“정확히 그 시각에 콜백이 실행되는 스케줄러”**처럼 사용해서는 안 된다.

또한 키에 TTL을 지정하지 않았다면, 모든 데이터가 기본적으로 자동 만료되는 것은 아니다.

## 캐시 이외 용도

### 로그인 세션 공유

애플리케이션 서버가 여러 대일 때 로그인 세션을 Redis에 저장하면 서버 간에 공유할 수 있다.

```
앱 서버 A ─┐
앱 서버 B ─┼─ Redis의 공통 세션 저장소
앱 서버 C ─┘
```

사용자의 요청이 다른 서버로 가더라도 같은 세션 정보를 조회할 수 있다.

### 요청 횟수 제한

사용자별 요청 수를 세고 일정 기준을 넘으면 제한한다.

```
rate:user:100:202609171430 → 37
```

예를 들어 분 단위 키를 사용하면 해당 분에 들어온 요청 수를 기록할 수 있다.

구현할 때는 카운터 증가와 최초 만료 설정이 어긋나지 않도록 해야 한다. 엄밀한 제한이 필요하면 Lua 스크립트 등으로 관련 연산을 묶고, 시간 구간 경계에서 요청이 몰리는 문제도 고려한다.

### 실시간 순위

Sorted Set으로 점수를 갱신하고 상위 사용자 또는 특정 사용자의 순위를 조회할 수 있다.

### 실시간 메시지와 이벤트

Redis에는 Pub/Sub과 Stream이 있지만 성격이 다룬다.

|구분|Pub/Sub|Stream|
|---|---|---|
|기본 개념|연결된 구독자에게 실시간 전달|이벤트를 저장하고 읽기|
|메시지 기록|재생용 기록을 보관하지 않음|보존된 기록을 다시 읽을 수 있음|
|연결이 끊긴 소비자|그동안 메시지를 놓침|보존 범위 내에서 이후 읽기 가능|
|처리 완료 확인|기본 제공하지 않음|소비자 그룹에서 지원|

Pub/Sub은 **최대 한 번 전달** 방식이며, 연결 문제 등으로 놓친 메시지를 다시 전달하지 않는다. Stream의 복구 가능성은 기록 보존과 영속성 설정에도 달려 있다. 

### 분산 락

여러 서버가 같은 작업을 동시에 수행하지 않도록 잠금 키를 사용할 수 있다.

```
SET lock:report:100 unique-token NX PX 10000
```

- `NX`: 키가 없을 때만 저장
- `PX 10000`: 10초 후 만료
- `unique-token`: 잠금 소유자를 구분하는 값

실제로는 **자신이 획득한 락인지 확인하고 원자적으로 해제**해야 한다. 작업 도중 락이 만료되면 다른 서버도 작업을 시작할 수 있으므로, 이 명령 하나만으로 모든 중복 실행 문제가 해결되지는 않는다.

## 메모리에 저장하면 재시작 시 데이터 존재 여부

**영속성 설정에 따라 달라진다.**

Redis는 데이터를 디스크에 기록하고 재시작 시 복구할 수 있다. 대표 방식은 RDB와 AOF이다.

|방식|기록 방법|장점|주의점|
|---|---|---|---|
|RDB|특정 시점의 스냅샷 저장|백업·복원에 유리|마지막 스냅샷 이후 변경 유실 가능|
|AOF|쓰기 작업을 로그로 기록|동기화 주기에 따라 유실 범위 축소|디스크 I/O와 로그 관리 비용|
|함께 사용|스냅샷과 쓰기 로그 활용|복구와 백업 선택지 확대|메모리·디스크 운영 부담|
|미사용|디스크 복구 데이터 없음|단순한 재생성 가능 캐시에 적합|재시작 시 데이터 복구 불가|

### RDB의 예

마지막 스냅샷이 14시이고 14시 4분에 장애가 발생했다면, 이후 변경 내용이 유실될 수 있다.

### AOF의 예

쓰기 내용을 로그에 기록하고, `fsync` 정책에 따라 디스크 반영 시점을 결정한다.

- `always`: 각 쓰기 반영에 맞춰 동기화하므로 내구성에 유리하지만 비용이 큼
- `everysec`: 대략 매초 동기화하며 장애 시 최근 약 1초의 쓰기 유실 가능
- `no`: 운영체제의 디스크 반영 정책에 의존

영속성을 켜더라도 **모든 장애에서 데이터 유실이 0이 되는 것은 아니다.** 스냅샷 생성과 AOF 재작성에는 추가 메모리와 I/O 여유도 필요하다.

## 복제, Sentinel, Cluster의 차이

세 기능은 각각 해결하는 문제가 다르다.

### 복제: 데이터 복사본 유지

```
Primary ──복제──→ Replica
        └─복제──→ Replica
```

Primary의 데이터를 Replica에 복사한다.

읽기를 분산하거나 장애 시 전환할 복사본을 확보하는 데 사용한다. 일반적인 복제는 비동기이므로 Replica가 잠시 뒤처질 수 있고, 장애 전환 과정에서 최근 쓰기가 유실될 수도 있다.

### Sentinel: 장애 감지와 자동 전환

Sentinel은 Primary의 상태를 감시하고, 장애 시 Replica를 새 Primary로 승격하는 역할을 한다.

**데이터를 여러 서버로 나누는 샤딩 기능은 아니다.**

### Cluster: 데이터를 여러 노드에 분산

Redis Cluster는 키 공간을 **16,384개의 해시 슬롯**으로 나누고 노드들이 이를 분담한다.

```
Primary A → 일부 슬롯
Primary B → 일부 슬롯
Primary C → 일부 슬롯
```

각 Primary에 Replica를 두면 장애 전환도 구성할 수 있다.

주의할 점은 여러 키를 함께 처리하는 명령이나 트랜잭션이 일반적으로 **같은 슬롯에 속한 키**를 요구한다는 것이다.

```
cart:{user100}:items
cart:{user100}:total
```

이처럼 같은 해시 태그를 사용하면 관련 키를 같은 슬롯에 배치할 수 있다.

|기능|주된 목적|
|---|---|
|복제|데이터 복사본과 읽기 분산|
|Sentinel|장애 감지와 Primary 자동 전환|
|Cluster|데이터 분산과 수평 확장, 장애 전환|

## 원자성과 트랜잭션의 동작

### 개별 명령과 여러 명령은 다르다

다음 연산은 원자적으로 실행된다.

```
INCR counter
```

반면 애플리케이션에서 다음처럼 처리하면 경쟁 조건이 생길 수 있다.

```
GET counter
애플리케이션에서 1 증가
SET counter 새값
```

두 요청이 동시에 같은 값을 읽으면 증가분 하나가 사라질 수 있다.

**개별 명령이 원자적이어도 여러 명령으로 구성된 로직이 자동으로 원자적이지는 않다.**

### MULTI / EXEC

여러 명령을 묶어 다른 클라이언트 명령이 중간에 끼어들지 않도록 실행할 수 있다.

```
MULTI
SET user:100:status "active"
INCR active:user:count
EXEC
```

다만 관계형 DB처럼 실행 도중 오류가 발생한 명령 때문에 다른 명령의 변경을 자동으로 되돌리는 **일반적인 롤백을 제공하지 않는다.**

조건부 갱신에는 `WATCH`, 서버 안에서 판단과 갱신을 묶는 데는 Lua 스크립트나 Redis Functions를 사용할 수 있다.

### Pipeline은 성능을 위한 기능

Pipeline은 여러 명령을 보내고 응답을 묶어 받아 네트워크 왕복 비용을 줄인다.

**Pipeline 자체는 명령 묶음의 원자성을 보장하지 않는다.**

## 메모리 부족

Redis에서는 `maxmemory`와 퇴거 정책으로 메모리 한도에 도달했을 때의 동작을 정한다.

|정책|동작|
|---|---|
|`noeviction`|키를 자동 제거하지 않고, 메모리를 늘리는 쓰기에 오류 반환|
|`allkeys-lru`|전체 키 중 최근 사용이 적은 키를 우선 제거|
|`allkeys-lfu`|전체 키 중 사용 빈도가 낮은 키를 우선 제거|
|`volatile-lru`|TTL이 있는 키 중 최근 사용이 적은 키를 우선 제거|
|`volatile-ttl`|TTL이 있는 키 중 만료가 가까운 키를 우선 제거|

LRU와 LFU는 근사 알고리즘을 사용한다.

여기서 구분해야 할 점이 있다.

- **만료:** TTL이 끝나서 데이터가 사라짐
- **퇴거:** 메모리 공간을 확보하려고 데이터가 사라짐

따라서 **TTL이 남아 있어도 퇴거 정책에 따라 키가 제거될 수 있다.**

캐시와 유실되면 안 되는 작업 데이터를 같은 인스턴스에 섞으면 퇴거 정책을 정하기 어려워진다. 역할에 따라 분리하면 운영 기준을 명확히 할 수 있다.

## 운영할 때 자주 겪는 문제

### 캐시 스탬피드

인기 키가 만료되는 순간, 다수의 요청이 동시에 DB로 몰리는 현상이다.

완화 방법으로는 다음이 있다.

- 같은 데이터의 재조회 요청을 하나로 합치기
- 만료 전에 백그라운드 갱신하기
- 여러 키의 TTL에 임의의 편차를 주어 동시 만료 줄이기

TTL 편차는 여러 키가 한꺼번에 만료되는 문제에 도움이 되지만, 인기 키 하나에 요청이 몰리는 문제까지 해결하지는 않는다.

### Hot Key

특정 키에 트래픽이 집중되는 현상이다.

Cluster로 노드를 늘려도 키 하나는 특정 샤드가 담당하므로 병목이 남을 수 있다. 로컬 캐시, 읽기 분산, 데이터 분할 등을 검토해야 한다.

### Big Key

값이 매우 크거나 한 자료구조에 원소가 지나치게 많은 상태이다.

전체 조회나 삭제가 오래 걸리고, 네트워크와 다른 요청에 영향을 줄 수 있다. 큰 데이터를 적절히 나누고 한 번에 읽는 범위를 제한하는 것이 도움이 된다.

### Redis 장애가 DB 장애로 번지는 문제

Redis가 멈췄을 때 모든 요청을 바로 DB로 보내면 DB가 과부하에 빠질 수 있다.

캐시 장애 시의 동시 요청 제한, 타임아웃, 재시도 정책도 함께 설계해야 한다.

### 모니터링

주로 다음 지표를 함께 본다.

- 메모리 사용량과 퇴거된 키 수
- 캐시 적중률
- 응답시간, 특히 p95·p99
- 느린 명령과 연결 수
- 복제 지연
- RDB·AOF 저장 상태

캐시 적중률이 높더라도 큰 값의 전송이나 느린 명령 때문에 사용자 응답은 느릴 수 있다.

## 관계형 데이터베이스와 Redis

| 항목        | Redis                   | MySQL·PostgreSQL           |
| --------- | ----------------------- | -------------------------- |
| 기본 데이터 모델 | 키와 자료구조                 | 테이블과 관계                    |
| 대표 강점     | 빠른 키 접근, 카운터, 순위, 임시 상태 | 관계 표현, SQL, 제약조건, 복잡한 트랜잭션 |
| 유효기간 관리   | TTL 제공                  | 보통 별도 로직이나 정리 작업 필요        |
| 조회 방식     | 키·자료구조 중심               | 조건 검색·조인·집계                |
| 흔한 역할     | 캐시, 세션, 실시간 상태          | 업무 데이터의 기준 저장소             |

예를 들어 쇼핑몰에서는 다음과 같이 역할을 나눌 수 있다.

```
MySQL / PostgreSQL
  ├─ 회원 원본 정보
  ├─ 주문과 결제 기록
  └─ 상품과 재고의 기준 데이터

Redis
  ├─ 상품 조회 캐시
  ├─ 로그인 세션
  ├─ 인기 상품 순위
  └─ API 요청 횟수
```

Redis를 주 데이터베이스로 사용하는 것도 가능하지만, **허용 가능한 데이터 유실, 복구 방식, 일관성, 메모리 비용을 먼저 설계해야 한다.**

Redis 도입 여부를 판단할 때는 “빠른가?”와 함께 **“이 데이터가 사라지면 다시 만들 수 있는가?”, “얼마나 오래된 값을 허용할 수 있는가?”**를 물어보는 것이 중요하다.
